Board: LOLIN(WeMos) D1 R1  (boards.txt id "d1", build.variant=d1, build.board=ESP8266_WEMOS_D1R1)
Arduino-Uno-shield-form-factor ESP8266 board. NOT the same as the "D1 Mini" family
(sibling variant dir ../d1_mini) - confirmed distinct via boards.txt (only one entry,
"d1", uses build.variant=d1) and via pins_arduino.h (D1 R1 maps D0=GPIO3(RX)/D1=GPIO1(TX)
to match Arduino Uno's D0=RX/D1=TX convention; D1 Mini instead uses D0=GPIO16/D1=GPIO5
and separate RX/TX aliases - a real hardware/pin-map difference between the two boards).

=== 2026-07-12: dedicated-hardware pin-exclusion audit (separate pass) ===

Scope: this is the full KEEP-vs-EXCLUDE dedicated-hardware sweep (per the
board-variant pin-audit playbook), distinct from the earlier button/LED/ADC
pass above. Re-read pins_arduino.h and variants/esp8266/esp8266/generic/
common.h in full; re-checked variants/esp8266/esp8266/d1/board.json in full.

--- Step: alias-collision check on the tagged LED pin (GPIO2) ---

Checked whether GPIO2 (LED_BUILTIN, tagged "led_low" in board.json) is
aliased anywhere in pins_arduino.h or common.h as SDA/SCL/SS/MOSI/MISO/SCK/
TX/RX (the contamination pattern found repeatedly on the ESP32 side this
session). Direct inspection of both files:
  - SDA = PIN_WIRE_SDA = 4 (pins_arduino.h line 29/32)
  - SCL = PIN_WIRE_SCL = 5 (pins_arduino.h line 30/33)
  - SS = PIN_SPI_SS = 15, MOSI = PIN_SPI_MOSI = 13, MISO = PIN_SPI_MISO = 12,
    SCK = PIN_SPI_SCK = 14 (common.h lines 42-50)
  - TX/RX are hardware UART0 on GPIO1/GPIO3 (D1/D0), not GPIO2
  - GPIO2's only other alias in this file is D9 (plain D-numbering, not a
    bus alias)
None of SDA/SCL/SS/MOSI/MISO/SCK/TX/RX resolve to 2. GPIO2 is clean - no
collision, no contamination of its capability list. board.json's chipGpios
entry for "2" already contains only ["digital_output","pwm_output","led_low"]
with no bus-role tag, confirming there was nothing to fix.
RESULT: NO CHANGE required for this check.

--- Step: verify the dual D0-D15 numbering is intentional, not a bug ---

The task flagged that several GPIOs appear under two different D-numbers
(GPIO12 = D6 and D12; GPIO13 = D7 and D11; GPIO14 = D5 and D13; GPIO4 = D4
and D14; GPIO5 = D3 and D15) and asked to confirm this is deliberate dual
pin-map support rather than a bug.

Cross-checked common.h's SPI macros against this file's D10-D13 aliases:
  PIN_SPI_SS=15 -> D10=15, PIN_SPI_MOSI=13 -> D11=13,
  PIN_SPI_MISO=12 -> D12=12, PIN_SPI_SCK=14 -> D13=14.
This is an exact match to the classic Arduino Uno shield SPI-on-digital-pin
convention (Uno: D10=SS, D11=MOSI, D12=MISO, D13=SCK), confirmed against
WeMos D1 R2 SPI pinout references (SPI hardware lives on GPIO12/13/14/15,
same GPIOs as D5-D8 in the short numbering / D10-D13 in the extended
numbering - source: steve.fi/hardware/d1-pins and general D1 R2 pinout
pages consulted this pass). So D0-D8 is the "short" Uno-digital-row naming
(matching this board's physical Uno-shield form factor: D0=RX/D1=TX like
an Uno) and D9-D15 is a second, overlapping naming scheme laid over the
SAME physical GPIOs so that Uno-shield SPI libraries expecting D10-D13 for
SS/MOSI/MISO/SCK resolve to the correct GPIOs on this ESP8266 board. This
is a normal, intentional vendor convenience pattern (dual pin-map for Uno
shield compatibility), not a duplicate/conflicting definition and not a
dedicated-hardware exclusion candidate - the underlying GPIOs (4,5,12,13,14)
are still general-purpose and already correctly listed once each in
board.json's chipGpios.
RESULT: NO CHANGE required - confirmed intentional, not a bug.

--- Step: onboard voltage-regulator / shield-header dedicated hardware check ---

Researched whether the Uno-shield form factor dedicates any GPIO to a
voltage-regulator-select jumper or other onboard peripheral beyond the
D-numbering and A0 divider already documented.
  - https://mischianti.org/wemos-d1-esp8266-manage-relay-and-shield/ - turned
    out to document a D1 Mini relay shield, not this Uno-shield board;
    no Uno-shield-specific jumper info, not used as a source for this board.
  - Web searches on "WeMos D1 R2 jumper JP1 5V regulator select shield power"
    and general D1/D1 R2 regulator discussions (eevblog forum thread title,
    wemos.cc DC Power Shield docs) confirm that voltage-regulator-select
    jumpers on WeMos D1-family *shields* (e.g. the separate DC Power Shield
    product) select between the shield's own regulator and the main board's
    3.3V rail - this is a VCC/power-rail selection on add-on shields, not a
    GPIO-level function of the D1 board itself, and no such jumper exists on
    the D1 R1/R2 base board's own schematic per sources consulted (only a
    single onboard 5V-in -> 3.3V LDO regulator feeding the ESP module,
    per source #4/#5 in the prior audit pass and the search results this
    pass). No specific GPIO is dedicated to a regulator-select function.
  - No SD card slot, no second LED/RGB, no additional onboard sensor found
    on the base D1 R1 board (consistent with the prior pass's findings).
RESULT: NO CHANGE required - no additional dedicated-hardware GPIO found.

No board.json edits were made. All three checks (LED-pin alias-collision,
