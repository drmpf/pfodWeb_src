=== Considered but NOT changed, and why ===

- pins_arduino.h defines `#define LED_BUILTIN 16` for this board. Per task instructions,
  an alias name/LED_BUILTIN value in pins_arduino.h is explicitly NOT sufficient evidence
  on its own — real vendor documentation or a schematic is required to confirm an onboard
  LED exists on GPIO16, its drive polarity (active-high/low), and whether it's even
  present as a physical component (some "Phoenix"-style community-contributed
  Arduino-core variants are added purely to get pin-numbering right for a chip module,
  without every declared alias corresponding to a populated onboard part).
  No such vendor documentation could be located (see sources above — the vendor site is
  dead and no independent teardown/schematic exists), so GPIO16 was NOT tagged with any
  led_high/led_low/pwm_output capability. It also would not add pwm_output regardless,
  since chip-level defaults already correctly omit pwm_output for GPIO16 (RTC-domain pin,
  no PWM per the ESP8266 chip's own hardware limits — that's chip-wide, not board-specific).
- No button alias of any kind is declared anywhere in phoenix_v1/pins_arduino.h, and no
  vendor source confirms a physical user button on this board at all, so no button tag
  was considered for any GPIO.
- Conclusion: no board.json was created for phoenix_v1. It continues to inherit the
  esp8266 chip-level default board.json (variants/esp8266/esp8266/board.json) unchanged,
  which is the correct behavior in the absence of confirmed board-specific facts.

=== ADC reference voltage ===

- No board.json exists (see above), so defaultRefVolts continues to be inherited from the
  chip-level default of "1.0" (native ESP8266 bare-chip ADC range, no external divider
  assumed). No source located (PlatformIO board JSON, ESP8266 Arduino core docs, PR #2088,
  or any web search) mentions a resistor-divider network, external ADC circuitry, or any
  0-3.3V analog range claim for this board — unlike NodeMCU/D1 Mini, which do have
  documented on-board dividers and get an overridden defaultRefVolts in their own
  board.json. Left at 1.0V (chip default, no override).

=== Summary ===

No vendor-confirmed onboard button or LED was found for Phoenix 1.0 (espert.co is a dead
domain and no independent documentation/schematic exists), and no evidence of an ADC
divider was found either — no board.json was created/edited and phoenix_v1 continues to
fully inherit the esp8266 chip-level defaults unchanged.

=== 2026-07-12 — Dedicated-hardware pin-exclusion audit (sections 1-6 of the playbook) ===

This is a separate, more thorough pass than the 2026-07-11 button/LED/ADC-divider research
above — it targets pin *availability* (is any GPIO wired to fixed onboard hardware that
should be excluded from the Designer's pin picker), plus a specific check for a
version-selector-macro parser bug found on several sibling boards this session.

--- Version-branch ambiguity check (the reason this board was specifically flagged) ---

`variants/esp8266/esp8266/phoenix_v1/pins_arduino.h` contains `#define PHOENIX_VERSION 1`
but this is a plain, standalone macro — the file has NO `#if`/`#ifdef`/`#else`/`#endif`
structure anywhere except the ordinary `#ifndef Pins_Arduino_h ... #endif` header guard, and
no declaration name (macro or `static const`) appears more than once within the file. So
there is no ambiguity for `build_boards.js`'s comment-blind/ifdef-blind/last-wins regex
parser to mis-resolve within this file — every declaration it will scan is unique and
unconditional.

Checked `variants/esp8266/esp8266/phoenix_v2/pins_arduino.h` as instructed, since the task
flagged this pair as sharing the same era/style as `espectro` and `espresso_lite_v1/v2`,
where a real `#if`/`#else` branch bug was found hiding behind a similar version macro on
some siblings. Confirmed phoenix_v1 and phoenix_v2 are **two completely separate,
self-contained files** (like espresso_lite_v1/v2 turned out to be), NOT one shared file with
`#if PHOENIX_VERSION==1 ... #else ... #endif` branches (unlike espectro's actual bug
pattern). Each file declares its own unambiguous `PHOENIX_VERSION` (1 vs 2) and its own
unambiguous `LED_BUILTIN` (16 vs 2) — no cross-file interaction, and `build_boards.js`
processes each variant directory independently, so there is no last-wins collision between
the two files either.

Conclusion: NO version-branch ambiguity exists in phoenix_v1 (or phoenix_v2). NO FIX
required on this front — the file was already unambiguous going in.

--- KEEP vs EXCLUDE sweep (sections 1-4 of the playbook) ---

Applied the corrected discovery regex (playbook section 11) to
`phoenix_v1/pins_arduino.h`. Every `^#define`/`^static const` line in the file is either the
header guard, the version macro (not a pin), or standard boilerplate already covered by the
exclude list (`PIN_WIRE_SDA`/`PIN_WIRE_SCL`, `static const uint8_t SDA/SCL`, `LED_BUILTIN`).
The shared `variants/esp8266/esp8266/generic/common.h` this file includes adds only the
standard chip-wide `SS`/`MOSI`/`MISO`/`SCK`/`A0` boilerplate aliases (GPIO15/13/12/14, and
the virtual analog pin) — nothing board-specific, nothing dedicated to an onboard peripheral.

No `#define` or `static const` declaration anywhere in this board's file (or its included
common.h) names any radio module, SD card, display, motor/servo/stepper driver, analog mux,
or other fixed onboard peripheral. **No dedicated hardware was found on phoenix_v1** — there
is nothing to EXCLUDE beyond what the chip-level `board.json` default already omits.

--- SDA/SCL/SS/MOSI/MISO/SCK/TX/RX aliasing / capability-contamination check (critical check per task) ---

Checked whether the candidate GPIO already discussed in this file (GPIO16, `LED_BUILTIN`)
collides with any bus alias. It does not: `SDA`=GPIO4, `SCL`=GPIO5, `SS`=GPIO15,
`MOSI`=GPIO13, `MISO`=GPIO12, `SCK`=GPIO14 (all from `common.h`) — none equal GPIO16. Neither
`phoenix_v1/pins_arduino.h` nor `common.h` declares a `TX`/`RX` alias at all for this board,
so there is no serial_tx/serial_rx hard-reservation interaction (per playbook section 7a's
last bullet) to worry about either. No aliasing contamination found.
