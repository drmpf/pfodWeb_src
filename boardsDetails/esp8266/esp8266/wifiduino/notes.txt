CHANGES MADE

Part A (button/LED):
- TAGGED GPIO0 ["digital_input","button"] — vendor datasheet ("WiFiduino-8266数据手册",
  corroborated across 3 independent citations: openjumper.cn index snippets, the Arduino-CN
  datasheet thread, and the CSDN "KEY_FLASH" search-result quote) documents a physical
  KEY_FLASH pushbutton on GPIO0 usable as general user input, not merely a flash/boot pin.
- NOT tagged: GPIO2 (LED_BUILTIN). Vendor datasheet confirms a real onboard LED exists on
  GPIO2 ("L" LED), but no source found (vendor page unreachable, datasheet thread unreachable
  first-hand, PR discussion, PlatformIO docs, multiple CSDN reproductions) states whether it
  is active-high or active-low. Per this session's rule of never inferring polarity from a
  pin alias name (LED_BUILTIN) alone, GPIO2 was left untagged rather than guessed. Noted in
  board.json pinNotes/chipGpios for a future pass if a schematic surfaces.

Part B (ADC reference voltage):
- CHANGED defaultRefVolts from the chip-level default "1.0" to "3.3". Vendor datasheet
  explicitly states the A0 pin's input voltage range as "0~3.3V" (not the bare ESP8266
  chip's native 0-1.0V), which is only physically possible via an onboard resistor-divider
  network — the same pattern already confirmed by schematic on ESPDuino/ESPino/D1 R1 in this
  session. No schematic with exact resistor values could be located for WiFiduino (vendor
  site down throughout this research), so the vendor's own stated round-number full-scale
  figure (3.3V) was used directly rather than a resistor-computed exact ratio.

FILES MODIFIED
- variants/esp8266/esp8266/wifiduino/board.json — created (did not previously exist), as a
  full copy of the esp8266 chip-level default board.json with only GPIO0's capabilities,
  GPIO2's pinNote/chipGpios note (documentation only, no capability change), and
  adc.defaultRefVolts changed, plus a NOTE comment block citing all sources above.

SUMMARY
TAGGED wifiduino GPIO0 as a vendor-datasheet-confirmed user button (KEY_FLASH); left GPIO2's
onboard LED (LED_BUILTIN) untagged because no source documents its active-high/active-low
polarity; changed ADC defaultRefVolts from 1.0V to 3.3V based on the vendor datasheet's
explicit "A0 input voltage range 0~3.3V" statement, matching the divider pattern already
confirmed on other shield-form-factor ESP8266 boards this session.

3. ALIAS-COLLISION CHECK (GPIO0/GPIO2 vs SDA/SCL/SS/MOSI/MISO/SCK)

Checked both by direct file inspection and by re-reading the actual parser logic in
pfodWeb_src/build_boards.js (buildEsp32Board(), which esp8266-family boards route through):
the parser reads PIN_WIRE_SDA/PIN_WIRE_SCL and the SDA/SCL/SS/MOSI/MISO/SCK `static const`
aliases from the fully #include-resolved source (pins_arduino.h + common.h are concatenated
before parsing — resolveIncludes() in build_boards.js), then unconditionally appends
i2c_sda/i2c_scl/spi_ss/spi_mosi/spi_miso/spi_sck capabilities onto whichever chipGpios entry
matches those GPIO numbers, REGARDLESS of any chipGpios override already set (this is the
exact mechanism that silently contaminated GPIO4/GPIO5 on the espino board this session,
per boardsDetails/esp8266/esp8266/espino/notes.txt).

For wifiduino: PIN_WIRE_SDA=4, PIN_WIRE_SCL=5 (this board's own pins_arduino.h); SS=15,
MOSI=13, MISO=12, SCK=14 (inherited from ../generic/common.h). None of these six values is 0
or 2. GPIO0 (button) and GPIO2 (LED) are NOT aliased as SDA/SCL/SS/MOSI/MISO/SCK anywhere in
this board's resolved source. CONFIRMED CLEAN — no collision, no contamination, NO CHANGE
needed to board.json.
