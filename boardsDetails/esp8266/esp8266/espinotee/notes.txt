Board: variants/esp8266/esp8266/espinotee  ("ThaiEasyElec's ESPino", PlatformIO id "espinotee")
Research date: 2026-07-11

IMPORTANT DISAMBIGUATION
-------------------------
There are TWO different ESP8266 boards both commonly called "ESPino":
  1. "ESPino (ESP-12 Module)" — product of espino.io — a SIBLING variant
     directory in this repo. NOT part of this task. Not touched.
  2. "ThaiEasyElec's ESPino" (ETEE052) — the board covered by THIS task,
     variant directory "espinotee", product of thaieasyelec.com (Thailand).
Search engines and AI summarizers repeatedly blended descriptions of these
two boards together (see below) because they share the word "ESPino". Care
was taken throughout this research to keep them separate and to trust only
text that could be pinned to the correct product.

pins_arduino.h for espinotee (current, unedited) defines only:
  PIN_WIRE_SDA=4, PIN_WIRE_SCL=5, LED_BUILTIN=16
No BUTTON_BUILTIN or RGB LED aliases are present (unlike the sibling
"espino" directory, which has LED_BUILTIN_R/G/B and BUTTON_BUILTIN — that
is the OTHER, unrelated "ESPino (ESP-12 Module)" board and was left
untouched per instructions).
Per task rules, LED_BUILTIN=16 is NOT by itself sufficient evidence of an
onboard LED, and cannot be used to infer active-high/low polarity — real
vendor schematic/doc confirmation was required and sought below.

CONSIDERED BUT NOT TAGGED / CHANGED, AND WHY
----------------------------------------------
- GPIO16 (LED_BUILTIN alias): Considered tagging ["digital_output",
  "led_high"] or "led_low" based on the pins_arduino.h alias. NOT done —
  no reachable vendor schematic confirms an LED is actually wired to
  GPIO16 on this specific board, nor its polarity, and the one
  authoritative source that does distinguish this board from the
  lookalike "ESPino (ESP-12 Module)" pointedly does NOT claim an onboard
  LED for it. Per task rules ("NEVER infer purely from pins_arduino.h
  alias names"), left untagged.
- GPIO0 (commonly a FLASH/BOOT button on ESP8266 dev boards generically):
  Considered tagging ["digital_input","button"]. NOT done — no
  ThaiEasyElec-specific documentation was reachable to confirm a physical
  button is populated on this board (unlike, e.g., NodeMCU where vendor
  photos/schematics are reachable and confirm it). pins_arduino.h for
  espinotee doesn't even alias a BUTTON_BUILTIN, unlike the sibling
  "espino" board which does.
  Note this is moot for tagging purposes anyway per the task's TX/RX
  guard: GPIO0 is not TX/RX so it wasn't excluded on those grounds, it
  simply lacks evidence.
- RGB LED (LED_BUILTIN_R/G/B style): Considered because the search-engine
  summarizer kept asserting "RGB Led and two buttons" for "ESPino" —
  traced this claim to the sibling "ESPino (ESP-12 Module)" board (see
  URL 3) and explicitly did NOT apply it here.
- No board.json existed for espinotee before this task, and none was
  created, since no GPIO capability change was warranted (task instructs
  to create one as a copy of the chip default ONLY when a change is being
  made; with no confirmed change, the chip-level board.json default for
  esp8266 continues to apply unmodified).
- ADC divider: considered because several sibling boards (NodeMCU, D1
  Mini) are noted in the chip-level board.json as having documented
  dividers extending A0 to 3.3V. No schematic for espinotee was reachable
  to confirm or deny a similar divider on this board, so defaultRefVolts
  was left at the chip default of 1.0V (native ESP8266 ADC range).

TX/RX GUARD CHECK
------------------
GPIO1 (TX0) / GPIO3 (RX0) are the hard-reserved serial pins per the
esp8266 chip-level board.json chipGpios notes. No tagging was attempted on
GPIO16 or GPIO0 in any case (see above), so this guard was not triggered,
but confirmed neither candidate pin coincides with TX/RX.

SUMMARY
-------
NO CHANGE made to espinotee: no board.json created/edited. Button/LED
capability could not be confirmed via reachable, real ThaiEasyElec
documentation (the vendor's download server is unreachable/dead and the
product page renders no usable content); the one authoritative source
that does distinguish this board from the similarly-named "ESPino
(ESP-12 Module)" does not claim an onboard LED or button for it. ADC
reference voltage left at the chip-level default of 1.0V for the same
reason — no divider schematic could be confirmed.

[2026-07-12] DEDICATED-HARDWARE PIN-EXCLUSION AUDIT (separate pass)
===============================================================
Scope of this pass: NOT a re-run of the button/LED/ADC tagging above.
This is the dedicated-hardware EXCLUDE-vs-KEEP sweep per
project_board_variant_pin_audit_playbook.md — i.e. checking whether any
pin should be removed from the Designer's general-purpose GPIO pool
because it is wired to an onboard radio/SD/display/actuator etc.

1. FULL pins_arduino.h RE-READ
   variants/esp8266/esp8266/espinotee/pins_arduino.h defines only:
     PIN_WIRE_SDA=4, PIN_WIRE_SCL=5 (SDA/SCL aliases), LED_BUILTIN=16
   and #includes ../generic/common.h, which unconditionally defines the
   standard ESP8266 SPI aliases SS=15, MOSI=13, MISO=12, SCK=14 (used by
   every esp8266 board that doesn't override them) plus A0=17,
   NUM_ANALOG_INPUTS=1, isFlashInterfacePin() etc. No board-specific
   TX/RX aliases are declared (UART0 Serial uses the chip's fixed
   TX=GPIO1/RX=GPIO3, not a pins_arduino.h alias). This matches the
   "zero non-boilerplate declarations" finding that put this board in
   the audit queue — confirmed still true on re-read.

2. SELF-CONSISTENCY CHECK (requested this wave after the espectro
   sibling board was found to have a copy-paste SDA/SCL/SPI conflict)
   Checked SDA/SCL/SS/MOSI/MISO/SCK/TX/RX for internal contradiction:
   SDA=4, SCL=5 (espinotee's own file) vs SS=15/MOSI=13/MISO=12/SCK=14
   (inherited from common.h) — all five pin numbers are distinct, no
   pin is claimed by two different aliases. No TX/RX override exists in
   this file to conflict with anything. CONCLUSION: self-consistent,
   no espectro-style conflict here.

3. FRESH RESEARCH ATTEMPT (Wayback Machine — NOT tried in the earlier
   pass, which only tried live URLs and got ECONNREFUSED / dead JS
   storefront)
   Used the archive.org "available" API and CDX API (curl directly,
   since the WebFetch tool refuses web.archive.org URLs) and got a real
   hit:
   - https://web.archive.org/web/20180224101857/http://www.thaieasyelec.com/en/products-en/development-boards-en/espino-wifi-development-board-detail.html
     A full archived (Thai-language) product page for THIS exact board
     (ETEE052/espinotee), unlike the live fetch which only returned
     banner/header text. Relevant excerpts (translated):
       "GPIO pins: 0 1 2 3 4 5 12 13 14 15 16" (11 GPIOs, matches the
         standard non-flash ESP8266 GPIO set exactly — no extra
         dedicated pin claimed).
       "Has a RESET switch for resetting the board."
       "Has an LED connected to GPIO for user-controlled status
         display, connected to GPIO16."
       "Has an LED showing status while transmitting/receiving data
         via the serial port / programming the board" (a separate
         TX/RX activity LED on the CP2104 USB-serial bridge chip, not
         a chip GPIO).
   - CDX search (`web.archive.org/cdx/search/cdx?url=downloads.thaieasyelec.com/ETEE052/...`)
     found a genuine archived copy of the user manual PDF (two
     snapshots, 2023-01-30 and 2024-06-22, ~1-1.4MB, mimetype

     `.../web/20240622190540if_/https://downloads.thaieasyelec.com/ETEE052/ETEE052_ESPino_User_Manual_TH_v1_0_20160204.pdf`

       "UART: 1(Tx) 3(Rx) 15(Tx2) 13(Rx2)" — describes GPIO15/13 as

       "SPI (Software): 15(SS) 14(SCK) 13(MOSI) 12(MISO)" — exactly

4. DEDICATED-HARDWARE EXCLUDE-vs-KEEP DECISION (this pass's actual
   scope)
   Nothing found rises to EXCLUDE tier. There is no radio module, SD
   card, display, motor/stepper/heater driver, or analog mux anywhere
   in this board's documentation — the vendor's own manual describes
   SPI and I2C as generic "software" (bit-banged) buses on the standard
   pins, not dedicated to any onboard chip, and lists exactly the
   standard 11-pin ESP8266 GPIO set with no extra dedicated signal.
   The GPIO16 LED and the GPIO0-adjacent PROGRAM button (both newly
   confirmed above) both fall under the playbook's explicit KEEP
   category ("simple onboard buttons, single LEDs... even if shared
   with boot pin — note it, don't exclude"), so even with this
   stronger evidence than the earlier pass had, no chipGpios exclusion
   is warranted. RESET and the "Auto Program" DTR/RTS circuit are
   USB-serial/EN-pin level, not GPIO-space at all, so they were never
   candidates for exclusion.
   CONCLUSION: NO CHANGE to chipGpios / no board.json created. This
   confirms (rather than merely repeats) the earlier pass's NO CHANGE
   outcome, now with real vendor pin data instead of an unreachable
   site.

       GPIO16 for user-controlled status display, and the board-photo

       (active-high vs active-low) is still NOT stated anywhere in the
       manual text extracted here — only pin number and purpose.
     - GPIO0 button: the manual confirms a "PROGRAM" button exists on
       the board (component callout 5) and, by ESP8266 universal
       convention plus this board's GPIO0 being in both the general
       GPIO list and the breakout header, is presumably wired to
       GPIO0/boot-strap, though the manual text extracted here does not
       spell out "GPIO0" next to "PROGRAM" explicitly in so many words
       (it's the photo caption + adjacent GPIO0 pin in the header list
       that make this the obvious inference — a full page-by-page
       manual/schematic image read, not attempted here, would confirm
       it outright).
     - RESET button: confirmed to exist, but it resets the chip via the
       EN pin, not a GPIO, so it is out of scope for GPIO capability
       tagging either way.
   This pass deliberately did NOT apply any button_builtin/led tags or
