Board file shared by TWO boards.txt entries: nodemcu = "NodeMCU 0.9 (ESP-12 Module)"

Date: 2026-07-11

URLS CONSULTED AND FINDINGS
----------------------------

1. https://lowvoltage.github.io/2017/07/09/Onboard-LEDs-NodeMCU-Got-Two
   Blog post specifically about NodeMCU's two onboard LEDs. States:
   - GPIO16 (silkscreen "D0"): LED mounted on the NodeMCU devkit PCB itself.
   - GPIO2 (silkscreen "D4"): LED mounted on the ESP-12/ESP-12E module itself
     (also flashes during programming since GPIO2 = U1TXD, secondary UART TX).
   - Both are 0603 blue LEDs through 470-ohm current-limit resistors, wired
     "inverted" (pin LOW = LED on) i.e. ACTIVE-LOW.
   - Matches this board's own pins_arduino.h: `#define LED_BUILTIN 2` and
     `#define LED_BUILTIN_AUX 16`.
   Used as primary source for the LED GPIO/polarity tagging.

2. GPIO-12/12E module comparison (multiple pinout reference sites, e.g.
   randomnerdtutorials.com ESP8266 pinout reference, kofa.mmto.arizona.edu
   ESP-12 module page): confirms GPIO16 exists and is wired identically on
   both the ESP-12 (used on NodeMCU 0.9/Amica) and ESP-12E (used on NodeMCU
   1.0/Lolin) modules — the ESP-12E's extra pins (vs ESP-12) are additional
   bottom-row flash-chip pins, not GPIO16. This supports tagging GPIO16's
   LED as applicable to BOTH board revisions, since the D0 LED is a devkit
   PCB feature (not gated by which module variant is fitted).

3. https://www.etechnophiles.com/nodemcu-esp8266-pinout-specs-board-layout/
   and https://esp8266.com/viewtopic.php?f=32&t=15869 (forum thread on using
   the flash button as input) — both describe the onboard FLASH/BOOT button
   wired to GPIO0, pulled LOW when pressed, standard bootloader-entry button,
   described identically for the NodeMCU Amica (0.9) and Lolin (1.0)
   revisions. No schematic PDF with resistor designators could be located
   (NodeMCU devkit schematics on GitHub — see below — are Altium binary PDFs
   with no extractable text/component layer), but the GPIO0-button wiring is
   corroborated by multiple independent community sources plus the standard
   ESP8266 "GPIO0 LOW at boot = program mode" behavior that a FLASH button
   is universally wired to exploit. Tagged ["digital_input","button"] with
   no active-high/low variant, matching this repo's convention for other
   boards where the exact pull-up value/polarity note isn't schematic-cited
   (e.g. espino, ESPDuino, itead).

4. https://github.com/nodemcu/nodemcu-devkit-v1.0
   (NODEMCU_DEVKIT_V1.0.PDF, Altium-generated schematic) — official v1.0
   schematic repo. The PDF is binary/image-based (compressed Altium output);
   WebFetch could not extract readable text/component designators from it.
   Referenced only to confirm the board is officially open-source and that
   no textual disagreement with the community sources above was found in
   the repo's issue tracker (issue #32 is an unrelated request for a V3
   schematic, no technical content).

5. https://esp8266.com/viewtopic.php?f=8&t=16799 (forum thread, "analog
   input affected by internal voltage divider?") — contributor "btidey"
   (well-known, technically detailed poster in this community) gives the
   NodeMCU A0 divider as 220k (in series from A0) + 100k (to GND), with
   formula V(ADC) = 100000/(320000+RT) x 3.3 for external source resistance
   RT. Setting RT=0 (direct connection) gives V(ADC) = 0.3125 x 3.3 =
   1.031V at the chip's raw ADC pin for a full 3.3V input at A0 — i.e.
   slightly OVER the chip's 1.0V native max, meaning the true safe/rated
   full-scale at A0 is not 3.3V.

6. https://www.electronicwings.com/nodemcu/nodemcu-adc-with-arduino-ide
   Independent source, explicitly states: "voltage divider network of
   resistors (100Kohm & 220Kohm)... R2 is 100kOhm and R1 equals 220kOhm.
   The Vout port is connected to the ADC pin of the ESP-12 module and Vin
   is connected to the A0 pin on the NodeMCU board." Confirms same 220k/100k
   values as source 5, independently.
   Exact math: chip-native ADC max (1.0V) x (220k+100k)/100k = 3.2V
   full-scale at A0. This is the SAME 220k/100k divider (and same 3.2V
   result) already found and corrected on this repo's D1 Mini, D1 R1, and
   ESPino board.json files — NodeMCU is NOT a different ratio, it is the
   same widespread reference-design divider, informally rounded to "3.3V"
   in both of the above sources and in this file's pre-existing (unverified)
   note.

WHAT WAS CONSIDERED BUT NOT CHANGED
------------------------------------
- No 0.9-vs-1.0 discrepancy was found for the GPIO0 button, GPIO2 LED,
  GPIO16 LED, or the A0 ADC divider — all sources describe the "NodeMCU Dev
  Kit" family (both Amica/0.9 and Lolin/1.0) identically for these
  features, so all tags were applied to this single shared board.json
  without a per-revision split or notes-only flag.
- GPIO1/GPIO3 (hardware UART0 TX0/RX0) were left untouched — not this
  board's button/LED pins, and build_boards.js hard-reserves them anyway.
- RST is the chip's physical reset pin (wired to a separate RESET button on
  the devkit), not a GPIO — not tagged, consistent with every other board
  in this repo.
- Could not obtain a text-readable schematic PDF (official NodeMCU
  Altium-exported PDFs are image/binary only) to cite exact resistor
  designators (e.g. "R1"/"R2") for the FLASH button's pull-up value or the
  LEDs' exact 470-ohm figure beyond the secondary source (lowvoltage.github.io)
  — two independent, mutually-corroborating community sources were used
  instead, consistent with this repo's precedent on boards like
  espresso_lite_v1/v2 where "no schematic PDF could be located" but two
  independent official/community sources were accepted.

SUMMARY
-------
TAGGED: GPIO0 -> +button (FLASH/BOOT, active-low). GPIO2 -> +led_low
(module LED, D4/LED_BUILTIN). GPIO16 -> +led_low (devkit PCB LED,
D0/LED_BUILTIN_AUX). All three confirmed to apply identically to both
NodeMCU 0.9 (ESP-12) and NodeMCU 1.0 (ESP-12E).
ADC: pre-existing "3.3" value was NOT correct — CORRECTED to "3.2",
confirmed via independent resistor-math sources (220k/100k divider,
same as this repo's D1 Mini/D1 R1/ESPino boards) — NodeMCU uses the same
divider ratio, not a different one.

CRITICAL CHECK: alias-collision between GPIO0/GPIO2/GPIO16 (already
tagged button/led_low/led_low) and SDA/SCL/SS/MOSI/MISO/SCK
--------------------------------------------------------------
Explicitly checked whether the three already-tagged pins are ALSO
aliased to an I2C/SPI bus role anywhere in this file or the shared
common.h it includes, which would mean the earlier button/LED tagging
is silently sitting on top of a bus pin (a real contamination risk this
audit pass exists to catch):
  - SDA = 4, SCL = 5           (this file, PIN_WIRE_SDA/SCL)
  - SS = 15, MOSI = 13, MISO = 12, SCK = 14   (generic/common.h)
  - Tagged pins: GPIO0 (button), GPIO2 (led_low), GPIO16 (led_low)
None of {4, 5, 15, 13, 12, 14} intersects {0, 2, 16}. CONFIRMED: no
collision, no contamination. The button/LED tags are clean and do not
overlap any I2C/SPI bus pin.

KEEP vs EXCLUDE POLICY CHECK ON REMAINING GPIOs
------------------------------------------------
board.json's chipGpios already lists GPIO4, GPIO5 (I2C SDA/SCL, D2/D1)
and GPIO12, GPIO13, GPIO14, GPIO15 (SPI MISO/MOSI/SCK/SS, D6/D7/D5/D8)
with their plain digital_input/digital_output/pwm_output capability
sets, no bus-specific restriction. Per playbook section 3 ("KEEP
available: General-purpose I2C/SPI buses without a documented exclusive
onboard consumer") this is correct as-is — NodeMCU's I2C/SPI header
pins are general-purpose breakout pins with no onboard device
permanently wired to them (unlike, e.g., a board with an onboard SD
card on the SPI bus), so no exclusion applies. No change needed.
