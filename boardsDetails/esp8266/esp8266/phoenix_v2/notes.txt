- ADC divider (defaultRefVolts): no schematic or vendor text of any kind was found describing

- No board.json was created for phoenix_v2 since no GPIO-specific facts were confirmed to
  override the chip-level default — the board correctly continues to inherit
  variants/esp8266/esp8266/board.json unchanged.
- phoenix_v1 was not touched or inferred from (per task instructions and because its
  LED_BUILTIN alias, GPIO16, differs from v2's GPIO2, confirming the two boards are distinct
  hardware that cannot be assumed identical).

Version-branch ambiguity check
-------------------------------
Read both C:\ai\aicode\pfodWeb\variants\esp8266\esp8266\phoenix_v2\pins_arduino.h and its
sibling C:\ai\aicode\pfodWeb\variants\esp8266\esp8266\phoenix_v1\pins_arduino.h in full,

Result: phoenix_v1 and phoenix_v2 are two SEPARATE, self-contained files, each with its own
unambiguous, unconditional declarations — the same pattern as espresso_lite_v1/v2, NOT the
espectro single-shared-file-with-#if-branches bug pattern. Neither file contains any
#if/#ifdef/#else/#endif conditional structure at all (only the standard
#ifndef Pins_Arduino_h include-guard), and no declaration name is repeated within either file.
phoenix_v2 declares PHOENIX_VERSION 2 once, unconditionally, matching its own filename/version
— no fix needed, no ambiguity exists. build_boards.js's comment-blind/ifdef-blind parser
resolves phoenix_v2 correctly because there is only one candidate value for every name in this
file, not two competing branches.

Dedicated-hardware / KEEP-vs-EXCLUDE sweep
--------------------------------------------
Full content of phoenix_v2/pins_arduino.h (already quoted above) declares only:
  - PIN_WIRE_SDA=4, PIN_WIRE_SCL=5 (static const SDA/SCL) — general-purpose I2C bus, no
    onboard-only consumer documented anywhere (see URLs from the earlier pass, all still the
    same dead-end). Per playbook policy this is KEEP (general I2C without confirmed exclusive
    onboard consumer).
  - LED_BUILTIN=2 — already covered chip-wide by the base ESP8266 board.json's own GPIO2
    pinNote/capabilities; not a board-specific dedicated-hardware pin.
  - #include "../generic/common.h", which adds PIN_SPI_SS=15, PIN_SPI_MOSI=13,
    PIN_SPI_MISO=12, PIN_SPI_SCK=14 (static const SS/MOSI/MISO/SCK) — standard ESP8266 HSPI
    pins, shared by every ESP8266 board via the same common.h, general-purpose SPI bus with no
    board-specific dedicated peripheral documented. KEEP.
No motor/servo/heater/stepper/radio-module/SD-card/display/analog-mux pins or any other
non-standard #define/static const declarations are present in this file at all — it is one of
the smallest/plainest pins_arduino.h in the ESP8266 family, with nothing beyond the
LED/SDA/SCL/SPI convention the playbook's discovery grep already filters out as ordinary.

SDA/SCL/SS/MOSI/MISO/SCK/TX/RX alias-contamination check
------------------------------------------------------------
Checked whether any single GPIO carries more than one of these role aliases (which would
signal silent capability contamination, e.g. a pin double-booked as both LED and bus signal):
  GPIO4 -> SDA only
  GPIO5 -> SCL only
  GPIO12 -> MISO only
  GPIO13 -> MOSI only
  GPIO14 -> SCK only
  GPIO15 -> SS only
  GPIO2  -> LED_BUILTIN only (not aliased to any bus role)
No GPIO is aliased under more than one of these role names in this file or in
generic/common.h. TX/RX are not aliased at all in this file (hardware UART0 TX/RX, GPIO1/3,
are forced generically at the chip-level board.json rather than via a literal alias, matching
every other ESP8266 board — see that file's own comment). No contamination found.
