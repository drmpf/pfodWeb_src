**Why:** The Designer's pin picker must not offer GPIOs that are actually wired to onboard peripherals (SD card, radio module, display, motor driver, analog mux, etc.) — a user picking one of those for their own sketch would silently break the board's built-in hardware or get misleading capability info (e.g. an "analog_input" label on a pin that's really a digital mux-select line).

**How to apply:** Run this whenever a new `<chipFamily>_board_variants/` raw source tree is dropped in for import, or when re-auditing an existing family the user flags as incomplete.

## 1. Establish ground truth board count

- Find the raw vendor source (`<family>_board_variants/boards.txt` + `variants/<name>/pins_arduino.h`).
- `grep -oE '^\S+\.build\.variant=.*' boards.txt` → sorted unique list of real variant ids referenced by boards.txt.
- `find variants/<family> -mindepth 1 -maxdepth 1 -type d` (per chip bucket) → what's actually in our tree.
- `comm -23`/`comm -13` diff the two lists. Anything in boards.txt but missing from our tree is a genuine gap (add it). Anything in our tree but not boards.txt-referenced is likely an orphan (menu-only sub-variant like ESP8266's `arduino_spi`/`arduino_uart`, or a truly unreferenced dir like RP2040's `vicharak_shrike-lite`-adjacent `wifio`) — confirm via `grep -B5 build.variant=<name> boards.txt` before excluding.
- Also check for missing *shared* files, not just missing boards — a chip bucket's `generic/pins_arduino.h` or `common.h` copy can be silently absent, causing every board that `#include`s it to build with 0 pins (found this exact bug in the RP2040 pass for 3 boards + a generic entry).

## 1b. Check the copied `boards.txt` isn't stale, and watch for menu-only sub-variants

Before diffing (step 1), confirm the copy under `variants/<family>/boards.txt` is actually current against the raw vendor source — `diff <(wc -l both files)` or just `cp` the source over it and re-run the build, diffing the set of unique output board ids before/after. Found a real case (ESP32) where the copy was ~1700 lines / several months stale, causing **multiple genuinely-different boards to silently collide onto the same output JSON** (last one processed during the build wins, the others vanish from the Designer with no error) — because `_lookupAllBoardsTxt()` requires an exact `<id>.build.variant=<dirname>` line to exist in whatever copy of `boards.txt` is present.

Separately, some variant directories are **only reachable via a `.menu.<MenuName>.<option>.build.variant=` line**, not a top-level `<id>.build.variant=` line, because they're a "Revision"/sub-model menu option under a different parent board id in the real Arduino IDE (e.g. one physical board line offering a menu to pick which radio chip variant is installed, each with a different pinout). `_lookupAllBoardsTxt()` correctly skips these (no matching `<id>.name=` line for the full dotted menu-option "id"), which means they ALSO fall back to the chip-level default name and collide with each other. Find these via: after fixing the stale-copy issue, re-run the build and grep for any output path written more than once — each remaining collision is one of these menu-only boards. Fix: give each its own per-board `board.json` (full copy of the chip-level file, override only `boardName`/`displayName` using the menu option's own human-readable label from boards.txt), exactly like the empty-`chipGpios`-vs-full-copy precedent in section 4.

## 1d. Hit-count sweeps miss sibling boards in the same product line

Ranking boards by non-standard-declaration hit count (section 2) is a good prioritization heuristic but **not a complete discovery method** — a board sharing a product line with an already-flagged board can have far fewer hits (shorter file, less-verbose vendor comments) yet still have the same class of dedicated hardware. Found this with Waveshare's "ESP32-S3-Touch-LCD-*"/"Touch-AMOLED-*" line: 6 of 18 variants surfaced via the hit-count sweep, but rebuilding after fixing those revealed 12 more sibling boards sharing the exact same chip and naming prefix that the sweep had ranked too low to appear in a manually-chosen top-N cutoff. **After fixing any board, grep the vendor source tree for other directories sharing its name prefix/product line and check each one explicitly** — don't rely solely on the hit-count ranking to decide what's "done."

**Don't over-extrapolate structural similarity across siblings, either.** Within that same Waveshare line, several boards share byte-identical boilerplate (`OUTPUT_IO2/3/17/18`, `A0-A6`, `D0-D16`, `T1-T7` blocks) *only because the vendor copy-pasted the template* — the actual dedicated-pin assignment differs per physical display model. One variant with zero documentation comments was initially assumed to match its heavily-documented siblings (same GPIO2/3/17/18 "must be the display" reasoning) purely from the boilerplate match; a fuller sibling file later showed those exact GPIOs are *not* dedicated on its (different) physical display. Verify against a documented sibling before trusting boilerplate-similarity inference, and prefer reverting to "no change" over a guess when the evidence conflicts — an incorrectly-excluded pin has no user recourse, while an incorrectly-kept one is just a pin the user must avoid if it misbehaves.

## 2. Exhaustive non-standard-`#define`/`static const` sweep

This is the main discovery tool — it surfaces every board with *any* declaration outside the ordinary LED/Serial/SPI/Wire/pin-count convention, which is where dedicated-hardware pins hide:

```bash
find <family>_board_variants/variants -name "pins_arduino.h" -exec grep -H "^#define\|^static const" {} \; \
  | grep -viE "PIN_LED|PIN_SERIAL[0-9]*_(TX|RX|CTS|RTS)|PIN_SPI[0-9]*_(MISO|MOSI|SCK|SS)|PIN_WIRE[0-9]*_(SDA|SCL)|PINS_COUNT|NUM_DIGITAL_PINS|NUM_ANALOG_INPUTS|NUM_ANALOG_OUTPUTS|ADC_RESOLUTION|SERIAL_HOWMANY|SPI_HOWMANY|WIRE_HOWMANY|LED_BUILTIN|WIRE_INTERFACES_COUNT|static const uint8_t (SS|MOSI|MISO|SCK|SDA|SCL|TX|RX|A[0-9]|D[0-9]+) ="
```

Group the hits by board, then triage every unique macro/alias name found (motor/servo/heater/stepper pins, radio module CS/RST/DIO lines, SD-card SPI buses, display CS/DC/RST, NFC/LoRa/cellular-modem control lines, analog-mux select/channel pins, USB-host D+/D-, PSRAM CS, DVI connectors, etc.).

## 3. Keep vs. exclude policy

**EXCLUDE** (dedicated to onboard hardware, not general-purpose):
- Communication bus wired exclusively to a specific onboard/always-attached chip: radio module SPI/UART (LoRa, sub-GHz, NFC, cellular modem, add-on WiFi/BLE co-processor), SD-card SPI, Ethernet SPI, display SPI/parallel bus, DVI/HDMI connector, dedicated I2S audio codec bus, PSRAM chip-select.
- Fixed hardware actuator requiring specific timing/safety: stepper DIR/STEP/EN/STOP, heater PWM, servo PWM header, motor-driver output, fan PWM.
- Internal-only control/power lines: reset/enable lines for an onboard chip (OLED_RST, ESP-coprocessor RESET/MODE, NeoPixel power-gate confirmed internal via vendor docs), power-enable lines whose default state a downstream peripheral depends on (e.g. "must stay HIGH to power the Grove port ring").
- Pins that are electrically real but *don't behave as advertised* — e.g. an analog mux's channel-select/address lines aliased as "A0-A7" when they're actually digital lines feeding one shared real ADC pin, or "analog" aliases that are really channel indices into an external ADC chip (PCF8591 etc.), not real per-GPIO analog capability.

**KEEP available** (safe/expected to expose):
- Simple onboard buttons, single LEDs/NeoPixels (even if "shared with boot pin" — note it, don't exclude).
- Analog sensor readings that match pfodWeb's own "data display" use case: thermistors, current/voltage/battery monitors, SD-card-detect switches, ultrasonic trigger/echo pins.
- **Relay outputs** (Sonoff-style boards): a relay is a simple digital on/off actuator, and controlling it from pfodWeb *is* the point of using such a board with pfodWeb — do not exclude, unlike a stepper/heater.
- General-purpose I2C/SPI buses without a documented exclusive onboard consumer, even if only one device happens to be attached in the reference design (I2C especially is inherently multi-drop).

When genuinely unsure which bucket a pin falls into (obscure/community board, ambiguous vendor comment), spawn a research Agent (or WebSearch directly) to check the vendor's own product page/schematic/datasheet before deciding — this caught real, non-obvious findings twice (Amperka WiFi Slot's 74HC4052 analog mux, confirmed via a datasheet in the vendor's own wiki media folder; "InventOne"'s external PCF8591 ADC, confirmed via secondary sources since the vendor site itself was thin). Don't guess on these — a wrong guess either wrongly hides a legitimate pin or wrongly exposes something that breaks onboard hardware.

## 4. How to actually apply an exclusion — check the parser mechanics FIRST

Before editing anything, check whether the chip family's chip-level `board.json` has a non-empty `chipGpios` map (ESP32/ESP8266-style: chip has a small number of pins so a uniform "full GPIO map" default makes sense) or an empty one (RP2040-style: third-party boards too heterogeneous, each board's own file is authoritative). This determines the fix mechanism:

- **Empty chip-level `chipGpios` (RP2040 pattern):** a board only needs its own `pins_arduino.h` edited to stop declaring the dedicated pin(s) as `static const uint8_t D<n>/A<n>/<alias> = ...`. If the board `#include`s a *shared* `common.h`/`generic/pins_arduino.h` that unconditionally declares the pin (e.g. `SS`/`MOSI`/`MISO`/`SCK`/`SDA`/`SCL` aliasing whatever `PIN_SPI0_SS` etc. equals, regardless of value), **you cannot fix it by editing the shared file** without affecting every other board that legitimately uses it — convert *that one board* to a fully self-contained `pins_arduino.h` (stop including the shared file, write out every kept `D<n>`/`A<n>` directly) and simply omit the excluded ones.
- **Non-empty chip-level `chipGpios` (ESP8266-style — every board gets the full chip default merged in regardless of its own file):** create a per-board `board.json` (full copy of the chip-level one, per the existing precedent — there is no partial-merge mechanism) with the excluded GPIO(s) removed from its `chipGpios` map. **But this alone is not sufficient** if the board's own `pins_arduino.h` (or a shared `common.h` it includes) *also* declares a `static const` alias for that GPIO — `allGpios` is the union of chip-level `chipGpios` keys AND every alias found via `pins_arduino.h`, so the board's own file must also stop declaring the excluded pin (same "convert to self-contained, bypass the shared common.h" fix as above).

In both cases: after excluding a GPIO, re-run the build and grep the generated JSON for that GPIO number to confirm it's actually gone — don't assume the board.json edit alone worked.

**Both halves are independently necessary — doing only one is the single most common mistake in this whole process.** Concretely hit this twice in the ESP32 audit alone: removing a board's own `MOTOR_L_IN1`-style alias from `pins_arduino.h` left the underlying GPIO still exposed (unlabeled, as plain `"GPIO17"`) via the chip-level `chipGpios` default — the motor-driver pin was still pickable, just without the misleading name. Always do the `board.json` override too, even when the board's own file looks fully cleaned up.

Also: **any `static const uint8_t NAME = value;` declaration adds that GPIO to the pin list, regardless of what `NAME` is** — not just `D<n>`/`A<n>`/`SS`/`MOSI`/etc. Blanket-identity blocks like `A0=1, A1=2, ..., A19=20` and `T1=1, T2=2, ..., T14=14` (seen on several ESP32-S3 badge/game boards) will silently re-leak every GPIO in their range even after you've excluded those same GPIOs elsewhere in the file and in `board.json` — you must also trim the specific `A<n>`/`T<n>` entries whose value falls in the excluded range, not just the semantically-named aliases.

## 1c. Check individual board files for staleness too, not just `boards.txt`

Before trusting a board's content, `diff` its `pins_arduino.h` (and any board-specific `common.h`) against the raw vendor source — a handful of individual files can be stale copies of an older core revision even when the great majority of the tree is current (found 2 out of ~380 in the ESP32 pass: one had no functionally-relevant diff and was left alone, the other was missing an entire camera-pin/LoRa-CS section present upstream, which would have led to auditing the wrong/incomplete pin set). Quick check across a whole family:
```bash
for d in $(find variants/<family> -mindepth 2 -maxdepth 2 -type d -exec basename {} \; | sort -u); do
  src="<family>_board_variants/variants/$d/pins_arduino.h"
  ours=$(find variants/<family> -path "*/$d/pins_arduino.h" | head -1)
  [ -f "$src" ] && [ -f "$ours" ] && diff -q "$src" "$ours" > /dev/null 2>&1 || echo "DIFFERENT: $d"
done
```
Expect most/all "DIFFERENT" results to be fixes already in progress (compare against what you've actually edited this session) — anything unexplained is a genuine stale-file finding worth refreshing from source before auditing that board.

## 4b. Two more real cases from later ESP32 batches

- **A dedicated peripheral's pins can be declared ONLY as `#define`, never as `static const uint8_t`** — in that case the board's own `pins_arduino.h` needs NO edit at all, since the regex-based parser only ever picks up `static const` declarations. The fix is `board.json`-only (remove those GPIOs from the chip-level `chipGpios` copy). Found on `rakwireless_rak3112`: its onboard SX1262 LoRa radio's SCK/MISO/MOSI/CS/reset/DIO1/BUSY lines are all `#define LORA_* n` macros, never aliased via `static const` — so despite looking "unfixed," the file was already safe from a *leak via its own declarations*; the only real gap was the chip-level default silently still offering those GPIOs generically.
- **When independent research conflicts with the board's own file, trust the file and apply only the corroborated parts.** On `elecrow_crowpanel_7`, vendor-wiki research for the RGB LCD panel and I2S audio pins directly contradicted this file's own `TX`/`RX`/`TXD2`/`RXD2` declarations (same GPIO numbers, different claimed function) — likely the research applies to a different CrowPanel revision/SKU. Applied only the two findings that exactly matched the file's own declared values (touch I2C, SD SPI), left the rest of the board unchanged, and noted the conflict in a comment rather than picking a side.

## 4c. Watch for mismatched results when reading multiple files in parallel

When several `Read` calls are issued together (e.g. one call per board in a batch), double-check that the analysis for board X actually uses board X's returned content, not a neighboring result that got mentally attached to the wrong filename while writing up the batch. Concretely happened once in the ESP32 audit: a batch of 5 parallel reads (`m5stack_core2`, `dpu_esp32`, `deneyapmini`, `cytron_maker_feather_aiot_s3`, `bpi-bit`) — the TFT+touch+SD-dedicated content actually belonging to `dpu_esp32` was analyzed and initially edited under the `deneyapmini` filename instead, only caught because the `Edit` tool's exact-string-match failed (the real `deneyapmini` file had totally different content) and prompted a re-read. If an `Edit` string-match fails right after a multi-file parallel read, don't just "fix the string" — re-verify which file's content you actually intended to change.

## 5. Known parser gotchas (regex-only, NO real C preprocessor)

`build_boards.js`'s ESP32/ESP8266/RP2040 shared parser (`parseEsp32Consts`/`buildEsp32Board`) is a **plain regex scan of the fully `#include`-flattened text** — it does not evaluate `#if`/`#ifdef`/`#ifndef`/`#else`/`#endif`, and does not strip `//`/`/* */` comments before scanning. This causes real, non-obvious bugs — always check for these after editing:

1. **Both branches of `#ifdef X ... #else ... #endif` get scanned regardless of whether `X` is actually defined.** For a `static const` alias-form assignment (`D4 = __PIN_D4;`) vs a numeric fallback (`D4 = (4u);`) in the two branches, the numeric direct-assignment ALWAYS wins over the pending alias (checked via `if (name in out) continue` — direct numeric assignments win unconditionally, regardless of scan order or which branch is "real"). Net effect: **board-specific `__PIN_Dn`/`__PIN_An` override mechanisms silently do nothing** — the board gets the generic identity-mapped value instead of its real override. Found this affecting `adafruit_feather`'s D4/D5/D6 in the RP2040 audit. Fix: don't rely on the override macro pattern — write the resolved value directly as a literal in a self-contained file.
2. **Commented-out reference lines still match.** A vendor comment like `//static const uint8_t SS = PIN_SPI0_SS;   // SPI Slave SS not used, for reference only` is still parsed as a real declaration, because the regex has no comment-awareness. Delete these lines entirely — commenting them out is not enough. (Found affecting 3 Pimoroni RP2040 boards.)
3. **`#if 0 ... #endif`-disabled blocks still get scanned too** — this can accidentally be *helpful* (Pimoroni Plasma boards' "disabled" D0-D10 block turned out to hold the board's real, correct pin mapping) but verify case-by-case; don't assume disabled-looking code is inert.
4. **Vendor "not pinned out" sentinel values leak as phantom pins.** Boards commonly use `31u` (or occasionally `99u`) as a "this signal doesn't exist on this board" marker for `PIN_SPIx_SS` etc. Since `SS = PIN_SPI0_SS;`-style aliases get declared unconditionally, `SS` ends up literally aliasing "GPIO31", which doesn't physically exist — the Designer then shows a bogus "SS (GPIO31)" pin. Scan generated JSON for any pin label matching `GPIO(\d+)` with a number at/above the chip's real max GPIO (30 for RP2040/RP2350A, 40+ only for genuinely-confirmed 48-pin RP2350B, 18 for ESP8266) and treat every hit as a bug **unless** the board is a confirmed-genuine larger-package chip variant (e.g. RP2350B `PICO_RP2350A 0`) with real hardware in that range.
5. **Multi-level `#define` chains don't resolve.** The alias-resolution fallback (`pending` → `out` or → `defines`) only follows ONE hop of indirection: `X = Y;` resolves if `Y` is a peer `static const` OR a directly-numeric `#define`. If `Y` is itself a `#define` pointing at a THIRD macro (`#define PIN_WIRE_SDA PIN_SDA` where `PIN_SDA` is `#define PIN_SDA 2`), resolution silently fails and the pin **disappears from the list entirely** rather than erroring. Found this dropping `SDA`/`SCL` entirely on an ESP8266 board (`agruminolemonv4`). Fix: write the final numeric value directly, skip the macro chain.

After ANY fix, do a full-family re-scan for `GPIO(\d+)` labels at/above the chip's real max, and spot-check the specific boards you touched by dumping their generated JSON pin list, not just relying on "no errors" from the build.

## 6. Verification checklist before calling a family done

1. `node build_boards.js` (from `pfodWeb_src/`) — must complete with zero errors/warnings, and the printed per-board summary lines are worth skimming for `(0 pins...)` (missing-shared-file bug) or unexpectedly tiny/huge counts.
2. Zero-pin scan: `require()` every generated board JSON, flag any with `pins.length === 0` (except deliberately pin-less `ccode`/`unlistedBoard`-style stubs).
3. Phantom/out-of-range GPIO scan (regex the `(GPIO\d+)` label text, flag anything ≥ the chip's real max) — cross-check every hit against whether that specific board is a confirmed larger-package variant.
4. Pin-count sanity pass: dump every board's pin count, and for any surprisingly low or high count relative to its known form factor, dump its actual pin list and either confirm the reasoning is already documented in that board's file/comments, or flag it to the user rather than silently guessing (this surfaced a servo-driver board showing only 3 pins because its 18 servo channels were `#define`-only and never picked up, and a USB-stick keychain board showing all 30 silicon GPIOs despite having no header at all — both were user decisions, not something to silently "fix").
5. Full rebuild-and-stage cycle: `node build_boards.js` → `node build-bundle.js` → `bash build-pfodWeb.sh` (or the `.bat` equivalents) from the repo root — the last step is easy to forget and was repeatedly missed in earlier sessions; it's what actually updates the deployed `pfodWeb/pfodWeb.html`, not the transient root-level copy `build-bundle.js` produces.

## 7. Three additional checks for boards audited from here on (NOT yet applied retroactively)

Added mid-way through the ESP32 pass once the mechanism existed — apply these to every board audited **going forward**. The ~155+ ESP32 boards already completed before this point have NOT been retrofitted; that's a separate, later pass, not part of the current batch cadence.

**a) Button/LED hardware-identity capability tags.** `designer/boards/shared/PinType.js` has capability constants for this: `BUTTON`, `LED_HIGH`, `LED_LOW`, `LED_NEOPIXEL`, `LED_R_HIGH`/`LED_R_LOW`, `LED_G_HIGH`/`LED_G_LOW`, `LED_B_HIGH`/`LED_B_LOW` (`'button'`, `'led_high'`, `'led_low'`, `'led_neopixel'`, `'led_r_high'`, etc. as raw strings). `build_boards.js`'s `CAP_ORDER` already includes them so they pass through a `chipGpios` entry's `capabilities` array into the generated pin JSON — **nothing in the parser enforces the exclusion rule below; it's a hand-authoring discipline, applied every time a chipGpios entry is written for a confirmed button/LED pin.** These tags are never inferred from `pins_arduino.h` alias names (names like `BUTTON_A`, `LED_BUILTIN`, `RGB_LED` are not reliable enough — confirmed by the user) — only added after checking the vendor's actual product page/schematic:
   - A confirmed onboard button's GPIO gets `capabilities: ["digital_input", "button"]` **and nothing else** — write exactly this restricted list, don't carry over the pin's normal full chip-level capability set (`digital_output`/`pwm_output`/`analog_input`/`analog_input_serial`/`dac_output` must never appear alongside `button`). A button pin wired to a fixed pull resistor + switch has no externally-accessible circuit to usefully drive or read as analog, so those capabilities must not even appear in the board.json entry in the first place, not be filtered out later.
   - A confirmed onboard single-colour LED gets `capabilities: ["digital_output", "led_high"]` or `"led_low"` (plus `pwm_output` only if the pin actually supports PWM) **and nothing else** — `digital_input`/`analog_input`/`analog_input_serial`/`dac_output` must never appear alongside an `led_*` tag.
   - A confirmed onboard addressable (WS2812/NeoPixel-style) RGB LED's data pin gets `capabilities: ["digital_output", "led_neopixel"]` (plus `pwm_output` if applicable), same exclusions as above — note many boards declare this via the `LED_BUILTIN = SOC_GPIO_PIN_COUNT + N` "virtual pin" convention, which `build_boards.js` does **not** currently resolve to a real GPIO at all (the underlying real GPIO `N` needs to be found separately, e.g. from a vendor comment naming the real pin, before it can be tagged).
   - A confirmed discrete 3-pin RGB LED (separate GPIOs for each colour, e.g. `LED_RED`/`LED_GREEN`/`LED_BLUE`) gets each channel's GPIO tagged individually with the same exclusion rule: `capabilities: ["digital_output", "led_r_high"]` (or `led_r_low`) on the red pin, `led_g_high`/`led_g_low` on the green pin, `led_b_high`/`led_b_low` on the blue pin — again only after confirming polarity, not guessed from the file.
   - **Before tagging, check the confirmed GPIO isn't also the board's declared `TX`/`RX` pin.** `build_boards.js` hard-reserves whatever GPIO equals the board's `TX`/`RX` alias: it unconditionally overwrites that pin's `capabilities` to `['serial_tx']`/`['serial_rx']` only, discarding ANY `chipGpios` tag (button/LED or otherwise) — but the **label override still applies** (computed earlier in the pipeline), so a tagged-but-overridden pin ends up silently mislabeled as e.g. "GPIO1 (Led Green active low)" while its real, functional capability is just `serial_tx`. Found this on `deneyapkart` (GPIO1/GPIO3 are simultaneously TX/RX and the vendor-documented discrete RGB LED pins) — the fix was to NOT tag them (revert to the plain default capability set) since the tag can never actually take effect while those pins are committed to serial duty (pfodWeb's serial connection always needs them). Quick check before tagging: grep the board's `TX =`/`RX =` values in `pins_arduino.h` and skip tagging (or tag-then-verify-in-generated-output) if they match your candidate GPIO.

**b) Board-level ADC reference-voltage accuracy.** Every board.json already has `"adc": { "bits": ..., "max": ..., "defaultRefVolts": "..." }` — verify this is *correct for the specific board*, not just copied from the chip-level default. This matters most for **ESP8266**: the bare chip's native ADC input range is ~1.0V (some datasheets say 1.1V), but many dev boards (NodeMCU, Wemos D1 Mini, etc.) add an onboard resistor-divider network ahead of the ADC pin specifically to extend the usable range to the board's ~3.3V supply rail. A board with that divider needs `defaultRefVolts: "3.3"`; a bare/raw module without it needs the chip's native ~"1.0". Check the specific board's schematic/product page — don't assume either value by default.

**c) These three checks require real per-board research (schematic/product page/vendor docs), matching the "don't guess without evidence" policy already established** — never populate button/LED tags or correct the ADC voltage from `pins_arduino.h` alone.

### New parser-gotcha class found repeatedly this pass: confirmed hardware-identity pin also carries a spurious bus-role alias

This is a **different** bug from section 5's existing gotchas — it doesn't involve `#ifdef`/comments at all. A GPIO gets a real, evidence-based `button`/`led_*` tag in `chipGpios`, but that same GPIO *also* happens to be the board's default `SDA`/`SCL`/`SS`/`MOSI`/`MISO`/`SCK` alias (usually inherited boilerplate from a shared `common.h` include, or a generic vendor-template default nobody customized for the board's real hardware). `build_boards.js`'s capability-assembly logic (`if (g === sda) caps.push('i2c_sda')` etc., around line 698 at time of writing) runs **unconditionally on every pin, regardless of a `chipGpios` override** — so the confirmed `["digital_input","button"]` list silently gets an extra `spi_ss`/`i2c_scl`/etc. capability appended.

**Important scope correction (checked 2026-07-12 via a dedicated code-search agent, after initially overstating this in a user-facing summary)**: this does NOT affect the generated *label* — that's computed separately (`_hwIdentityLabel(chipEntry.capabilities)`, using only the raw `chipGpios` config, before the bus-capability appends run), so a contaminated pin still correctly displays as e.g. `"GPIO13 (Led active low)"`. It also does NOT currently affect any Designer *behavior* — `designer/boards/shared/PinCapabilities.js`'s `.supports()` method is the sole consumer of capability data anywhere in the Designer (`state.js`, `editMenuItemPin.js`, `editChart.js`), and it never checks for `i2c_sda`/`i2c_scl`/`spi_ss`/`spi_mosi`/`spi_miso`/`spi_sck`/`serial_rx`/`serial_tx` — those eight strings are validated-on-load (`BoardLoader.js`'s `_validateCapability`, a schema check only) but otherwise inert/decorative today. So the bug was real (corrupted stored metadata) but had **zero live user-facing impact** at the time it was found — it only becomes consequential if/when SPI or I2C pin-picking is ever built on top of this data. Worth fixing regardless (stored data should be accurate), but don't describe it in the past tense as having misled users — it hadn't, yet.

**Detection method**: after tagging a pin, grep the board's own `pins_arduino.h` (and any included `common.h`) for the confirmed GPIO number appearing as the value of `SDA`/`SCL`/`SS`/`MOSI`/`MISO`/`SCK`. A **network-wide detection script** (run against the fully-generated JSON, not the source files) is the reliable final check:
```js
const fs = require("fs");
const dirs = fs.readdirSync("designer/boards").filter(d => d.startsWith("esp32_") || d.startsWith("esp8266_"));
for (const dir of dirs) {
  const files = fs.readdirSync("designer/boards/"+dir).filter(f=>f.endsWith(".json"));
  const d = JSON.parse(fs.readFileSync("designer/boards/"+dir+"/"+files[0], "utf8"));
  for (const p of d.pins||[]) {
    const caps = p.capabilities||[];
    const tagged = caps.some(c=>c==="button"||c.startsWith("led_"));
    const busCap = caps.some(c=>["i2c_sda","i2c_scl","spi_ss","spi_mosi","spi_miso","spi_sck"].includes(c));
    if (tagged && busCap) console.log(dir, p.label, JSON.stringify(caps));
  }
}
```
Run this after **every** wave's checkpoint build, not just spot-checks — it catches what individual subagents miss (many were only told to check the specific alias types their own board's flagged declarations suggested, not the full SDA/SCL/SS/MOSI/MISO/SCK set).

**Fix mechanism** (three variants depending on the source):
1. **Direct declaration in the board's own file**: delete the specific colliding line (e.g. just `SS = 42;`) outright.
2. **Inherited via a shared `common.h` include**: convert the file to self-contained — stop including `common.h`, reproduce every *non-colliding* alias directly, and simply omit the colliding one(s). (Precedent: `itead`, `wifinfo`, `espectro`, `xinabox`, `pandabyte_xc6` all needed this.)
3. **A plain `= -1;` override does NOT work if another real declaration of the same name exists elsewhere in the flattened source** (e.g. via an include) — `-1` fails the parser's numeric regex entirely (no leading-minus support), so the override line is silently invisible and the *other* declaration resolves unopposed. Confirmed this the hard way on `espectro`: writing `SS = -1;` after `#include "../generic/common.h"` had zero effect, because `common.h`'s own `SS = PIN_SPI_SS;` alias still resolved via the two-pass `pending`/`defines` mechanism regardless. Use fix #2 (self-contained conversion) whenever an include is involved; `-1` only works when the colliding declaration exists *nowhere else* in the whole flattened source (e.g. a board's own single un-included `SDA = 8;` line with no shared-file fallback).

**A second, related sub-bug: writing the literal old declaration text into the deletion's explanatory comment.** Found on `esp32c3/esp32c3` and `axiometa_genesis_one` mid-pass: an agent correctly deleted a colliding alias line, but then wrote a NOTE comment quoting the exact original `static const uint8_t SDA = 8;` text for documentation purposes — since the parser is comment-blind, that quoted text matched the regex again and silently reintroduced the exact bug the deletion was meant to fix. **Rule enforced in every subagent prompt from this point on**: never write the literal `static const uint8_t NAME = value;` shape anywhere in an explanatory comment, whether describing a fresh deletion or an old one — describe the change in plain English only. This also generalizes to "don't even comment-out the old line as a disabled reference" (section 5 already covered this for the commented-out-code case; the quoted-in-prose case was the new wrinkle).

## 15. Arduino AVR family: new chipGpios/pinNotes mechanism + full audit, 26 boards — COMPLETE (2026-07-14)

Unlike ESP32/ESP8266/RP2040 (all routed through the shared `buildEsp32Board()` parser), AVR boards (`variants/arduino/avr/`, 10 source directories) go through a completely separate `buildAvrBoard()` function that derives every pin's capabilities mechanically from `pins_arduino.h` (`NUM_DIGITAL_PINS`, the analog-offset macro, the `digitalPinHasPWM` predicate, and the board's own `PIN_SPI_*`/`PIN_WIRE_*` numbers) with **no per-pin override mechanism at all** — `chipGpios` was a required schema field on every AVR board.json but was always `{}` and completely unused by the AVR code path. This meant button/LED tagging and dedicated-hardware exclusion — the whole point of this playbook — were structurally impossible for AVR before this session, even though several AVR boards (Circuit Playground Classic, the Arduino Robot kit, Esplora) are exactly the kind of sensor-rich board this audit exists for.

**Code change (`pfodWeb_src/build_boards.js`)**: extended `buildAvrBoard()` to consult `cfg.chipGpios`/`cfg.pinNotes`, keyed by **digital pin number as a string** (never "GPIO" — AVR pins are named `D<n>`/`A<n>` and labels must stay that way, e.g. `"D13 (Led active high)"` not `"GPIO13 (...)"`). A `chipGpios` entry's `capabilities` array **completely replaces** the auto-derived list for that pin — deliberately skipping the SPI/I2C bus-role auto-append entirely when an override is present, to avoid ever reproducing the "confirmed identity tag contaminated with a spurious bus-role tag" bug class from section 12 (a mistake the ESP32/RP2040 parsers still carry as a known, accepted quirk — the AVR mechanism was written fresh with the fix already built in, since there was no existing behavior to preserve). `CAP_ORDER`/`HW_IDENTITY_LABEL`/`_hwIdentityLabel` were hoisted from inside `buildEsp32Board()` to module scope so both parsers share one definition. Verified as a true no-op for all 26 pre-existing AVR board outputs (byte-identical diff) before any audit findings were applied — the schema/field set didn't change, only previously-inert fields became load-bearing.

### A second real gap found alongside the missing mechanism: `boards.txt` sub-variants sharing a directory despite genuinely different hardware or voltage

AVR's `boards.txt` maps many distinct real products onto just 10 source directories via `<id>.build.variant=<dirname>` (e.g. `esplora.build.variant=leonardo`) — the same "menu-only sub-variant" pattern documented in section 1b, but here it wasn't a menu, it was flatly wrong: several of these grouped products have genuinely different onboard hardware or a different supply voltage, meaning one shared `board.json` cannot correctly describe all of them. Six new variant directories were carved out this session (each a one-line `#include "../<parent>/pins_arduino.h"` plus its own distinct `board.json`, with the specific `boards.txt` line repointed):

- **`lilypad`, `lilypadusb`, `fio`** — split off `standard`/`leonardo`/`eightanaloginputs` respectively purely for **ADC reference voltage**: all three are genuine 3.3V/8MHz products (official Arduino/SparkFun documentation confirmed) incorrectly inheriting their 5V/16MHz siblings' `defaultRefVolts: "5.0"`. `"pro"` (Arduino Pro/Pro Mini) was deliberately left un-split — its own `boards.txt` entry has a real user-facing IDE menu choosing between 3.3V/8MHz and 5V/16MHz variants, so no single fixed voltage is correct for it either way; flagged in `standard/board.json`'s comments rather than guessed.
- **`unowifi`** (Arduino UNO WiFi Rev1) — split off `standard` for its onboard ESP8266 co-processor, bridged via an **SC16IS750 UART-to-I2C IO-expander on the shared A4/A5 bus**, not a dedicated pin. Correctly kept A4/A5 available (documented via `pinNotes`, not excluded) since I2C is inherently multi-drop and the expander only occupies one fixed address — matches the established "general-purpose I2C bus, even with one onboard device attached" KEEP policy from section 3.
- **`esplora`** (Arduino Esplora) — split off `leonardo`. The entire joystick/4-button/slider/light/temperature/microphone/TinkerKit-input cluster reads through **one shared analog mux pin (A4)** with a 4-bit address selector (A0-A3) — there is no discrete per-button GPIO anywhere on this board, so correctly **no `button` tag was applied to any of it** (excluded instead, since a multiplexed analog reading doesn't fit this vocabulary's simple digital-button model). - **`leonardoeth`** (Arduino Leonardo ETH) — split off `leonardo` for its onboard W5500 Ethernet controller (D10 CS) and microSD slot (D4 CS), `connections` gained `tcp`. Caught a real ATmega32U4-specific gotcha: D4/D10 are **dual-numbered** as A6/A10 on this chip (same physical pins, different alias-driven index), so both the `D<n>` and the `A<n>` index for each pin had to be excluded — excluding only the `D<n>` key would have left the identical physical pin fully exposed under its `A<n>` entry.
- **`megaADK`** (Arduino Mega ADK) — split off `mega` for its onboard MAX3421E USB host controller. Only the RST line (D7) lands on a numbered Arduino digital pin per official docs; the chip's SS/INT/GPX lines land on ATmega2560 port pins with no Arduino digital-pin number at all (not present in `mega/pins_arduino.h`'s pin tables), so they're already inaccessible via `digitalWrite()`/`digitalRead()` and correctly need no `chipGpios` entry.

Verified via `node build_boards.js` (0 errors, `avr_pro5v`/`avr_pro3v3` both correct, `avr_pro` confirmed gone after the manual cleanup) → network-wide contamination + zero-pin scans (600 total boards now, same single pre-existing exception, 0 new issues) → `node build-bundle.js` → `bash build-pfodWeb.sh`, deployed.

### Remaining work flagged for a future session

None currently outstanding for the AVR family — every board.json in `variants/arduino/avr/` now has a confirmed, researched `chipGpios` state (even if `{}`/NO CHANGE) and a matching `boardsDetails/.../notes.txt`.

## 16. ESP32-family `boardsDetails/.../notes.txt` documentation backfill — 123 boards (2026-07-14)

A `boardsDetails/` vs `variants/` coverage scan (walking every `pins_arduino.h` and checking for a matching `notes.txt`) found **123 ESP32-family boards** (spanning `esp32`, `esp32c2`, `esp32c3`, `esp32c6`, `esp32p4`, `esp32s2`, `esp32s3` chip buckets) with real, confirmed `chipGpios` findings already baked into their `board.json` (14-43 entries each, complete with inline `note` fields citing sources) but **no companion `boardsDetails/.../notes.txt` research-trail file** — the documentation requirement from section 10 was never honored for this large a slice of the family, likely because much of this work predates that convention or was done directly rather than via the notes.txt-writing subagent pattern. Same scan also flagged 2 AVR directories (`eightanaloginputs`, `micro`) and 2 intentional zero-pin stubs (`Ccode`, `UnlistedBoard`) as "missing" — confirmed these are NOT real gaps: the AVR pair already has their findings documented in their ancestor's notes.txt (`standard`/`leonardo`), and the stubs have nothing to document.

**This was a pure documentation backfill, not new research** — every one of the 123 boards' `board.json` already contained the sources/reasoning inline in `//` comments and per-pin `note` fields; the task was purely to extract and reformat that into the standalone `notes.txt` format. Ran as 10 parallel background subagents (10-15 boards each), each instructed to distinguish two cases per board:
- **Board has its own dedicated `board.json`**: write a proper per-board notes.txt from its existing inline comments (sources, per-pin reasoning, summary).
- **Board has no `board.json` of its own** (relies on `build_boards.js`'s ancestor-fallback to a shared chip-level default, e.g. `variants/esp32/esp32/board.json`): write an honest notes.txt stating this board uses the plain chip-level default with no board-specific findings, naming its sibling boards on the same fallback — never invent board-specific findings for these.

**Result: a genuinely high fraction of "missing notes.txt" boards turned out to have no board-specific board.json at all** — roughly 25-30 of the 123 are chip-level-default fallback boards (concentrated in the plain `esp32` chip bucket: `doitESP32devkitV1`, `esp32` itself, `esp32-sbc-fabgl`, `esp320`, `esp32vn-iot-uno`, `firebeetle32`, `frog32`, `hornbill32minima`, `lolin32`, `lolin32-lite`, `mhetesp32devkit`, `mhetesp32minikit`, `pocket_32`, `quantum`, `ttgo-t7-v13-mini32`, `ttgo-t7-v14-mini32`, `xinabox`, plus `esp32c2`/`esp32c3`/`esp32c6`'s `wifiduinov2`, `dfrobot_beetle_esp32c6`, `sparkfun_esp32c6_qwiic_pocket`, and `esp32s3`'s `um_omgs3`) — meaning this whole segment of the family was already covered by the chip-level default's own findings, just never had a per-board pointer file confirming that explicitly.

## 17. Weak-source re-verification pass — 42 boards, real findings uncovered (2026-07-14)

A follow-up scan (`grep`-based, then refined twice to eliminate false positives from bare-domain citations like `arduino.cc` without an `https://` prefix, and from files using non-standard section headers like "URLS CONSULTED" instead of "Sources consulted:") found **42 boards** (out of 566 total `notes.txt` files) whose research trail cited **only** the repo's own `board.json`/`pins_arduino.h` — no external vendor documentation, schematic, datasheet, or forum was ever independently checked. Most of these were populated by the section-16 documentation-only backfill, which by design never did fresh research. The user asked for genuine re-verification, not just better citations.

Ran as 8 parallel background subagents (5-6 boards each), each instructed to independently research the real physical board via WebSearch/WebFetch and either confirm existing `chipGpios` findings (adding real citations) or correct them if they didn't hold up — explicitly told this was real verification work, not more reformatting.

**Result: this was NOT busywork — 8 of the 42 boards had genuine, previously-undetected errors, now fixed:**
- **`ch_denky`**: missing exclusion — GPIO25 is dedicated onboard RGB LED hardware on both board revisions, was left with generic capabilities.
- **`twatch` (LILYGO T-Watch)**: missing exclusions — GPIO5/12/18/19/27 (the dedicated ST7789 TFT display bus) were never excluded by any prior pass, because the vendor's `pins_arduino.h` declares them only as `#define`s, never `static const` — invisible to the alias parser. Confirmed via LilyGO's own docs and added.
- **`adafruit_feather_esp32s2`**: missing button tag — GPIO0 is a real, application-usable onboard BOOT button per Adafruit's own tutorial, previously untagged.
- **`adafruit_feather_esp32s2_reversetft`**: missing button tags — 3 physical pushbuttons (D0/D1/D2 on GPIO0/1/2) explicitly documented on Adafruit's pinouts page, completely missed by the prior pass.
- **`adafruit_feather_esp32s2_tft`**: missing button tag — same GPIO0 BOOT button pattern as the other Feather S2 variants.
- **`adafruit_funhouse_esp32s2`**: two corrections — GPIO37 was wrongly lumped into a "TFT SPI bus" exclusion but is actually `LED_BUILTIN` (the display's unused MISO line repurposed as a status LED), confirmed active-high and re-tagged; GPIO14/15 were left as plain GPIO but are the dedicated onboard 4-pixel DotStar driver pins, now excluded.
- **`adafruit_magtag29_esp32s2`**: missing LED tag — GPIO13 is `LED_BUILTIN` (a red LED separate from the NeoPixel strip), confirmed via Adafruit's own pinouts page, previously missed entirely.
- **`Edgebox-ESP-100`**: missing button tag (GPIO0, vendor wiki confirms a physical Reset button) plus 3 wrongly-excluded pins (GPIO35/36/37) — these had silently inherited a chip-level "reserved for octal PSRAM" assumption that doesn't apply to this specific board, which actually wires them out to real industrial output terminals (DO3/DO4/DO5) per the vendor's own wiki.
- **`waveshare_esp32s3_touch_lcd_128`**: 2 wrongly-excluded pins (GPIO4/5) — previously assumed exclusively dedicated to the IMU/touch interrupt, but Waveshare's own wiki shows they're also broken out on an external header for user peripherals (shared, not dedicated — restored to available).
- **`XIAO_ESP32S3_Plus`**: the most significant single correction — 6 GPIOs (10-13, 38-40) had been wrongly excluded as camera/mic-bus pins, copied from the sibling "Sense" variant's findings. Seeed's own product page confirms the "Plus" variant has **no onboard camera or microphone at all** — confirmed via the official upstream `arduino-esp32` pins_arduino.h for this exact variant (declares these as ordinary D-numbered user pins) and restored.
- **`xteink_x4`**: a genuine new confirmed finding, not previously tagged — GPIO3 (single power button) now has real two-source corroboration and was tagged `button` for the first time.

All other 32 boards had their existing findings independently confirmed against real vendor sources (Adafruit, Espressif upstream `pins_arduino.h`, official GitHub repos, vendor wikis, forum corroboration) with citations added — no further correction needed. Two boards (`Aventen_S3_Sync`, `franzininho_wifi_esp32s2`) surfaced additional uncorroborated leads (extra undocumented pins/LEDs) that were explicitly **not** acted on per the "never guess" policy — flagged in their `notes.txt` for a possible future pass instead.

**Verification**: full checkpoint re-run after all 8 batches — `node build_boards.js` (0 errors, 600 boards) → contamination scan (same single pre-existing exception, 0 new issues) → zero-pin scan (0, excluding the 2 intentional stubs) → `node build-bundle.js` → `bash build-pfodWeb.sh`, deployed.

**Lesson for any future automated "coverage scan" of this kind**: a naive regex/keyword scan for "has this file been sourced" produces a high false-positive rate — bare domain citations without `https://`, and non-standard section headers, both need explicit handling before trusting a scan's negative-result bucket. But once refined, this kind of periodic re-verification pass is genuinely worth running: roughly 1 in 5 of the flagged boards this pass had a real, previously-undetected data error, several stemming from the exact same root causes documented elsewhere in this playbook (parser blindness to `#define`-only declarations, findings copied from a sibling board without re-verifying that the sibling's hardware actually matches, chip-level default assumptions that don't hold for a specific board).
