Board: soldered_nula_rp2350 (chip bucket: rp2040w)
Audit date: 2026-07-13
Part of the ongoing RP2040/RP2350-family dedicated-hardware pin-exclusion +
button/LED/NeoPixel capability-tagging audit (ESP32/ESP8266 already fully
audited; RP2040/RP2350 family audit in progress, this board never previously
touched).

Starting state: no per-board board.json override existed at
variants/rp2040/rp2040w/soldered_nula_rp2350/ - the rp2040w chip bucket's
own board.json has chipGpios: {} for this whole bucket (deliberately - see
that file's own comments), so every GPIO with ANY alias in this board's own
pins_arduino.h defaulted to full digital_input/digital_output/pwm_output via
build_boards.js's buildEsp32Board(). This meant:
  - The onboard WiFi/BT radio's power-enable pin (WRL_ON, GPIO23) was fully
    exposed as a general-purpose digital output.
  - The onboard USER button (USER_BTN, GPIO27) was fully exposed as a
    general-purpose digital output, with no "button" identity.
  - The onboard microSD card's dedicated chip-select pin (PIN_SPI1_SS,
    GPIO33) was exposed as plain "D33" general-purpose digital I/O, with no
    indication it was SD-card-dedicated (no automatic bus-role tag applies
    to it either, since this board's generic SS/MOSI/MISO/SCK aliases
    resolve to the OTHER SPI bus, SPI0 at GPIO2-5, not SPI1).
  - The onboard WS2812 NeoPixel LED (PIN_NEOPIXEL, GPIO26) was declared only
    as a bare `#define`, which build_boards.js's alias parser does not
    recognise (only `static const uint8_t` declarations count as aliases) -
    it had NO alias at all and was therefore completely ABSENT from the
    generated pin list, with no way for a user to select it in the Designer.

- pfodWeb_src/build_boards.js (buildEsp32Board(), lines ~515-736 and
  parseEsp32Consts(), lines ~439-495) - re-read directly (not required as
  a module, per task instructions) to confirm two mechanics relevant to
  this board specifically:
  (a) parseEsp32Consts only recognises `static const uint8_t NAME = ...;`
      declarations as aliases - a bare `#define PIN_NEOPIXEL (26u)` does
      NOT create an alias, confirming GPIO26 was genuinely invisible to
      the pin generator before this audit, not merely mistagged.
  (b) The generic bus-role auto-tagging (`if (g === ss) caps.push('spi_ss')`
      etc.) keys off the single unindexed consts.SS/MOSI/MISO/SCK/SDA/SCL
      names, which this board's pins_arduino.h binds only to SPI0/Wire0
      (GPIO2-5, GPIO8-9) - confirming GPIO33 (SPI1's SS) gets NO automatic
      bus tag at all, so a chipGpios capabilities:[] override for it fully
      and cleanly excludes it from general I/O with no leftover spi_ss
      label to worry about (unlike the "bug class" flagged in this
      session's task brief, which does not apply to any of GPIO23/26/27/33
      here - confirmed by checking none of them equal 2/3/4/5/8/9).

       Designer's purposes (it is the actual file the Designer's generated
       Arduino sketches compile against) rather than the pico-sdk's
       bare-metal default scheme, which reads as unused/inapplicable
       boilerplate for this board's Arduino-core integration - no
       chipGpios override added for GPIO0-3.

Per-pin reasoning / decisions applied to
variants/rp2040/rp2040w/soldered_nula_rp2350/board.json:

- GPIO23 (WRL_ON): EXCLUDED, capabilities: []. High confidence. Confirmed
  WiFi/BT radio (RM2/CYW43439) power-enable control line via this board's
  own pins_arduino.h comment ("// WiFi power GPIO") plus the confirmed RM2
  radio (source 3). Driving this pin as plain digital I/O risks powering
  the radio off mid-session or fighting the CYW43 driver's own
  enable-sequencing at cyw43_arch_init() time - the same class of hazard
  already documented for CYW43/RM2 radio-control lines elsewhere in this
  chip bucket. No SS/MOSI/MISO/SCK/SDA/SCL alias collision (GPIO23 is not
  2/3/4/5/8/9), so no pins_arduino.h edit was needed.

- GPIO26 (PIN_NEOPIXEL, previously alias-less and therefore entirely
  absent from the generated pin list): ADDED, capabilities:
  ["digital_output","led_neopixel","pwm_output"]. High confidence -
  doubly confirmed by this board's own pins_arduino.h (NUM_NEOPIXEL=1) AND
  the independent, official pico-sdk board header
  (PICO_DEFAULT_WS2812_PIN 26) AND the vendor's consumer product listing
  ("WS2812 RGB LED"). digital_input omitted, matching this repo's
  established led_neopixel precedent (sparkfun_thingplusrp2350 GPIO14).

- GPIO27 (USER_BTN): RESTRICTED, capabilities: ["digital_input","button"]
  (digital_output/pwm_output dropped from the prior full default). High
  confidence - doubly confirmed by this board's own pins_arduino.h ("//
  User button") AND the official pico-sdk board header
  (SOLDERED_NULA_MAX_RP2350_USER_BTN 27) AND the vendor's product listing
  ("RESET, BOOTSEL, and USER buttons"). digital_output/pwm_output
  deliberately omitted - no source confirms safe output use, matching this
  repo's conservative user-button precedent (pimoroni_pico_plus_2w GPIO45).

- GPIO33 (PIN_SPI1_SS, "SD Card SPI" bus, "CS pin for SD card"): EXCLUDED,
  capabilities: []. High confidence - this board's own pins_arduino.h
  comment is unambiguous and directly on the pin's own #define, matching
  the exact confirmation standard already accepted for
  sparkfun_thingplusrp2350's GPIO9 (also "CS pin for SD card", also
  excluded in that precedent without needing a schematic net-label
  re-derivation). This board's generic SS alias resolves to SPI0 (GPIO5),
  not SPI1, so GPIO33 has no automatic spi_ss tag to worry about - the
  capabilities:[] override is the ENTIRE fix needed.

- GPIO30/31/32 (PIN_SPI1_MISO/MOSI/SCK, rest of the "SD Card SPI" bus):
  NO CHANGE, left at chip-derived general-purpose defaults. Medium
  confidence. GPIO30/31 are also aliased as this board's Wire1 SDA1/SCL1
  (an alternate, user-selectable I2C1 role), which is direct evidence they
  are genuinely broken out/shared rather than SD-internal-only wiring -
  matches this repo's existing "dual-purpose SPI bus left general-purpose"
  policy (sparkfun_thingplusrp2350's SPI0 SCK/MOSI/MISO). GPIO32 has no
  alternate documented alias, but also no source confirms it as
  SD-exclusive (unlike GPIO33's explicit CS comment) - left unchanged per
  the "only exclude on a direct dedicated-pin confirmation" bar this audit
  applies; flagged here as the single lowest-confidence NO-CHANGE call in
  this board's audit, should the vendor's promised hardware-repository
  documentation clarify this differently in future.

- GPIO4 (SD_ENABLE, "SD Card detect - Active Low"): NO CHANGE. Medium-high
  confidence. Vendor's own hardware-details page's JP3 entry ("Connects
  GPIO4 to the MicroSD card power enable line", default NC) confirms this
  connection is jumper-gated and not present by default - a
  board-specific-use, user-configurable signal, not fixed dedicated
  silicon. Matches the established GPIO13/RT9080-EN "jumper/board-specific
  power-enable pin, NO CHANGE" precedent from sparkfun_thingplusrp2350.

- GPIO5 (PIN_SPI0_SS): NO CHANGE (remains the general-purpose SPI0 SS pin,
  keeps its automatic "spi_ss" tag via the pre-existing SS-alias match).
  Medium confidence - possibly the target of JP2's "Enables MicroSD chip
  select line" (also default NC, i.e. not connected by default), which
  would make it an optional/legacy alternate SD wiring path rather than
  this board's primary (SPI1/GPIO33) SD chip-select. Either way, not
  connected by default, so left unchanged.

- GPIO6 (BATT_ALRT_N, "Low battery alert - Active Low"): NO CHANGE.
  Lower-medium confidence. Plausibly a status/alert signal from the
  onboard Li-Ion charger IC (vendor confirms "onboard charger included"),
  but no source specifically names the charger IC or confirms this pin is
  unsafe to drive as an output or permanently hardwired without a jumper -
  left general-purpose per this audit's "confirm via real documentation,
  do not guess a restriction" policy.

- GPIO7 (PERIPHERAL_POWER_ENABLE, "Power enable for peripherals - qwiic,
  sd, rgb. Default HIGH via HW jumper."): NO CHANGE. Medium-high
  confidence - this board's own pins_arduino.h comment already states it
  is jumper-configurable (consistent with JP4/JP5's territory), matching
  the same board-specific-use/NO-CHANGE precedent as GPIO4 above.

- GPIO12-19 (HDMI/DVI CLK/D0/D1/D2 N/P differential pairs): NO CHANGE
  NEEDED - already fully absent from this board's own pins_arduino.h
  alias list (confirmed by direct read - no D12-D19 anywhere), so already
  correctly excluded from the generated pin set by omission. Confirmed as
  dedicated DVI/HDMI lines via the official pico-sdk board header's
  SOLDERED_NULA_MAX_RP2350_HDMI_* defines (source 2). No chipGpios entry
  added or needed.

- GPIO24/25/28/29/36-39 (no alias anywhere, no dedicated function
  identified in any source consulted): NO CHANGE - already excluded from
  the generated pin set by omission; no evidence found that they are
  anything other than simply unbroken-out/unused on this board.

- GPIO0/1 (PIN_SERIAL1_TX/RX): NO CHANGE NEEDED - unlike several sibling
  boards in this chip bucket (sparkfun_thingplusrp2350, rpipico2w), this
  board's own pins_arduino.h already declares proper bare `TX`/`RX`
  aliases, so build_boards.js's serial-role auto-detection already fires
  correctly - no pre-existing gap to flag here.

- BOOTSEL/RESET: NO CHANGE (no "button" tag applied to either) - RESET is
  a hardware reset line, not a GPIO; BOOTSEL is read via the boot ROM, not
  a normal digitalRead()-capable GPIO on this family, matching this repo's
  universal convention of never tagging Pico-family BOOTSEL as a
  general-purpose "button".

No SDA/SCL/SS/MOSI/MISO/SCK bus-collision "bug class" (as described in this
session's task brief - a confirmed button/LED pin also aliased as a bus
role, causing build_boards.js to unconditionally auto-append an unwanted
bus capability) applies anywhere on this board: none of GPIO23 (WRL_ON),
GPIO26 (NeoPixel), GPIO27 (USER_BTN), or GPIO33 (SD CS) coincide with this
board's SS=5/MOSI=3/MISO=2/SCK=4/SDA=8/SCL=9 aliases. No pins_arduino.h
edits were made or needed.

Summary: created variants/rp2040/rp2040w/soldered_nula_rp2350/board.json as
a full copy of the rp2040w chip-level default with four chipGpios overrides
- GPIO23 (WiFi/BT radio power-enable) excluded, GPIO26 (onboard WS2812
NeoPixel, previously entirely invisible to the pin generator) tagged
led_neopixel, GPIO27 (onboard USER button) restricted to digital_input+
button, and GPIO33 (onboard microSD chip-select) excluded. GPIO4/5/6/7
(jumper-configurable SD-power/battery-alert/peripheral-power signals) and
GPIO30-32 (rest of the dedicated SD SPI1 bus, partly dual-purposed as
Wire1) were deliberately left at chip-derived general-purpose defaults
after review, matching this repo's existing conservative precedents for
similar board-specific-use and dual-purpose-bus pins. GPIO12-19 (DVI/HDMI)
and several other unaliased GPIOs were confirmed already correctly excluded
by omission via the official pico-sdk board header cross-check; no action
needed for them.
