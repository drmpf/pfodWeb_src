NEOPIXEL FINDING (no onboard NeoPixel on this board)
------------------------------------------------------------------------
This board's own pins_arduino.h defines NO "NEOPIXEL" macro anywhere (in
contrast to the RP2040-generation sibling
challenger_2040_wifi6_ble/pins_arduino.h, which does define one at
GPIO11). Two independent primary vendor pages (the datasheet page and the
separate product page) make no mention of any NeoPixel/addressable
RGB/WS2812 LED. The one source suggesting otherwise - a third-party news
article - explicitly flags its own claim as "(TBC)"/unconfirmed. Per this
audit's standing "confirm via real vendor documentation - never guess"
rule, the weight of evidence (2 primary sources + this board's own
firmware header, all in agreement) is treated as confirming this specific
board/firmware revision has NO onboard NeoPixel. No chipGpios entry was
added for a NeoPixel since none exists to tag.

BUTTON FINDING (no separate user pushbutton found, moderate confidence)
------------------------------------------------------------------------
Neither vendor page (datasheet or product) mentions any button at all -
this differs from the RP2040 sibling's datasheet, which explicitly named
"the button closest to the USB connector is the reset button, and there
is the boot button towards the rear end of the board" (RESET+BOOTSEL
only, no user GPIO button). This RP2350 board's own pages are simply
silent on the topic rather than affirmatively describing RESET+BOOTSEL-
only. No PIN_BUTTON-style alias or button-related comment appears in this
board's own pins_arduino.h either, which is consistent with (though not
independent proof of) there being no separate user-GPIO pushbutton. Given
every single other Challenger-family board audited this session confirms
RESET+BOOTSEL only, and RP2040/RP2350 chips always expose a BOOTSEL pad
sampled by the boot ROM (never a general-purpose sketch GPIO in Arduino
core terms) plus these boards conventionally carry a reset button, this
is treated as most likely RESET+BOOTSEL only, same as every sibling - but
flagged here as a slightly lower-confidence conclusion than the RP2040
sibling's, since this exact board's own documentation did not explicitly
itemize its buttons.

PER-PIN REASONING
------------------
GPIO4  (PIN_SERIAL2_TX / PIN_ESP_TX) - ESP32-C6-MINI-1 co-processor's
  dedicated UART (Serial2) TX line, confirmed by vendor datasheet ("Data
  output from RP2350 (ESP32-C6 RXD)"). Not aliased to any Dn/An header pin
  or SPI0/Wire0 bus constant in this board's pins_arduino.h. capabilities: [].

GPIO5  (PIN_SERIAL2_RX / PIN_ESP_RX) - ESP32-C6-MINI-1 UART RX line,
  confirmed by vendor datasheet ("Data input to RP2350 (ESP32-C6 TXD)").
  Same reasoning as GPIO4. capabilities: [].

GPIO8  (PIN_SPI1_MISO) - dedicated SPI1 (ESP32_SPI object) MISO line to
  the ESP32-C6-MINI-1 ("GPIO8: Serial data input (SDI)" per vendor
  datasheet - SDI from the ESP32-C6's own perspective as SPI peripheral).
  Not aliased to the generic MISO constant (PIN_SPI0_MISO=GPIO16, the
  separate header-routed user bus) - no bus-capability auto-append
  collision. capabilities: [].

GPIO9  (PIN_SPI1_SS / ESPHOST_CS) - dedicated SPI1 chip-select line to the
  ESP32-C6-MINI-1 ("GPIO9: Chip select (#CS)" per vendor datasheet). Not
  aliased to the generic SS constant (PIN_SPI0_SS=GPIO17). capabilities: [].

GPIO10 (PIN_SPI1_SCK) - dedicated SPI1 clock line to the ESP32-C6-MINI-1
  ("GPIO10: Serial clock (SCK)" per vendor datasheet). Not aliased to the
  generic SCK constant (PIN_SPI0_SCK=GPIO18). capabilities: [].

GPIO11 (PIN_SPI1_MOSI) - dedicated SPI1 MOSI line to the ESP32-C6-MINI-1
  ("GPIO11: Serial data output (SDO)" per vendor datasheet). Not aliased
  to the generic MOSI constant (PIN_SPI0_MOSI=GPIO19). capabilities: [].
  NOTE: on the RP2040-generation sibling, GPIO11 is the NEOPIXEL pin - on
  THIS board GPIO11 is an unrelated dedicated SPI1 line; the two boards'
  pin layouts do not correspond 1:1 and were independently verified rather
  than assumed to match.

GPIO14 (PIN_ESP32_MODE / PIN_ESP_MODE / ESPHOST_DATA_READY) - dual-purpose
  control line to the ESP32-C6-MINI-1: mode-select during the
  co-processor's own externally-driven reflash sequence, and the
  ESP-Hosted protocol's "data ready" signal during normal runtime
  operation. Confirmed by vendor datasheet ("Boot/mode pin (pulled low
  during reset enters flash mode; also DREADY when using ESP Hosted
  firmware)"), which directly explains and validates this board's own
  ESPHOST_DATA_READY=PIN_ESP_MODE #define as a genuine, vendor-intended
  dual-purpose pin rather than a mistake. Not general-purpose.
  capabilities: [].

GPIO15 (PIN_ESP32_RST / PIN_ESP_RST / ESPHOST_RESET) - active-low reset
  line to the ESP32-C6-MINI-1, driven by the RP2350 host. Confirmed
  active-low by vendor datasheet ("ESP32-C6 reset (active low)"). Not
  general-purpose. capabilities: [].

GPIO22 (PIN_ESP32_HS / ESPHOST_HANDSHAKE) - handshake signal for the
  ESP-Hosted SPI1 link, confirmed by vendor datasheet ("Handshake signal
  for ESP Hosted operation"). Not general-purpose. capabilities: [].

GPIO7  (PIN_LED / LED_BUILTIN / D13) - onboard user LED, vendor-documented
  as "connected to pin D13" ("On the other side of the USB connector
  there is a user programmable green LED. This LED is connected to pin
  D13 and can easily be controlled by the user program"), matching this
  board's own pins_arduino.h (PIN_LED=(7u), D13=(7u), LED_BUILTIN=PIN_LED).
  Tagged ["digital_output","pwm_output","led_high"] - active-high polarity
  inferred from the confirmed active-high sibling precedent
  (challenger_2040_wifi/board.json, challenger_2040_wifi6_ble/board.json
  GPIO10 - same vendor, identical recurring datasheet phrasing, same
  simple onboard-LED design repeated across the whole Challenger product
  line), NOT from a directly-quoted "Active level: High" statement for
  this exact model (a targeted re-fetch specifically searching for that
  phrase came back empty for this page - see SOURCES CONSULTED #5 above).
  digital_input dropped, pwm_output kept for brightness dimming.

No NEOPIXEL macro/pin exists on this board (see NEOPIXEL FINDING above) -
no chipGpios entry to add.

No onboard user pushbutton found beyond RESET/BOOTSEL (see BUTTON FINDING
above, moderate confidence) - no chipGpios entry to add.

WIFI CHIP-BUCKETING FLAG (per this audit's standing instruction)
------------------------------------------------------------------------
This board genuinely carries onboard WiFi6+BLE5 silicon (an
ESP32-C6-MINI-1 co-processor module, confirmed by the vendor datasheet),
yet lives in the plain "rp2350" chip bucket (variants/rp2040/rp2350/,
family "rp2040"), not "rp2040w" (variants/rp2040/rp2040w/, which grants
tcp/http/ble connections for boards using the native RP2040/RP2350 +
CYW43439 combo).

This is NOT a miscategorization to silently fix - it is architecturally
correct as-is, and was already explained by a pfodWeb NOTE present in this
board's pins_arduino.h BEFORE this audit began: the ESP32-C6-MINI-1 is
reached over a dedicated UART (GPIO4/5) plus a second SPI channel
(GPIO8-11, ESP-Hosted/ESP-AT protocol) plus 3 control GPIOs (14/15/22),
not the native cyw43 SPI-attached radio that variants/rp2040/tcp.ino,
http.ino, and ble.ino are written against. This board would need its own
dedicated "ESP hosted"/"ESP-AT"-protocol .ino templates before it could
genuinely offer tcp/http/ble connections through the Designer - a larger
feature-scope change, out of scope for this pin-tagging/exclusion audit
task. Flagging per the task's standing instruction to surface (not
silently move) any WiFi-bucketing question. No chip-bucket move was made.
Same reasoning already applied to the RP2040-generation sibling
challenger_2040_wifi6_ble in this same audit's earlier session.
