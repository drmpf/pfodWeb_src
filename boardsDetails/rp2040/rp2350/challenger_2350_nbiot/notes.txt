Board: iLabs "Challenger+ RP2350 NB-IoT" (chip bucket: rp2350)
Directory: variants/rp2040/rp2350/challenger_2350_nbiot/
Audit date: 2026-07-13

SUMMARY
-------
Confirmed the onboard STMicroelectronics ST87M01-1301 module is a
genuine LTE Cat NB2 (NB-IoT) cellular modem with integrated GNSS
(GPS L1 + Galileo) and Wi-Fi (802.11b scan-only) positioning - NOT the
"No Battery" false-friend found on the challenger_nb_2040_wifi sibling
earlier this session. The modem occupies GPIO4/5 (UART TX/RX) and
GPIO8/9/10/11 (INT/RSTN/WAKEUP/GNSS-bias-enable control lines); GPIO14
is a separate dedicated BConnect/SWD debug-connector UART pin (unrelated
to the modem). All seven of these GPIOs were ALREADY fully excluded from
the Designer's pin list because pins_arduino.h declares no `static const
uint8_t` alias for any of them - so no board.json chipGpios entries were
needed or added for them (adding entries would have been counterproductive
- see "WHY NO chipGpios ENTRIES..." below).

Created board.json (this board previously had none) containing a single
chipGpios entry: GPIO15 (PIN_LED/LED_BUILTIN), tagged as the onboard
general-purpose user LED (active-high, cross-referenced inference).
Unlike the challenger_2040_lte/challenger_nb_2040_wifi siblings, this
board's LED pin carries NO D-number alias at all in pins_arduino.h (only
the #define, which build_boards.js's parser does not read), so without
this chipGpios entry GPIO15 would be entirely invisible in the Designer,
not merely mistagged - this entry was required to surface it.

No onboard NeoPixel found (unlike the challenger_2350_bconnect/
challenger_2350_wifi6_ble5 siblings in this same rp2350 chip bucket,
which do have one - those boards are unaudited and out of scope here).
No discrete user pushbutton found beyond the standard RST reset line
(out of scope, same BOOTSEL/reset precedent as rpipico2/board.json).

GPIO0 and GPIO22 carry no pins_arduino.h alias and are not mentioned
anywhere in the datasheet either (header table, internal module table,
or debug section) - no dedicated function could be confirmed for either,
so per this audit's "report NO CHANGE rather than guess" guidance, no
chipGpios entry was added; they remain fully hidden from the Designer's
pin list exactly as pins_arduino.h already leaves them (the safe default).

pins_arduino.h was NOT modified this session - no button/LED pin was
found to collide with any SPI/I2C/UART bus alias, so the "confirmed
button/LED pin also aliased as a bus signal" bug class does not apply to
this board.

WHY NO chipGpios ENTRIES FOR THE MODEM/DEBUG PINS (GPIO4,5,8,9,10,11,14)
--------------------------------------------------------------------
build_boards.js's buildEsp32Board() (the parser the "rp2040" family
routes through) only lists a GPIO in the Designer's pin picker if it
appears either (a) as a `static const uint8_t` alias in pins_arduino.h,
or (b) as a key in this board's chipGpios object:
  `const allGpios = new Set(aliasesByGpio.keys());
   for (const key of Object.keys(chipGpiosMap)) { ... allGpios.add(n); }`
  (build_boards.js ~line 535-539)

Since this board's pins_arduino.h already declares NO `static const
uint8_t` alias resolving to GPIO4, 5, 8, 9, 10, 11, or 14, those seven
GPIOs are already 100% absent from the Designer's pin list with zero
board.json involvement. Adding chipGpios entries for them here would have
been COUNTERPRODUCTIVE: build_boards.js unconditionally appends a "Check
if available on board" note to ANY rp2040-family GPIO absent from
pins_arduino.h, regardless of whether a chipGpios entry (with its own
custom note) exists for it:
  `if (!inPinsH && cfg.family !== 'esp32' && cfg.family !== 'esp8266')
     noteParts.push('Check if available on board');`
  (build_boards.js ~line 718)
Adding entries here would re-add each pin to allGpios as a bare, visible
"GPIO<n>" row carrying that redundant/misleading note - undoing the full
concealment the pins_arduino.h omission already achieves. Same reasoning
independently traced and documented this session on the
challenger_2040_lte sibling.

PER-PIN REASONING
------------------
GPIO4 (PIN_SERIAL2_TX): ST87M01 modem's dedicated UART TX line ("NB-IoT
  TX | GPIO4 | UART0_RX (pin 15) | RP2350 transmit to module"). Not
  general-purpose. No pins_arduino.h alias exists; already fully absent
  from the Designer pin list. No board.json entry needed or added.

GPIO5 (PIN_SERIAL2_RX): ST87M01 modem's dedicated UART RX line ("NB-IoT
  RX | GPIO5 | UART0_TX (pin 16) | Module transmit to RP2350"). Same
  reasoning as GPIO4.

GPIO8 (PIN_ST87M01_INT): modem's ring/interrupt output line ("NB-IoT INT
  | GPIO8 | UART0_RTS (Pin 19) | Ring output to RP2350"). Same reasoning
  as GPIO4.

GPIO9 (PIN_ST87M01_RSTN): modem's active-low hardware reset line, driven
  by the RP2350 ("Module RESET | GPIO9 | RESETn (pin 38) | Active-low
  hardware reset"). Same reasoning as GPIO4.

GPIO10 (PIN_ST87M01_WAKEUP): modem's wake-from-sleep control line
  ("Module WAKEUP | GPIO10 | WAKE_UP (pin 39) | Wake module from
  sleep"). Same reasoning as GPIO4.

GPIO11 (PIN_GNSS_BIAS_EN): GNSS antenna-bias LDO enable line ("GNSS Bias
  Enable | GPIO11 | Connected to LDO enable | Enabled the GNSS bias
  voltage"). Not general-purpose. Same reasoning as GPIO4.

GPIO14 (PIN_IPROBE_TX): dedicated BConnect/SWD debug-connector software-
  UART TX pin ("The debug TXD signal on the BSWD connector is connected
  to pin GPIO14 ... can be configured as a Software UART pin"). Not
  general-purpose. Same reasoning as GPIO4.

GPIO15 (PIN_LED / LED_BUILTIN): tagged in the new board.json chipGpios
  with ["digital_output", "pwm_output", "led_high"]. Presence confirmed
  via this board's own pins_arduino.h and the byte-identical upstream
  arduino-pico source; corroborated by absence from the datasheet's own
  external header pin table (Section 3.1), confirming GPIO15 is a fixed
  onboard LED not broken out to any header pin. UNLIKE the
  challenger_2040_lte/challenger_nb_2040_wifi siblings, this board's
  PIN_LED carries NO static-const D-number alias in pins_arduino.h at
  all (only the #define, which build_boards.js's parser intentionally
  does not read - see parseEsp32Consts() doc-comment), so without this
  chipGpios entry GPIO15 would be completely ABSENT from the Designer's
  pin list, not merely mistagged - this entry was required to surface it
  at all. Active-high polarity is a cross-referenced inference: this
  board's own datasheet does not state the active level, so the tag
  relies on (a) every other RP2040/RP2350 board audited in this family to
  date being confirmed or inferred active-high, none active-low
  (challenger_2040_lte, challenger_nb_2040_wifi, rpipico2, etc.), and (b)
  this board reusing the same iLabs Challenger product-line onboard-LED
  reference circuit whose sibling boards' own datasheets (e.g.
  challenger_rp2040_wifi) explicitly state "Active level: High".
  digital_input capability dropped to match this repo's established
  led_high precedent for dedicated onboard LED pins; pwm_output kept
  since arduino-pico's analogWrite() works on any RP2040/RP2350 GPIO.

No onboard NeoPixel found - confirmed absent from this board's own
  pins_arduino.h, the byte-identical upstream arduino-pico source, and
  the datasheet (no NEOPIXEL/PIN_NEOPIXEL reference anywhere), unlike the
  challenger_2350_bconnect sibling in this same rp2350 chip bucket (which
  does define NEOPIXEL=GPIO22 - that board is unaudited, out of scope).
  No chipGpios tag applied.

No onboard user button found - confirmed absent by the datasheet (only
  the standard RST reset line is documented, not a normal GPIO on
  RP2040/RP2350, out of scope per the rpipico2/board.json BOOTSEL/reset
  precedent) and by the absence of any BUTTON-style define in
  pins_arduino.h. No chipGpios tag applied.

GPIO0 and GPIO22: no pins_arduino.h alias, and absent from every table in
  the datasheet (external header pins, internal module connections,
  debug section) despite the datasheet's own claim that "Pin assignments
  follow the standard Challenger / Feather layout ... All other pins
  remain fully available." No source consulted confirms a dedicated
  function for either GPIO. Per this audit's "report NO CHANGE rather
  than guess" guidance, no chipGpios entry was added; both remain fully
  absent from the Designer's pin list exactly as pins_arduino.h already
  leaves them - the safe default, since inventing a "general-purpose
  spare pin" chipGpios entry without a confirmed source would risk
  exposing a possibly-still-dedicated pin as user-wireable.

GPIO15 carries no SPI/I2C/other bus alias on this board (SPI0 lives on
  GPIO16-19, Wire0 on GPIO20-21), so the build_boards.js unconditional
  bus-capability auto-append (the "confirmed button/LED pin also aliased
  as SDA/SCL/SS/MOSI/MISO/SCK" bug class flagged for this audit) does not
  apply here - no pins_arduino.h edit was needed. Likewise none of
  GPIO4/5/8/9/10/11/14 collide with any SPI/I2C/UART alias either.

OUT-OF-SCOPE OBSERVATION (flagged only, not fixed): this board's
  pins_arduino.h aliases GPIO1 as "A4", and build_boards.js's default
  capability derivation tags any GPIO with an "A<n>"-pattern alias as
  analog_input - yet the datasheet's own header table explicitly
  annotates "A4 | GPIO1 | GPIO / PWM | Generic GPIO (Not analog input)",
  i.e. GPIO1 is NOT a real ADC-capable pin on this board (RP2350's 4 ADC
  channels are physically fixed to GPIO26-29; A4 is just the
  Feather-form-factor header-slot label reused for a plain digital pin
  here). This is a pre-existing upstream pins_arduino.h/arduino-pico
  naming quirk shared by every iLabs Challenger board in this repo
  (identical A4=(1u) alias already present on challenger_2040_lte,
  challenger_nb_2040_wifi, challenger_2350_wifi6_ble5, and
  challenger_2350_bconnect), not introduced or fixable by this board's
  own pin-exclusion audit - flagged for awareness of a possible future
  non-audit fix only, matching the analogous GPIO20/CircuitPython gap
  already flagged on the challenger_2040_lte sibling's own notes.txt.
