PER-PIN REASONING

GPIO25 (PIN_LED / User_Led):
  capabilities: ["digital_output", "pwm_output", "led_high"]
  Onboard user LED (green, 0603), active-high (see schematic detail above:
  GPIO25 -> R15 2.2k -> LED1 anode -> LED1 cathode -> GND). digital_input
  dropped, matching this repo's established led_high/led_low convention
  for dedicated onboard LED pins (see rpipico2/board.json and
  olimex_pico2xl/board.json GPIO25 precedents). pwm_output kept since
  arduino-pico's analogWrite() works on any RP2350 GPIO (enables LED
  brightness dimming). No SPI/I2C bus alias collision on GPIO25 in this
  board's own pins_arduino.h (SPI0=GPIO4-7, SPI1=GPIO9-11+24,
  Wire0=GPIO12-13, Wire1=GPIO2-3 - GPIO25 is untouched by any of these),
  confirmed independently at the schematic level too (no other net on the
  GPIO25 pad besides the LED branch). No pins_arduino.h edit needed.

GPIO8 (RP2350_PSRAM_CS / QMI_CS1n):
  No chipGpios entry added. This pin is wired to the PSRAM chip-select
  footprint, but that footprint (and the microSD card SPI-bus pins
  GPIO9-11/24) are only populated on the "BB48R" hardware variant, not on
  this base "BB48" board (confirmed via both the User Manual's bottom-view
  photo, showing an empty PSRAM footprint, and the schematic's explicit
  "Present only in the 'BB48R' variant!" annotations). Since this repo has
  a single board id for the family and the pin is a normal, unpopulated
  GPIO on the actual hardware being audited, no dedicated-hardware
  exclusion was applied - left at chip-level defaults. Out of scope for
  the button/LED/NeoPixel focus of this audit regardless (not a button,
  LED, or NeoPixel pin).

Buttons (BOOT/BOOTSEL, RESET):
  No chipGpios entry added, no capability tag applied. Both are wired to
  dedicated chip control lines (QSPI_SSn/bootsel for BOOT, RUN/RESET# for
  RESET), confirmed via the official schematic PDF, not to any numbered
  GPIO with a pins_arduino.h alias. This is the same out-of-scope
  rationale already established for every other RP2040/RP2350 Pico-style
  board in this repo (rpipico, rpipico2, olimex_pico2xl) - neither line is
  a normal digitalRead()-able Arduino GPIO, so there is no pin to attach a
  "button" capability to under this repo's GPIO-keyed tagging scheme.

NeoPixel: none present. Confirmed absent from both the official user
manual (LED-connection section documents exactly one discrete LED, no
addressable/RGB component) and the full schematic (only one LED
component, LED1, appears anywhere on the board). No led_neopixel tag
added.

All other GPIOs (0-7, 9-24, 26-47): no chipGpios entry added - inherit
only their auto-derived bus/digital capabilities from the chip-level
defaults (chipGpios: {} at the chip level). No further dedicated onboard
hardware found on this board beyond the LED (and the BB48R-only
PSRAM/microSD footprints, addressed above, which are unpopulated on this
board and not button/LED/NeoPixel pins in any case).
