Board: waveshare_rp2350_lcd_0_96 (chip: rp2350)
Waveshare "RP2350-LCD-0.96" — the RP2350 successor to the already-audited
waveshare_rp2040_lcd_0_96 sibling. Pico-form-factor RP2350A board with an
onboard 0.96" 160x80 65K-colour IPS TFT LCD (ST7735s-family controller,
4-wire SPI + separate D/C line), USB-C connector, MP28164 + TPS63000
buck-boost DC-DC chips, and an onboard temperature sensor.
Audit date: 2026-07-13.

PER-PIN REASONING / DECISIONS

GPIO8 (PIN_LCD_DC) — onboard LCD's dedicated SPI data/command select
  line. Confirmed by sources #1, #2 (real vendor header), and #3
  (CircuitPython pins.c: "LCD_DC=GPIO8"). ADDITIONALLY this GPIO carried
  the vendor's default Wire0 SDA alias (`PIN_WIRE0_SDA (8u)` promoted to
  a top-level `static const uint8_t SDA = PIN_WIRE0_SDA;`) — the same
  flagged bug class as the RP2040 sibling, and confirmed via source #2 to
  exist in the real arduino-pico vendor source too (not a mirror
  artifact). build_boards.js's unconditional i2c_sda auto-append (fires
  regardless of any chipGpios override) would otherwise tag this
  LCD-dedicated pin as i2c_sda on top of full generic digital I/O, even
  with a chipGpios["8"].capabilities=[] override in place. FIXED at the
  source: removed `#define PIN_WIRE0_SDA` and the referencing
  `static const uint8_t SDA = PIN_WIRE0_SDA;` line from this board's
  pins_arduino.h (this repo's Designer-parsing mirror, not a file
  consumed by any real firmware-build toolchain). Added chipGpios["8"] =
  empty capabilities + note documenting both the LCD dedication and the
  removed Wire0 alias.

GPIO9 (PIN_LCD_CS) — onboard LCD's dedicated SPI1 chip-select line. Same
  confirmation (sources #1-#3) and same bug-class fix as GPIO8: removed
  `#define PIN_WIRE0_SCL` and `static const uint8_t SCL = PIN_WIRE0_SCL;`.
  Added chipGpios["9"] = empty capabilities + note.

GPIO10 (PIN_LCD_SCLK) — onboard LCD's dedicated SPI1 clock line,
  software-remapped from SPI1's silicon-default GPIO14 to GPIO10 (a
  valid, ordinary RP2040/RP2350 GPIO-mux remap — SPI1 SCK is selectable
  among GPIO10/14/26 on this chip family; not a discrepancy). Confirmed
  by sources #1-#3 (CircuitPython: "LCD_CLK=GPIO10"). Already excluded
  from pins_arduino.h's own D-alias list. Added chipGpios["10"] = empty
  capabilities + note, purely to document the dedication (matches the
  RP2040 sibling and bridgetek_idm2040_43a precedent of recording
  already-invisible dedicated pins for clarity).

GPIO11 (PIN_LCD_MOSI / DIN) — onboard LCD's dedicated SPI1 data-out line,
  similarly remapped from SPI1's silicon-default GPIO15. Confirmed by
  sources #1-#3 (CircuitPython: "LCD_DIN=GPIO11"). Same treatment as
  GPIO10.

GPIO12 (PIN_LCD_RST) — onboard LCD's dedicated hardware reset line.
  Confirmed by sources #1-#3 (CircuitPython: "LCD_RST=GPIO12";
  independent WebSearch corroboration). Same treatment as GPIO10. (This
  GPIO is also SPI1's silicon-default MISO pin per PIN_SPI1_MISO=12, but
  that role is irrelevant here since RST is driven as a plain digital
  output, not read via the SPI1 peripheral.)

GPIO13, GPIO14, GPIO15 (PIN_SPI1_SS/SCK/MOSI, SPI1's silicon-*default*
  pins) — NOT confirmed by any source consulted as physically wired to
  the LCD or any other onboard peripheral; the LCD's actual SPI1 usage is
  entirely on the remapped GPIO10/11 (+ manual GPIO8/9/12 GPIO lines), so
  these three default-SPI1 pins are left unused by the display. This
  board's pins_arduino.h already omits their D13/D14/D15 aliases (mirrors
  the RP2040 sibling's identical prior decision), which was arguably
  conservative, but no vendor source found in this session confirms or
  refutes that choice either way. Per this audit's "confirm via real
  vendor documentation, never guess — report NO CHANGE rather than guess"
  rule: NOT added to chipGpios (no entry needed anyway, since they're
  already excluded from the Designer by the missing pins_arduino.h alias,
  and no new evidence supports changing that decision in either
  direction). Matches the RP2040 sibling's identical conclusion for these
  same three GPIOs.

GPIO25 (PIN_LCD_BL) — onboard LCD's dedicated, PWM-dimmable
  backlight-enable line. Confirmed via source #3 (CircuitPython:
  "LCD_BL=GPIO25") and independent WebSearch/product-page corroboration.
  This is NOT a general-purpose status LED (unlike, e.g.,
  bridgetek_idm2040_43a's or rpipico's GPIO25, which are genuinely spare
  onboard LEDs unrelated to any display) — it is entirely committed to
  the onboard LCD's backlight circuit, so it is tagged with empty
  capabilities (no led_high/led_low/pwm_output), matching this repo's
  dedicated-hardware-pin convention and the RP2040 sibling's identical
  treatment of its own GPIO25. Already excluded from pins_arduino.h's own
  D-alias list. Added chipGpios["25"] = empty capabilities + note.

Onboard buttons — NONE found beyond BOOT/RESET. Sources #3, #4, and #5
  all independently describe/enumerate this board's features/components
  without mentioning any general-purpose push-button — only the standard
  BOOT+RESET firmware-download key combo (RP2350's BOOTSEL-equivalent,
  out of scope per point 6 above). Per "confirm via real vendor
  documentation, never guess — report NO CHANGE rather than guess": NO
  button capability added anywhere on this board.

Onboard NeoPixel/WS2812 — NONE found. Source #3 (CircuitPython's own
  pins.c/mpconfigboard.h for this exact board) contains zero LED/NeoPixel
  pin definitions. Source #4's targeted re-scan of the full wiki page
  text for WS2812/NeoPixel/RGB LED/any LED demo found zero matches. An
  initial, more ambiguous WebSearch summary had suggested possible WS2812
  "board status" support, but this could not be corroborated against a
  direct, full-text fetch of the wiki page itself and is treated as a
  mix-up with a different Waveshare product (same conclusion pattern
  already established for the RP2040 sibling's audit, whose wiki WS2812
  demo also turned out to target an external, user-wired LED rather than
  an onboard one). NO NeoPixel capability added.

GPIO8/GPIO9 bus-role collision — CONFIRMED PRESENT on this RP2350 board,
  identically to the already-fixed RP2040 sibling, and independently
  confirmed present in the real earlephilhower/arduino-pico vendor source
  (source #2) — i.e. a genuine upstream header quirk on the actual
  hardware/toolchain, not something introduced by either repo's mirror.
  FIXED the same way as the sibling: removed `#define PIN_WIRE0_SDA (8u)`
  / `#define PIN_WIRE0_SCL (9u)` and the two referencing
  `static const uint8_t SDA/SCL = PIN_WIRE0_SDA/SCL;` lines from
  variants/rp2040/rp2350/waveshare_rp2350_lcd_0_96/pins_arduino.h. Wire1
  (GPIO6/7) is unaffected and untouched. Whole-file grep for
  SDA/SCL/WIRE0 after the edit confirms no remaining dangling references
  (only explanatory comment text). This pins_arduino.h copy is this
  repo's own Designer-parsing mirror, not a file consumed by any real
  firmware-build toolchain, so the edit does not affect real device
  firmware compiles.

SUMMARY
Created variants/rp2040/rp2350/waveshare_rp2350_lcd_0_96/board.json (new
file — none existed before; chip-level variants/rp2040/rp2350/board.json
has chipGpios={} by design). Added chipGpios documentation entries (empty
capabilities + sourced note) for GPIO8/9/10/11/12/25 (onboard LCD's
DC/CS/SCLK/MOSI/RST/backlight lines) — GPIO10-12/25 were already excluded
from pins_arduino.h's own alias declarations, so this formalizes/
documents rather than newly changes their Designer exposure. GPIO8/9
required an additional pins_arduino.h fix: their vendor-default Wire0
SDA/SCL aliases (PIN_WIRE0_SDA=8, PIN_WIRE0_SCL=9) collided with these
same GPIOs' dedicated LCD DC/CS role — a genuine bug confirmed present in
the real vendor arduino-pico source too, identical to the already-fixed
RP2040 sibling — so removed `#define PIN_WIRE0_SDA/SCL` and the two
referencing `static const uint8_t SDA/SCL` lines from this board's
pins_arduino.h (Wire1 on GPIO6/7 is unaffected and untouched; this
pins_arduino.h copy is this repo's own Designer-parsing mirror, not a
file consumed by any real firmware-build toolchain, so the edit does not
affect real device firmware compiles). No onboard button found beyond
the standard BOOT/RESET firmware-download combo (out of scope, matching
precedent). No onboard NeoPixel/WS2812 found after a targeted full-text
re-scan of the wiki page (an initial ambiguous search snippet could not
be corroborated and is treated as a product mix-up). GPIO13/14/15 (SPI1's
unused silicon-default pins) were investigated but left
unchanged/undocumented in chipGpios — no vendor confirmation either way,
matching both the "report NO CHANGE rather than guess" rule and the
RP2040 sibling's identical conclusion.
