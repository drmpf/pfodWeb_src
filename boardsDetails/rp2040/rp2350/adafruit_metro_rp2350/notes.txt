Board: Adafruit Metro RP2350 (Adafruit product 6003, also sold with PSRAM as
product 6267)
Chip bucket: variants/rp2040/rp2350/adafruit_metro_rp2350
Audit date: 2026-07-13
Part of: RP2040/RP2350 family button/LED/NeoPixel tagging + dedicated-hardware
pin exclusion audit (see project_board_variant_pin_audit_playbook memory).
Directly relevant precedent: variants/rp2040/rp2040/adafruit_metro (the RP2040
sibling, audited earlier this same session).

SUMMARY (one line): Tagged GPIO23 as the onboard LED (active-LOW — the
OPPOSITE polarity of the RP2040 sibling's active-high LED), GPIO24 as a
genuine onboard "Boot0" button that IS application-GPIO-readable (unlike the
RP2040 sibling and unlike the classic Pico's non-GPIO BOOTSEL), and GPIO25 as
the onboard single WS2812 NeoPixel (same as the RP2040 sibling). Also
restricted 11 additional dedicated-hardware pins (DVI/HSTX connector x8, USB
host D+/D-, SD DATA1/DATA2, PSRAM CS, SD card-detect) that carry no bus alias
and would otherwise get spurious full digital-I/O capability from the
chip-level default. No pins_arduino.h bug found (no bus-alias contamination
on any of the three confirmed LED/button/NeoPixel pins).

- PIN_NEOPIXEL = 25, NUM_NEOPIXEL = 1
- PIN_BUTTON = 24 ("'Boot0' button also on GPIO #24")

- SDIO/SD card: CLK=34, CMD/MOSI=35, DAT0/MISO=36, DAT1=37, DAT2=38,

PER-PIN REASONING
-----------------
GPIO23 (PIN_LED) — CHANGED. Onboard plain red status LED, ACTIVE-LOW
(sources #1, #3, #4). Tagged capabilities: digital_output, pwm_output,
led_low. digital_input dropped per this repo's established led_high/led_low
convention for dedicated onboard LED pins. pwm_output kept since
arduino-pico's analogWrite() works on any RP2350 GPIO. Checked for bus-alias
contamination: GPIO23 carries no SPI/Wire/Serial alias anywhere in this
board's pins_arduino.h (SPI0_SS=39, SPI1_SS=29, Wire0 SDA/SCL=20/21 — none
touch 23) — no pins_arduino.h edit needed. NOTE: this is the OPPOSITE
polarity from the RP2040 Metro sibling's GPIO13 LED (active-high there) —
independently re-verified via this board's own Zephyr devicetree source
rather than assumed carried-over from the sibling.

GPIO24 (PIN_BUTTON) — CHANGED (new finding vs. the RP2040 sibling, which has
no button at all). Onboard "Boot0" button, genuinely application-GPIO-
readable (sources #1 lists no D24 header pin, consistent with GPIO24 being
reserved for this role; source #4's CircuitPython pins.c independently maps
BOTH "BUTTON" and "BOOT" board-name aliases to pin_GPIO24; source #6
confirms the exact same PIN_BUTTON macro/comment exists byte-for-byte in the
upstream arduino-pico vendor package, not a repo-local addition). Tagged
capabilities: digital_input, button — matching this task's own stated
button-tagging vocabulary (two-element form), and matching several other
same-session precedents in this family for genuinely GPIO-wired onboard
buttons (evn_alpha PIN_BUTTON, cytron_maker_uno PIN_BUTTON, pimoroni_explorer
SWITCH_*, adafruit_fruitjam PIN_BUTTON2/3). Checked for bus-alias
contamination: GPIO24 carries no SPI/Wire/Serial alias in this board's
pins_arduino.h — no pins_arduino.h edit needed. This button is DIFFERENT in
kind from the classic RP2040 Pico/Pico 2's BOOTSEL (a hardwired
QSPI-flash-chip-select trick exposed only as a boolean object, never a
numbered GPIO — see this repo's own rpipico2/board.json precedent, which
explicitly declines to tag a button for that reason): RP2350 supports an
OTP-configurable boot-select GPIO instead, and Adafruit's own two
independent toolchains (arduino-pico and CircuitPython) both expose GPIO24
as a plain, application-readable button/boot pin on this specific board.

GPIO25 (PIN_NEOPIXEL) — CHANGED (carried over unchanged from the RP2040
sibling). Onboard single WS2812 status NeoPixel, output-only data line
(sources #1, #2, #3, #4 all agree). Tagged capabilities: digital_output,
led_neopixel — no pwm_output (a NeoPixel data line is not driven via
analogWrite()). Checked for bus-alias contamination: GPIO25 carries no
SPI/Wire/Serial alias in this board's pins_arduino.h — no pins_arduino.h
edit needed.

GPIO12-19 (DVI/HSTX connector: D2P, D2N, CKP, CKN, D1P, D1N, D0P, D0N) —
CHANGED (dedicated-hardware pin exclusion, secondary finding beyond the
button/LED/NeoPixel focus). None of these carry any bus alias in this
board's pins_arduino.h, so the RP2350 chip-level default (chipGpios: {})
would otherwise leave them with full digital_input/digital_output/pwm_output
capability despite being genuinely dedicated to the onboard DVI video output
connector (confirmed by this board's own pre-existing pins_arduino.h header
comment and independently corroborated by source #1's exact GPIO-role
match for the neighboring USB-host/SD pins). Each tagged
chipGpios["N"] = {"capabilities": []}.

GPIO32/33 (PIN_USB_HOST_DP/DM) — CHANGED. USB host connector data lines, no
bus alias, confirmed dedicated via source #1's exact GPIO match. Each tagged
capabilities: [].

GPIO37/38 (PIN_SD_DAT1/DAT2) — CHANGED. SDIO 4-bit-mode data lines for the
onboard microSD slot, no bus alias (unlike SD_CLK/CMD/DAT0/DAT3, which
double as PIN_SPI1_SCK/MOSI/MISO/SS and are correctly auto-supplied — see
NO CHANGE section below). Each tagged capabilities: [].

GPIO40 (PIN_SD_DETECT) — CHANGED. microSD card-presence-detect switch.
Tagged capabilities: ["digital_input"] — digital_output/pwm_output dropped
(driving this pin as an output could contend with the mechanical detect
switch when a card is inserted), matching this repo's
solderparty_rp2350_stamp PIN_CARD_DETECT precedent exactly.

GPIO47 (RP2350_PSRAM_CS) — CHANGED. Optional onboard PSRAM footprint's
chip-select line (not populated on all units — the base product 6003 ships
without PSRAM soldered; product 6267 ships with it). No bus alias. Tagged
capabilities: [].

NO CHANGE (left untouched, with reasoning)
-------------------------------------------
GPIO34/35/36/39 (SD CLK/MOSI/MISO/CS, doubling as PIN_SPI1_SCK/MOSI/MISO/SS)
— left untouched. These already carry correct PIN_SPI1_* aliases matching
the SD card's own genuine SPI interface, so build_boards.js's automatic
spi_sck/spi_mosi/spi_miso/spi_ss auto-append is the DESIRED behavior here
(the SD card genuinely owns this bus), not a contamination bug — exactly
matching the RP2040 Metro sibling's own explicit precedent for its
equivalent SD-SPI0 pins ("no board.json fix needed there ... the automatic
SPI-capability append on these pins is the DESIRED behavior here").

GPIO29 (PIN_5V_EN / PIN_SPI0_SS collision) — left untouched, NOT a bug fix
candidate. This board's own pins_arduino.h genuinely dual-purposes one
physical GPIO as both the general-purpose header SPI0's SS line AND the USB
host connector's 5V-power-enable control (already flagged in this board's
own pre-existing pfodWeb NOTE header comment, lines 86-88, before this
session). Unlike the PIN_SPIx_SS bug class this audit otherwise watches for
(a stray/incidental vendor #define with no genuine onboard device using
that SS role, fixable by deleting the #define), this is a genuine,
documented, real physical dual-use of a single pin by design — there is no
spurious #define to remove, and removing either the SPI0_SS or 5V_EN
alias would misrepresent the actual hardware. Left as a known hardware
constraint (a user driving SPI0 SS on the general header will also toggle
USB host 5V power), not something this repo's board.json schema can cleanly
resolve — noted here for visibility, no chipGpios entry added.

GPIO0/1 (Serial1 TX/RX), GPIO20/21 (Wire0 SDA/SCL, exposed on the STEMMA QT
connector per this board's own PCB README), GPIO26-28/30/31 (general-purpose
header pins doubling as the general SPI1-aka-spi0 bus: MISO=28, SCK=30,
MOSI=31, plus SS=29 covered above), GPIO2-11 (plain D2-D11), GPIO41-46
(A0-A5 analog inputs) — all left untouched as genuine general-purpose
header/bus pins, not dedicated onboard peripherals. No LED/button/NeoPixel
alias exists on any of them.
