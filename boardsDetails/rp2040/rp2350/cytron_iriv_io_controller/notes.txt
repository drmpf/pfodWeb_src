       output (up to 50V), 2x 12-bit analog input (0-10.56V / 0-42.58mA),
       PCF85063A RTC, "1x reset button 1x boot button & 1x programmable

       DOUT", "1x passive buzzer".

       +-50V, isolation 3750Vrms, max pulse freq 5000Hz. Isolated Digital
       Output up to 50V/500mA, isolation 1500Vrms. Isolated RS485 up to
       500kbps, isolation 5000Vrms. Analog input 12-bit, 0-10.56V or
       0-42.58mA full scale, 32K ohm / 248 ohm input impedance.
     - Section 3.1 (External Layout table, verbatim rows):
         "2 User Button - User programmable button. Connected to GPIO28
          (active low)."
         "6 Status LEDs - PWR: turn on when powered up. USR: User
          programmable LED. Controlled by GPIO29. 485: turn on when there
          is activity on RS485. DOUT 0-3: turn on when output activated.
          DIN 0-10: turn on when input triggered."
         "3 Boot Button" / "4 Reset Button" - pinhole buttons, not normal
          GPIOs (BOOTSEL-style, matches existing rpipico precedent
          reasoning - not GPIO-representable, out of scope).
     - Section 3.2 (Internal Board Layout table): "4 Passive Buzzer -
       ...Controlled by GPIO11." "2 RTC - PCF85063A Real Time Clock (I2C
       Slave Address = 0x51)." "3 Ethernet Controller - Wiznet W5500."
     - Section 4 (Block Diagram): full per-GPIO wiring diagram - GPIO28
       (User Btn), GPIO11 (Beep), GPIO29 (USR), GPIO18 (W5500 INT),
       SPI0 (MOSI:19, MISO:20, CSn:21, SCK:22 to W5500), Reset:23 (implied

       text extraction but confirmed by the pin-mapping table below),
       UART1 (RS485 TX:24, RX:25), I2C0 (RTC SDA:16, SCL:17), GPIO26/27
       (AN0/AN1 via voltage-level-shifter), GPIO0-4 + GPIO5-10 (DI0-DI10,
       each through an "Isolate" opto-isolator block), GPIO12-15 (DO0-DO3,
       each through an "Isolate" block, solid-state-relay driven).
     - Section 5.1 (Pin Mapping table) - the definitive, exact GPIO map,
       matching this board's own pins_arduino.h GPIO numbers 1:1 for every
       signal: DI0-DI10 = GP0-GP10, AN0/AN1 = GP26/GP27, DO0-DO3 =
       GP12-GP15, RS485 TX/RX (UART1) = GP24/GP25, Ethernet INT/RESET/CSn
       (GPIO) = GP18/GP23/GP21, Ethernet MOSI/MISO/SCK (SPI0) =
       GP19/GP20/GP22, RTC SDA/SCL (I2C0) = GP16/GP17, User Button (GPIO)
       = GP28, User LED (GPIO) = GP29, Passive Buzzer (GPIO/PWM) = GP11.
     - Section 5.2.3 (Analog Input): "There are 2 analog inputs
       (non-isolated, AGND is shared with system GND) connected to the AN0
       (GPIO26) & AN1 (GPIO27)... configured to measure voltage or current
       with a DIP switch... 12-bit resolution with full scale of 10.56V or
       42.58mA... input impedance 32K ohm (voltage) / 248 ohm (current)."
       Includes a simplified schematic (R16=22K series, R17=10K to GND,

       only ever sees 0-3.3V; the 10.56V/42.58mA full-scale figures
       describe the EXTERNAL terminal signal after conditioning, not the
       silicon ADC pin's own reference voltage.
     - Section 5.2.4 (Isolated Digital Input): "11 isolated digital inputs
       (active high) divided into two groups, with independent common S/S
       (Sink/Source) for each group... flexibility to connect to both PNP

       inputs."
     - Section 5.2.5 (Isolated Digital Output): "four digital outputs...
       isolated from the system as well as among the different output
       channels. The outputs are active high and controlled directly from
       the Raspberry Pi GPIO. They are dry contact outputs driven by a
       solid state relay and able to handle DC or AC load at maximum 50V
       500mA."
     - Section 5.3 (Ethernet): "communicates with the RP2350A MCU via SPI
       at maximum frequency up to 80MHz."

===============================================================================
PER-PIN DISPOSITION (full reasoning; see board.json's own top-of-file
comment for the condensed version that ships with the repo)
===============================================================================

GPIO0-10 (DI0-DI10, 11 pins) - CONFIRMED isolated digital inputs, active
  high, opto-isolated (3750Vrms), up to 50V. Tagged digital_input ONLY.
  Reasoning: the GPIO's sole electrical connection on this net is to the
  isolator's phototransistor collector/emitter (input direction only) -
  driving the pin would fight that phototransistor. This is the same
  class of finding as the existing wiznet_55rp20_evb_pico GPIO18
  (VBUS-sense-divider, tagged digital_input-only for the same "driving
  this pin fights the sense circuit" reason) - not a new precedent
  pattern, an application of an existing one. Not tagged "button" (that
  tag is reserved for actual onboard pushbuttons, not generic terminal-
  block digital inputs).

GPIO12-15 (DO0-DO3, 4 pins) - CONFIRMED isolated digital outputs, active
  high, solid-state-relay-driven, up to 50V/500mA. LEFT AT CHIP-LEVEL
  DEFAULT (no chipGpios entry) per this repo's own documented playbook
  policy: "Relay outputs (Sonoff-style boards): a relay is a simple
  digital on/off actuator, and controlling it from pfodWeb IS the point
  of using such a board with pfodWeb - do not exclude, unlike a
  stepper/heater." Matches the existing cytron_maker_pi_rp2040 precedent
  of leaving motor/servo-driver GPIOs at full default capability - the
  downstream relay hardware doesn't change what the RP2350 GPIO pin
  itself can safely do (digitalWrite/analogWrite both function normally;
  only the far side of the isolator/relay is affected, which is exactly
  the intended and expected behavior for this product).

GPIO26/27 (AN0/AN1) - CONFIRMED non-isolated analog inputs, switch-
  selectable voltage (0-10.56V) / current (0-42.58mA) mode via an onboard
  resistor-divider/shunt network, per the datasheet's own schematic
  (section 5.2.3: "Voltage scale: MCU = AN * 5/16", R16=22K series,
  R17=10K to GND). LEFT AT CHIP-LEVEL DEFAULT (analog_input +
  digital_input + digital_output + pwm_output, matching the alias-derived
  default from this board's own A0/A1 declarations) - ordinary sketch-
  facing analog input, exactly the board's intended use.
  "adc.defaultRefVolts" was deliberately NOT changed to "10.56" (or any
  other value) - unlike a simple fixed-ratio resistor-divider board (e.g.
  d1_mini's 3.2V correction), this terminal is switch-selectable between
  two entirely different physical units (volts vs. milliamps), which a
  single linear full-scale-voltage constant cannot represent. The RP2350
  ADC pin itself genuinely still only ever sees 0-3.3V (confirmed by the
  datasheet's own "MCU = AN * 5/16" formula, since 10.56V * 5/16 = 3.3V
  exactly) - so "3.3" remains the electrically correct answer for what
  the silicon pin experiences; a sketch reading either mode must still
  apply its own scaling based on which physical mode the DIP switch is
  set to, and that can't be captured in this single JSON field. Documented
  here explicitly rather than silently left unconsidered.

GPIO28 (PIN_BUTTON) - CONFIRMED via the official datasheet (section 3.1,
  verbatim): "User Button - User programmable button. Connected to GPIO28
  (active low)." Tagged ["digital_input","button"] only - no
  analog_input/digital_output/pwm_output, per this repo's standard
  button-tagging exclusion rule (section 7a of the pin-audit playbook).
  Note: this board's pins_arduino.h ALSO aliases GPIO28 as "A2"
  (boilerplate from the generic RP2350A core's declaration of all 4
  ADC-capable GPIOs as A0-A3, regardless of a specific board's real analog
  wiring - only GPIO26/27 are actually wired to real analog signals on
  this board). This is harmless: a chipGpios override entry with an
  explicit "capabilities" array fully replaces the alias-derived
  capability set (build_boards.js's buildEsp32Board(), `if (chipEntry &&
  chipEntry.capabilities) { caps = CAP_ORDER.filter(...) }` branch), so no
  spurious analog_input capability leaks through despite the A2 alias
  still being textually present in pins_arduino.h.

GPIO29 (PIN_LED) - CONFIRMED via the official datasheet (section 3.1,
  verbatim): "USR - User programmable LED. Controlled by GPIO29." Active-
  high polarity CONFIRMED via Cytron's own official CircuitPython HAL
  example (github.com/CytronTechnologies/Cytron-IRIV-IO-Controller,
  examples/circuitpython/modbus_io_expander/source/lib/iriv_ioc_hal.py):
  `led.direction = digitalio.Direction.OUTPUT; led.value = 0` initializes
  the LED OFF at value 0, implying value 1 turns it on (active-high).
  Tagged ["digital_output","pwm_output","led_high"] (digital_input
  dropped), matching the cytron_maker_nano_rp2040 GPIO2 / rpipico GPIO25
  precedent for a single dedicated status LED - pwm_output kept since
  arduino-pico's analogWrite() works on any RP2350 GPIO (enabling
  brightness dimming), matching those same two precedents. Same
  boilerplate "A3" alias situation as GPIO28 above, fully superseded by
  this override for the same reason.

PIN_BUZZER (GPIO11) - CONFIRMED passive buzzer, "able to play variable
  frequency tone or melody... Controlled by GPIO11" (datasheet section
  3.2). LEFT UNTAGGED / chip-level default, per task scope - no buzzer
  capability vocabulary exists anywhere in this codebase yet (confirmed by
  checking designer/boards/shared/PinType.js's capability constant list
  indirectly via the cytron_maker_pi_rp2040/cytron_maker_nano_rp2040
  precedent files, both of which explicitly left their own PIN_BUZZER
  GPIOs untagged for the identical reason). No chipGpios entry added.

GPIO16/17 (I2C0 SDA/SCL) - CONFIRMED wired to the onboard PCF85063A RTC
  (I2C address 0x51, datasheet section 3.2). LEFT UNCHANGED at chip-level
  default, per this repo's established KEEP policy for I2C buses:
  "General-purpose I2C/SPI buses without a documented exclusive onboard
  consumer, even if only one device happens to be attached in the
  reference design (I2C especially is inherently multi-drop)." The RTC
  being present on this bus doesn't preclude a sketch wiring up further
  I2C peripherals at a different bus address via the same SDA/SCL lines
  (a real, commonly-used pattern for this class of industrial I/O board).

GPIO18 (PIN_W5500_INT) and GPIO23 (PIN_W5500_RST/RESET) - CONFIRMED W5500
  Ethernet controller interrupt and reset lines (datasheet block diagram,
  section 4; pin-mapping table, section 5.1). NO chipGpios entry added -
  this board's own pins_arduino.h already declares neither GPIO as a
  static-const alias of any kind (no D18, no D23 - confirmed by direct
  inspection of the file, and by its own inline comment already flagging
  GPIO18/19/20/21/22/23 as dedicated). Per build_boards.js's `allGpios`
  construction (`new Set(aliasesByGpio.keys())` unioned with chipGpios
  object keys - read directly from pfodWeb_src/build_boards.js lines
  ~531-539 to confirm this mechanic before deciding, rather than assuming
  it), a GPIO absent from BOTH the pins_arduino.h alias set AND a
  chipGpios key never appears in the generated pin list at all - these
  two GPIOs are therefore already fully excluded by the existing file
  design, with no board.json action needed. Deliberately did NOT add a
  chipGpios entry to make them newly visible-but-restricted (unlike the
  wiznet_5100s_evb_pico precedent, where the underlying pins_arduino.h
  file DID already expose its board's equivalent INT/RESET GPIOs as
  ordinary D-pins and therefore genuinely required a board.json override
  to correct) - there is no user-facing benefit to exposing an Ethernet-
  library-internal interrupt/reset line as a pfodWeb-pickable pin, and
  doing so would only add UI clutter with zero legitimate use case.

GPIO19/20/21/22 (PIN_W5500_MOSI/MISO/CS/SCK = SPI0 MOSI/MISO/SS/SCK) -
  CONFIRMED dedicated onboard SPI bus to the W5500 Ethernet controller
  (datasheet section 5.3: SPI up to 80MHz). These GPIOs ARE still
  aliased in pins_arduino.h (as SS/MOSI/MISO/SCK - required for the SPI0
  peripheral itself to function, distinct from the D-pin aliases that
  were already removed for GPIO18/23 above) - so without an override they
  would carry full chip-level-default digital_input/digital_output/
  pwm_output capability alongside their auto-appended spi_mosi/spi_miso/
  spi_ss/spi_sck role (build_boards.js lines ~698-703, which run
  unconditionally regardless of any chipGpios override). Overridden here
  to "capabilities": [] - an exact precedent match to this repo's existing
  wiznet_5100s_evb_pico GPIO16/17/18/19 treatment (same "capabilities:[]"
  pattern, same reasoning: strip the generic default, keep only the
  genuine auto-appended SPI-bus-role tag).

GPIO24/25 (PIN_SERIAL2_TX/RX, UART1) - CONFIRMED dedicated isolated RS485
  transceiver UART (datasheet section 5.2.2: "mapped to the UART1 (Tx:
  GPIO24, Rx: GPIO25)... isolated from the system and other interfaces...
  automatic direction control"). The terminal block only ever exposes the
  RS485 A/B/G differential signals - never raw GPIO24/25 - so these two
  GPIOs have no legitimate general-purpose use outside driving the onboard
  isolated RS485 transceiver via Serial2. Categorized the same as the
  W5500 SPI bus above ("communication bus wired exclusively to a specific
  onboard/always-attached chip"). This board's own pins_arduino.h aliases
  these as plain D24/D25 (not the literal names "TX"/"RX"), so
  build_boards.js's automatic serial_tx/serial_rx detection (keyed only on
  a literal `static const uint8_t TX = ...;`/`RX = ...;` declaration) does
  NOT fire here on its own - confirmed by reading parseEsp32Consts()/
  buildEsp32Board() directly (pfodWeb_src/build_boards.js) rather than
  assuming. Fixed using the documented `forcedRole` mechanism instead: a
  chipGpios entry whose "capabilities" array contains "serial_tx" (or
  "serial_rx") forces the exact same single-role treatment a literal
  TX/RX alias would get (build_boards.js lines ~657-668) - this is
  precisely the use case called out in that file's own comment ("needed
  for chips... whose vendor pins_arduino.h files don't consistently alias
  the UART pins as literal TX/RX names"), so this is applying an existing,
  intended mechanism rather than inventing a new pattern.

Boot Button, Reset Button - NOT GPIO-representable (pinhole BOOTSEL-style
  buttons per the datasheet's own description "This is a pinhole button
  and can be pressed with a paperclip" for both), matching the existing
  rpipico board.json's identical reasoning for the plain Pico's BOOTSEL
  button. Out of scope, not a missed tag.

RS485 Termination Resistor Switch, Analog Input Mode Switch (voltage/
  current) - physical DIP switches on the board's underside, not GPIOs at
  all (confirmed via datasheet section 3.1, items 10/11). Not
  representable in board.json's GPIO-keyed schema; no action possible or
  needed.

SUMMARY
===============================================================================

board.json CREATED (did not exist before this session) at
variants/rp2040/rp2350/cytron_iriv_io_controller/board.json - full copy of
the rp2350 chip-level defaults plus 19 chipGpios overrides: 11 isolated
digital-input-only entries (GPIO0-10), 4 W5500-SPI-bus capability-strip
entries (GPIO19-22), 2 RS485-UART forced-serial-role entries (GPIO24-25),
1 confirmed button tag (GPIO28, active low), 1 confirmed LED tag (GPIO29,
active high). GPIO12-15 (isolated DO, relay outputs) and GPIO26/27 (analog
inputs) and GPIO11 (buzzer) and GPIO16/17 (RTC I2C bus) were all
deliberately left at chip-level default capability - explicitly considered
and NOT excluded, per the reasoning above, not overlooked. GPIO18/23
(W5500 INT/RESET) were confirmed already fully excluded by this board's
existing pins_arduino.h design (no alias present) - no board.json action
needed or taken for those two.

JSON validity confirmed via a comment-stripping JSON.parse check (no build
commands run, per task instructions).
