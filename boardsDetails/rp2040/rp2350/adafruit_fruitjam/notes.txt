PER-PIN REASONING (chipGpios entries added)
--------------------------------------------
Buttons (input-only, active-low, internal pull-up):
  GPIO0  -> digital_input + button   (PIN_BUTTON1 / board.BUTTON1, also doubles as UF2 BOOT button)
  GPIO4  -> digital_input + button   (PIN_BUTTON2 / board.BUTTON2)
  GPIO5  -> digital_input + button   (PIN_BUTTON3 / board.BUTTON3)

LED (dual-purpose, reversed polarity):
  GPIO29 -> digital_input + digital_output + led_low
    Confirmed reversed wiring (anode->3.3V, cathode->GPIO29): LOW = on, HIGH = off ("This is
    unusual and is the reverse from most other boards" — vendor's own words). ALSO wired to an
    onboard IR receiver (board.IR) on the exact same physical pin. No "IR receiver" capability
    exists in this codebase's vocabulary, so digital_input was kept alongside led_low (rather
    than dropped, as would be done for a plain single-purpose LED) to reflect the real, sourced,
    second function of this pin.

NeoPixel:
  GPIO32 -> digital_output + led_neopixel   (PIN_NEOPIXEL, NUM_NEOPIXEL=5, 3.3V powered)

Dedicated/excluded hardware (capabilities: [] — #define-only in pins_arduino.h, no
static-const alias, so none of these reached the Designer's pin picker before this board.json
existed; added explicitly with notes per the pimoroni_explorer/wiznet precedent):
  GPIO1, GPIO2   -> onboard USB host hub D+/D-
  GPIO3          -> ESP32-C6 co-processor SPI-hosted-link busy/ready (SPIWIFI_ACK)
  GPIO8, GPIO9   -> ESP32-C6 co-processor UART1 TX/RX (SerialESP32 = Serial1)
  GPIO11         -> onboard USB host hub 5V-enable
  GPIO12-19      -> DVI/HSTX video output (4 differential pairs: CK, D0, D1, D2)
  GPIO22         -> shared reset: ESP32-C6 co-processor AND TLV320DAC3100 audio codec
  GPIO23         -> I2S codec IRQ, dual-purpose with ESP32-C6 GPIO0 bootstrap pin
  GPIO24-27      -> I2S audio data/mclk/bitclk/wordsel to the TLV320DAC3100 codec
  GPIO28, 30, 31 -> ESP32-C6 co-processor SPI1 MISO/SCK/MOSI
  GPIO33-39      -> onboard microSD card slot (detect, SPI0/SDIO clock, cmd/mosi, dat0/miso,
                    dat1, dat2, dat3/cs)
  GPIO46         -> ESP32-C6 co-processor SPI1 chip-select (SPIWIFI_SS)
  GPIO47         -> onboard 8MB PSRAM chip-select

KEPT general-purpose (no chipGpios override — reached via existing static-const aliases,
default full digital_input/digital_output/pwm_output capability from the empty chip-level
board.json applies as-is):
  GPIO6, GPIO7, GPIO10 (D6/D7/D10) — plain breakout GPIOs on the 16-pin expansion header, no
    dedicated function found in any source consulted.
  GPIO40-45 (A0-A5) — the expansion header's 6 analog-friendly JST-PH inputs, a genuine
    user-facing expansion feature (matches this repo's established onboard-analog-expansion
    KEEP policy, e.g. pimoroni_explorer ADC0-5).
  GPIO20/21 (SDA/SCL) — the STEMMA QT connector's I2C0 bus. Documented via top-level pinNotes
    (informational only, capabilities unchanged) that this same bus also reaches the onboard
    TLV320DAC3100 codec's control interface and DVI EDID readout — kept general-purpose because
    it is still the board's standard user-facing Wire/STEMMA QT expansion bus, matching this
    repo's precedent of keeping a shared expansion I2C bus general-purpose even when onboard
    devices also sit on it.

BUS-COLLISION BUG CHECK (per this session's known bug class)
--------------------------------------------------------------
Checked whether any confirmed button/LED/NeoPixel pin (GPIO0, 4, 5, 29, 32) is ALSO aliased as
SDA/SCL/SS/MOSI/MISO/SCK by build_boards.js's parseEsp32Consts() (which would cause an
unconditional bus-capability auto-append regardless of chipGpios). This board's pins_arduino.h
declares only two such named aliases at all — `SDA` and `SCL`, both pointing to GPIO20/21 (the
STEMMA QT bus) — neither of which collides with any button/LED/NeoPixel pin. No `static const
uint8_t SS/MOSI/MISO/SCK/TX/RX` aliases exist anywhere in this file (the SPI/UART pins used by
the microSD, DVI, and ESP32-C6 co-processor links are all plain #defines, e.g. PIN_SPI0_MOSI,
PIN_SERIAL1_TX — not named SDA/SCL/SS/MOSI/MISO/SCK/TX/RX literally), so none of them are
picked up by the alias-based auto-append logic in the first place. No bug found; no #define
removal was necessary.
