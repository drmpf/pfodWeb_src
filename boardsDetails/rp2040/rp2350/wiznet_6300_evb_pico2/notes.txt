PER-PIN REASONING
------------------
- GPIO15 (INTn / PIO_IRQ_PIN): dedicated interrupt line asserted BY the W6300 to signal
  the RP2350 — not general purpose (driving it as output would contend with the chip).
  chipGpios capabilities set to [] (bare empty array, not an omitted key — see build_
  boards.js note above), note only. Confirmed by both WIZnet sources.
- GPIO16 (CSn / PIN_CS): dedicated SPI/QSPI chip-select output from the RP2350 to the
  W6300 — not general purpose. capabilities: []. NOTE: this board's inherited generic
  pins_arduino.h happens to alias GPIO16 as SPI0 MISO (PIN_SPI0_MISO=16u, a plain-Pico
  reference-design coincidence unrelated to this board's real wiring), which causes
  build_boards.js to unconditionally append a "spi_miso" capability tag regardless of
  the chipGpios override (see build_boards.js note above — this auto-append lives
  outside the chipGpios branch and cannot be suppressed without editing the shared
  generic/pins_arduino.h file, out of scope for a single-board audit since many other
  RP2350 boards depend on that file's SPI0 aliases unchanged). Documented explicitly in
  both the board.json comment block and each affected pin's "note" so the mismatch
  between the auto-tag label and the real function is traceable.
- GPIO17 (SCLK / PIO_SPI_SCK_PIN): dedicated QSPI clock output — not general purpose.
  capabilities: []. Same alias-collision gotcha as GPIO16: inherited generic file
  labels GPIO17 as SPI0 SS (PIN_SPI0_SS=17u), triggering an unavoidable auto-appended
  "spi_ss" tag that does not reflect the real SCLK function.
  Confirmed by both WIZnet sources.
- GPIO18 (MOSI/IO0 / PIO_SPI_DATA_IO0_PIN): dedicated QSPI data line — not general
  purpose. capabilities: []. Same gotcha: inherited generic file labels GPIO18 as SPI0
  SCK (PIN_SPI0_SCK=18u), triggering an unavoidable auto-appended "spi_sck" tag.
  Confirmed by both WIZnet sources.
- GPIO19 (MISO/IO1 / PIO_SPI_DATA_IO1_PIN): dedicated QSPI data line — not general
  purpose. capabilities: []. Same gotcha: inherited generic file labels GPIO19 as SPI0
  MOSI (PIN_SPI0_MOSI=19u), triggering an unavoidable auto-appended "spi_mosi" tag.
  Confirmed by both WIZnet sources.
- GPIO20 (IO2 / PIO_SPI_DATA_IO2_PIN): dedicated QSPI data line, only used in
  QSPI/Quad mode — not general purpose. capabilities: []. No alias collision (GPIO20
  has no SPI0/Wire0 role in the inherited generic file, only the plain D20 alias).
  Confirmed by both WIZnet sources.
- GPIO21 (IO3 / PIO_SPI_DATA_IO3_PIN): dedicated QSPI data line, only used in
  QSPI/Quad mode — not general purpose. capabilities: []. No alias collision.
  Confirmed by both WIZnet sources.
- GPIO22 (RSTn / PIN_RST): dedicated reset output from the RP2350 to the W6300 — not
  general purpose (toggling it outside the Ethernet driver would reset the chip
  mid-operation). capabilities: []. No alias collision. Confirmed by both WIZnet
  sources.
- GPIO24 (VBUS sense) and GPIO29 (VSYS/3 ADC3): confirmed by docs.wiznet.io as generic
  RP2350/Pico2 reference-design features, NOT part of the W6300 Ethernet interface, and
  already have no alias in the inherited generic pins_arduino.h chain (per common.h's
  own pfodWeb NOTE) — so they never appear as a pin in the Designer's list regardless.
  Out of scope for this Ethernet-focused audit (a chip-generic concern, not specific to
  this board); no chipGpios entry added, consistent with rpipico's board.json handling
  of the identical GPIO24/29 situation.
- GPIO25 (onboard user LED): DOES have no alias in the inherited generic file (see
  common.h note above) so without an explicit entry it would not appear as a pin at
  all. Confirmed as "Connected to user LED" via docs.wiznet.io. Tagged
  ["digital_output", "pwm_output", "led_high"], reusing this database's established
  rpipico precedent for the identical standard-Pico LED circuit (active-high assumed by
  convention — no explicit polarity statement found for this specific board, but no
  inverted-LED wiring documented anywhere either, and the vendor markets this board as
  working "basically the same as a Raspberry Pi Pico board" with Ethernet added).
  digital_input dropped to match the established led_high precedent for dedicated
  onboard LED pins; pwm_output kept since arduino-pico's analogWrite() works on any
  RP2040/RP2350 GPIO.
- No onboard push-button beyond BOOTSEL is documented anywhere consulted. BOOTSEL is
  not a GPIO-addressable pin on RP2040/RP2350 (arduino-pico exposes it only as a
  non-GPIO `BOOTSEL` boolean via a QSPI CS-line trick, same as every other board in this
  database) — out of scope, not a missed tag. No onboard NeoPixel is documented either.

SUMMARY
-------
Created variants/rp2040/rp2350/wiznet_6300_evb_pico2/board.json (full file, copied from
the chip-level variants/rp2040/rp2350/board.json defaults) adding nine chipGpios
overrides: GPIO15-22 (W6300 Ethernet chip INTn/CSn/SCLK/MOSI-IO0/MISO-IO1/IO2/IO3/RSTn,
all confirmed via docs.wiznet.io's own GPIO table and independently corroborated by
WIZnet's WIZnet-PICO-C firmware pin config) each set to capabilities: [] with a note
documenting their real function — including an explicit call-out of an unavoidable
build_boards.js alias-collision quirk that auto-tags GPIO16/17/18/19 with mismatched
spi_miso/spi_ss/spi_sck/spi_mosi labels inherited from the generic Pico SPI0 aliases,
which cannot be suppressed without editing the shared generic pins_arduino.h (out of
scope) — and GPIO25 (onboard user LED, previously unexposed since it has no alias in
the inherited generic file at all) tagged ["digital_output","pwm_output","led_high"],
active-high by the same Pico/Pico2 reference-design convention already applied to
rpipico's board.json. GPIO24/29 required no action (generic Pico2 VBUS/VSYS-sense
pins, not W6300-related, already alias-less and out of scope). No onboard button or
NeoPixel found in any consulted source.
