SUMMARY (one line)
-------------------
NO CHANGE — Pimoroni PGA2350 is a bare RP2350B "Pin Grid Array" breakout
module with no onboard LED, NeoPixel, button, or USB connector at all
(vendor-confirmed); board.json created with chip-level defaults verbatim
and an empty chipGpios (no tags to add). GPIO47 (onboard PSRAM chip-select)
and GPIO25/PIN_LED (generic fallback's Pico-shaped default) both
deliberately left out of chipGpios — neither is swept into the routable
pin set by build_boards.js (bare #define, no static-const alias), so
adding an entry for either would wrongly introduce a pin into the Designer
that isn't generated today.

3. variants/rp2040/rp2350/generic/common.h — declares PINS_COUNT=26,
   NUM_DIGITAL_PINS=26, `#define LED_BUILTIN PIN_LED` (plain macro, not
   static const), static-const D0-D22 + A0-A2 (26 pins total), and
   SS/MOSI/MISO/SCK/SDA/SCL aliased to the PIN_SPI0_*/PIN_WIRE0_* values
   (which all coincide with already-covered D-pins). Contains its own
   pfodWeb NOTE explaining GPIO23/24/25/29 are deliberately excluded
   because they assume a Raspberry-Pi-Pico-shaped reference design
   (SMPS control / VBUS sense / onboard LED / VSYS sense) — explicitly
   flagging that a board with a genuinely different pinout "should
   declare its own pins_arduino.h ... rather than relying on the blanket
   default." The PGA2350 does NOT do this (its pins_arduino.h just
   includes the generic fallback), so this fallback's 26-pin cap
   under-represents the real board's 48-GPIO breakout — a pre-existing
   scope-of-fallback limitation, out of scope for this audit (see below).

PER-PIN REASONING
------------------
- No onboard LED, NeoPixel, or button exists on this board at all.
  CONFIRMED directly from Pimoroni's own product page (source #1),
  corroborated by variants/rp2040/boards.txt's empty
  `pimoroni_pga2350.build.led=` entry. NO chipGpios entries added.

- GPIO47 (RP2350_PSRAM_CS) — onboard 8MB PSRAM chip-select. Confirmed
  via this board's own pins_arduino.h (`RP2350_PSRAM_CS 47`) and the
  vendor-documented "8MB of PSRAM" spec. Deliberately NOT given a
  chipGpios entry: it's a bare #define with no static-const alias
  anywhere in this board's pins_arduino.h or the generic fallback it
  includes, so build_boards.js does not sweep it into the routable pin
  set today. Adding a chipGpios["47"] entry (even with capabilities: [])
  would be counter-productive — chipGpios keys are unconditionally
  added to the routable-pin set, so it would introduce a previously-
  absent inert "GPIO47" pin into the Designer where none exists now.
  Matches the pimoroni_pico_plus_2/board.json precedent for the
  identical RP2350_PSRAM_CS situation.

- GPIO25 (PIN_LED, via the generic fallback) — NOT this board's own
  alias; inherited unconditionally from generic/pins_arduino.h regardless
  of whether the board has a real LED. Also NOT swept into the routable
  pin set (LED_BUILTIN is a plain #define macro in generic/common.h, not
  a static-const alias), so no board.json action is needed or possible.
  This is doubly correct for the PGA2350 since it has no LED at all.

- GPIO0-22, 26-28 (D0-D22, A0-A2 via the generic fallback's static-const
  aliases) — the only GPIOs actually in this board's routable pin set.
  These are genuine general-purpose pins on the real 48-GPIO PGA2350
  hardware. Left at chip-level default capabilities (digital_input/
  digital_output/pwm_output, no button/LED/NeoPixel tag) since none are
  confirmed dedicated/button/LED pins.

- Noted but NOT acted on (out of scope for this audit): the generic
  fallback's 26-pin cap (PINS_COUNT=26, matching a Pico-shaped reference
  design) significantly under-represents the real PGA2350's 48-GPIO
  breakout. Fixing this would require writing a genuinely custom
  pins_arduino.h for this board (bypassing the generic fallback), which
  is a separate, larger change outside this button/LED/NeoPixel-tagging
  + dedicated-hardware-pin-exclusion audit's scope. Flagged here for a
  future auditor.

- No SDA/SCL/SS/MOSI/MISO/SCK bus-collision bug applies: there is no
  confirmed button/LED/NeoPixel pin on this board at all, so
  build_boards.js's unconditional bus-alias auto-append cannot collide
  with anything here.
