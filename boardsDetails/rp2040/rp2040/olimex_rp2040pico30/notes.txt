SUMMARY
-------
NO CHANGE. No board.json was created. Olimex's RP2040-PICO30 is a
Pico-form-factor breakout that exposes all 30 RP2040 GPIOs (the stock
Raspberry Pi Pico only exposes 26; the missing 4 — GPIO23/24/25/29 — sit
on pads that are plain GND on the stock Pico). Confirmed directly from
Olimex's own schematic and user manual (both fetched and read in full,
see SOURCES) that:
  - GPIO25's onboard LED is NOT populated by default. The schematic shows
    LED1 (green 0603) and its series resistor R10 (2.2k) both marked
    "NA" (not assembled), and the dedicated "LED enable" solder jumper
    (net LED_E1) is drawn "Opened". Olimex's own order-code table
    confirms this is deliberate: only the "-U" SKU variant
    ("RP2040-PICO30U ... with UEXT, LED, R10, R15, R16") ships with the
    LED/R10 parts actually populated and the UEXT pull-ups (R15/R16)
    installed — the plain "RP2040-PICO30" SKU (the literal product name
    this single arduino-pico board ID/pins_arduino.h covers, for every
    SKU including -16 flash variants) ships without them. Since one
    board.json/pins_arduino.h serves all SKUs and the baseline/plain SKU
    has no working onboard LED, tagging GPIO25 as led_high would
    misrepresent the board as most customers receive it.
  - GPIO23, GPIO24, and GPIO29 (the other 3 of the "4 extra" GPIOs) have
    no onboard dedicated circuitry either — they are plain spare
    header-broken-out GPIOs. The manual's own "Table 1. Notable pins"
    and schematic "Important Notes" box both describe them only as pins
    that are GND on the ORIGINAL stock Pico footprint, with a caution to
    initialize them as INPUT if the board is ever plugged into
    Pico-designed carrier hardware/shields (to avoid driving current
    into what that carrier assumes is a ground pin). This is a
    physical-footprint-compatibility caution, not a description of any
    onboard peripheral wired to these pins on the PICO30 itself.
  - Two buttons exist (hardware layout diagram, page 5 of the manual,
    explicitly labels them): "Boot button" (BOOT1, wired GND <-> the
    QSPI_SS_N net — the standard ROM-bootloader-entry BOOTSEL line) and
    "RESET button" (RST1, wired GND <-> RUN — the standard hardware
    chip-reset line). Neither is a normal GPIO digitalRead() pin; both
    are out of scope per this audit's established BOOTSEL/RESET
    convention (see rpipico/board.json, waveshare_rp2040_pizero notes).
    No third/general-purpose user button exists anywhere.
  - No NeoPixel/WS2812/addressable LED anywhere on the schematic or in
    the manual's feature list.

Because there is no button, LED, or NeoPixel confirmed wired to any GPIO
that would need a chipGpios capability restriction or addition, and no
bus-alias collision was found (see BUG-CLASS CHECK below), there is
nothing for a per-board board.json to override. A board.json containing
only a byte-for-byte copy of the chip-level variants/rp2040/rp2040/
board.json defaults with an empty chipGpios:{} would be a functional
no-op, so — per this audit's own stated principle ("Report NO CHANGE
rather than guess") and the established rakwireless_rak11300 /
waveshare_rp2040_pizero precedent — none was created.

BUG-CLASS CHECK (button/LED aliased onto a bus pin)
-------------------------------------------------------
No button or working onboard LED exists on any GPIO in the first place
(the LED footprint is unpopulated/jumper-open by default), so there is
no button/LED pin to collide with a bus alias. Checked anyway: GPIO23,
24, 25, 29 (the four "extra" GPIOs) do not coincide with any of this
board's inherited bus aliases — PIN_SPI0_MISO/SS/SCK/MOSI = 16/17/18/19,
PIN_SPI1_MISO/SS/SCK/MOSI = 12/13/14/15, PIN_WIRE0_SDA/SCL = 4/5,
PIN_WIRE1_SDA/SCL = 26/27 — zero overlap with 23/24/25/29. The UEXT
connector's I2C signals (GPIO16=I2C0_SDA, GPIO17=I2C0_SCL per the
manual's pUEXT diagram) also don't collide: GPIO16/17 have no
static-const bus alias in pins_arduino.h (only GPIO4/5 and GPIO26/27 do),
so build_boards.js's auto-append-bus-capability logic never fires for
them. No pins_arduino.h edit was made — no `#define`/`static const`
lines were touched, so no dangling-reference risk.

PER-PIN REASONING
------------------
GPIO25 (PIN_LED / LED_BUILTIN, inherited from rpipico's
  pins_arduino.h): onboard LED footprint exists but is NOT populated and
  its enable jumper is NOT bridged on the plain SKU (confirmed via the
  official schematic: LED1 + R10 both "NA", jumper "Opened") — populated
  only on the "-U" SKU per the official user manual's order-code table.
  Since this board ID/board.json must serve all SKUs and the LED is not
  present out-of-the-box on the base product, left at the chip-level
  default full capability set (digital_input/digital_output/pwm_output)
  — same as every other spare GPIO. No chipGpios tag applied.

GPIO23, GPIO24, GPIO29: plain spare GPIOs exposed on header pads that are
  GND on the stock Raspberry Pi Pico footprint (confirmed via the
  official user manual's "Table 1. Notable pins" and the schematic's own
  "Important Notes" annotation) — no onboard dedicated circuitry. Left
  at the chip-level default full capability set. No chipGpios tag
  applied.

Boot button (BOOTSEL, on the QSPI_SS_N net): standard ROM-bootloader-
  entry button, not a normal GPIO digitalRead() pin. Out of scope per
  this audit's established convention (rpipico, waveshare_rp2040_pizero
  precedents).

RESET button (on the RUN net): standard hardware chip-reset line, not a
  GPIO. Out of scope, same convention as above.

No NeoPixel/WS2812 found anywhere in the schematic or user manual.

All remaining GPIOs (0-22, 26-28): standard header/UEXT/extension-
  connector pins per the inherited rpipico pins_arduino.h aliases; no
  dedicated onboard peripheral found for any of them beyond the
  already-declared Serial/SPI/Wire bus aliases. No chipGpios entry
  needed.

inputOnlyGpios / pinNotes / pwm / dac / adc: left at chip-level defaults
  (12-bit ADC, 8-bit analogWrite, no DAC) — this board declares no
  board-specific analog aliases beyond what rpipico's pins_arduino.h
  already provides (A0-A2 = GPIO26-28; GPIO29, one of the four "extra"
  GPIOs, has no A-alias in the inherited file, matching the stock Pico's
  own 3-analog-channel A0-A2 set — the manual does not describe any
  analog use for GPIO29 on this board either).

WHY NO board.json IS CREATED
------------------------------
Because (a) the onboard LED is not populated/enabled by default on the
product this board ID literally names ("RP2040-PICO30"), (b) GPIO23/24/29
have no onboard dedicated circuitry, (c) both buttons are non-GPIO
BOOTSEL/RESET lines already out of scope by established convention, and
(d) no NeoPixel exists, there is nothing this audit's button/LED/
NeoPixel-tagging or bus-collision mandate could correctly add via
chipGpios. A board.json holding only a verbatim copy of the chip-level
defaults with an empty chipGpios:{} would be a functional no-op (the
chip-level variants/rp2040/rp2040/board.json already supplies those same
defaults via fallback), so none was created — consistent with this
audit's "Report NO CHANGE rather than guess" principle and the
rakwireless_rak11300/waveshare_rp2040_pizero precedent from this same
session.
