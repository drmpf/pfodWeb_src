DIFF FINDING (key result of this audit)
-----------------------------------------
`diff` between variants/rp2040/rp2040/amken_revelop/pins_arduino.h and
variants/rp2040/rp2040/amken_revelop_plus/pins_arduino.h shows the two
files are BYTE-FOR-BYTE IDENTICAL (all 80 lines, including both
pre-existing pfodWeb NOTE comments at lines 40 and 75-77). Despite the
"Plus" name implying an expanded/richer board relative to plain
"Revelop", the Arduino-pico board-support source declares no additional
dedicated hardware, no additional bus, and no additional pin role
whatsoever versus the plain Revelop variant. Any physical differences
the real "Revelop Plus" board has over "Revelop" (extra connectors,
stepper-driver sockets, additional power stages, etc., if any) are
evidently not reflected in this Arduino core variant's GPIO-level pin
map — either because both variants share the same MCU pinout, or because
the "Plus" board's actual differentiating hardware is wired outside this
Arduino-core variant's scope (e.g. a separate Marlin/Klipper board config
not present in the arduino-pico repo, matching the same limitation noted
for amken_bunny's stepper/heater/endstop wiring).

PER-PIN REASONING
------------------
GPIO0 (PIN_SERIAL1_TX, D0): general Serial1 TX. No board-specific role
  comment. KEPT general-purpose.

GPIO1 (PIN_SERIAL1_RX, D1): general Serial1 RX. Same reasoning. KEPT
  general-purpose.

GPIO2, GPIO3 (D2, D3): no PIN_ macro, no comment, no known role. KEPT
  general-purpose.

GPIO4 (PIN_SERIAL2_TX): vendor's own comment "// TMC UART" directly
  above `#define PIN_SERIAL2_TX (4u)` confirms this is the UART TX line
  to an onboard TMC stepper-driver chip — dedicated, not general
  purpose. Already correctly excluded from the Designer's routable pin
  list by omission: this file's own D-alias list skips D4 and D5
  entirely, and its own pre-existing "pfodWeb NOTE" comment documents
  this. No chipGpios override needed; nothing broken to fix (same
  reasoning as amken_bunny GPIO4).

GPIO5 (PIN_SERIAL2_RX): TMC UART RX, same reasoning and same
  already-correct exclusion as GPIO4.

GPIO6-GPIO23, GPIO25-GPIO29 (D6-D23, D25-D29 / A0-A3 = GPIO26-29): no
  PIN_ macro, no board-specific comment identifying any of these as a
  STEP/DIR/EN/thermistor/heater/endstop/fan line, and (per the DIFF
  FINDING above) byte-identical to amken_revelop's own undifferentiated
  block. No external documentation (vendor site, GitHub PR/commit,
  PlatformIO JSON descriptor, general web search) maps any of these
  GPIOs to a specific onboard stepper driver, heater MOSFET, thermistor
  divider, endstop, or fan connector on the physical Revelop Plus board.
  Per this audit's rule to report NO CHANGE rather than guess, all of
  these pins are LEFT at full chip-default derived capabilities
  (digital_input/digital_output/pwm_output, plus analog_input on
  GPIO26-29 from the A0-A3 aliases) — exactly as they already build
  today via the chip-level empty chipGpios{} fallback.

GPIO24 (PIN_LED, D24): vendor's own comment "// LEDs" directly above
  `#define PIN_LED (24u)` confirms an onboard LED genuinely exists at
  this pin — vendor-authored labeling, not a guess from the alias name
  alone (identical comment/macro to amken_bunny and amken_revelop). The
  LED's drive polarity (active-high vs active-low) is NOT documented
  anywhere found: no datasheet, no schematic, no product page ("Revelop
  Plus" is absent from the current amken3d.com/amken.us lineup), no
  forum/review discussion, and no independent source turned up any
  authoritative confirmation either way. Per this audit's explicit rule
  ("if you cannot find authoritative vendor documentation, report NO
  CHANGE rather than guess at polarity from the alias name alone"),
  GPIO24 is NOT tagged led_high/led_low. It is left at its full
  chip-default derived capabilities (digital_input/digital_output/
  pwm_output) — the pin remains fully usable as a generic digital output
  for anyone wanting to drive the LED experimentally, it simply is not
  given an LED-specific on/off semantic in the Designer UI.

No button of any kind: no button/capacitive-touch alias is declared in
  pins_arduino.h, and no source consulted documents a physical button on
  this board beyond the RP2040's own BOOTSEL, which (per the established
  rpipico/board.json precedent) is wired to the QSPI flash chip-select
  line and read via a special SDK trick, not a normal GPIO
  digitalRead() — out of scope for this repo's GPIO-keyed capability
  tagging. No button tagging applied.

No NeoPixel: no PIN_NEOPIXEL/NUM_NEOPIXEL alias is declared anywhere in
  this file (contrast with sibling amken_revelop_es, which does declare
  one). No NeoPixel tagging applied.

BUS-COLLISION CHECK (SDA/SCL/SS/MOSI/MISO/SCK auto-append bug class)
----------------------------------------------------------------------
This board's PIN_SPI0_* and PIN_SPI1_* are ALL sentineled to (31u) —
GPIO31 does not physically exist on RP2040 (valid range is GPIO0-29) —
and, per this file's own pre-existing second "pfodWeb NOTE" comment,
none of SS/MOSI/MISO/SCK are declared as `static const` aliases at all
(avoiding a phantom "GPIO31" pin in the Designer). The only real bus
pins on this board are Wire0 SDA=GPIO28/SCL=GPIO29, which carry no
LED/button role and are not aliased to any other dedicated hardware —
GPIO24 (the LED) and GPIO4/5 (TMC UART) are entirely separate GPIOs from
GPIO28/29. No SDA/SCL/SS/MOSI/MISO/SCK collision found, no fix needed.
