Directory: variants/rp2040/rp2040/challenger_2040_lte/
Audit date: 2026-07-13

SUMMARY
-------
Confirmed the onboard u-blox SARA-R410M LTE-M/NB-IoT cellular modem
occupies GPIO4,5,6,7 (UART1 TX/RX/CTS/RTS) and GPIO13,14,15 (power-on,
reset, and LDO-power-enable control lines). Found these seven pins were
ALREADY fully excluded from the Designer's pin list by a prior-session
edit to this board's pins_arduino.h (no static const uint8_t alias
declared for any of them) - so no board.json chipGpios entries were
needed or added for the modem pins themselves (see "WHY NO chipGpios
ENTRIES..." reasoning below - adding them would have been
counterproductive, per independently-verified build_boards.js behavior).
Created board.json (this board previously had none) containing a single
chipGpios entry: GPIO19, tagged as the onboard general-purpose LED
(active-high, cross-referenced inference). No onboard NeoPixel or user
button found. pins_arduino.h was NOT modified this session (already
correct - GPIO20/SPI0 MISO gap flagged but left alone, out of scope).

WHY NO chipGpios ENTRIES FOR THE MODEM PINS (GPIO4,5,6,7,13,14,15)
--------------------------------------------------------------------
build_boards.js's buildEsp32Board() (the parser the "rp2040" family
routes through) only lists a GPIO in the Designer's pin picker if it
appears either (a) as a `static const uint8_t` alias in pins_arduino.h,
or (b) as a key in this board's chipGpios object:
  `const allGpios = new Set(aliasesByGpio.keys());
   for (const key of Object.keys(chipGpiosMap)) { ... allGpios.add(n); }`
  (build_boards.js ~line 535-539)

Since this board's pins_arduino.h already declares NO `static const
uint8_t` alias resolving to GPIO4, 5, 6, 7, 13, 14, or 15 (see source #5
above), those seven GPIOs are already 100% absent from the Designer's
pin list with zero board.json involvement. Adding chipGpios entries for
them here would have been COUNTERPRODUCTIVE: build_boards.js
unconditionally appends a "Check if available on board" note to ANY
rp2040-family GPIO absent from pins_arduino.h, regardless of whether a
chipGpios entry (with its own custom note) exists for it:
  `if (!inPinsH && cfg.family !== 'esp32' && cfg.family !== 'esp8266')
     noteParts.push('Check if available on board');`
  (build_boards.js ~line 718, confirmed by direct read this session -
  fires unconditionally on the inPinsH flag, NOT gated on chipGpios
  presence)
Adding entries here would re-add each pin to allGpios as a bare, visible
"GPIO<n>" row carrying that redundant/misleading note alongside the real
explanation - undoing the full concealment the pins_arduino.h omission
already achieves, and misleadingly suggesting the pin's availability is
merely unverified rather than physically dedicated to the LTE modem.

FLAGGED INCONSISTENCY (not fixed, out of scope): the earlier
challenger_2040_wifi and challenger_2040_nfc sibling audits this session
DID add chipGpios entries for some of their own unaliased dedicated
pins (e.g. wifi's GPIO4/5/13/19 and nfc's GPIO9/10/11/12/14), which by
the same build_boards.js mechanism traced above would actually surface
those pins in the Designer with a "Check if available on board" note
attached - the opposite of full concealment. This appears to be an
inconsistency between those two earlier audits and the later lora/
subghz audits' (and this audit's) more carefully-traced reasoning about
build_boards.js's actual runtime behavior, not a deliberate alternative
approach. This audit follows the lora/subghz reasoning (independently
re-verified by reading build_boards.js directly, not just trusting the
prior notes.txt). No changes were made to the wifi/nfc boards - fixing
them is out of scope for this task, which is scoped to challenger_2040_lte
only.

PER-PIN REASONING
------------------
GPIO4 (PIN_SERIAL2_TX): SARA-R410M modem's dedicated UART1 TX line
  ("GPIO4 acts as UART1 TXD" per the official datasheet). Not
  general-purpose. No pins_arduino.h alias exists for this GPIO;
  already fully absent from the Designer pin list. No board.json entry
  needed or added.

GPIO5 (PIN_SERIAL2_RX): SARA-R410M modem's dedicated UART1 RX line
  ("GPIO5 acts as UART1 RXD"). Same reasoning as GPIO4.

GPIO6 (PIN_SERIAL2_CTS): SARA-R410M modem's UART1 hardware flow-control
  CTS line ("GPIO6 acts as UART1 CTS"). Same reasoning as GPIO4.

GPIO7 (PIN_SERIAL2_RTS): SARA-R410M modem's UART1 hardware flow-control
  RTS line ("GPIO7 acts as UART1 RTS"). Same reasoning as GPIO4.

GPIO13 (PIN_SARA_ON): SARA-R410M modem's power-on control line, driven
  by the RP2040 ("GPIO13 is connected the power on signal of the SARA
  R410M module"). Not general-purpose. Same reasoning as GPIO4.

GPIO14 (PIN_SARA_RST): SARA-R410M modem's reset control line, driven by
  the RP2040 ("GPIO14 is connected to the reset signal of the SARA
  R410M module"). Same reasoning as GPIO4.

GPIO15 (PIN_SARA_PWR): SARA-R410M modem's power-supply LDO enable line,
  driven by the RP2040 ("GPIO15 is connected to the LDO that supplies
  the modem with power"). Same reasoning as GPIO4.

GPIO19 (PIN_LED / LED_BUILTIN, D17 alias): tagged in the new board.json
  chipGpios with ["digital_output", "pwm_output", "led_high"]. Presence
  and GPIO number confirmed by cross-referencing the official iLabs
  datasheet's "pin D15" (iLabs' own silkscreen numbering) against
  CircuitPython's independent board.LED=GPIO19 definition, which
  matches this board's own PIN_LED=(19u) exactly - two independent
  sources agree on GPIO19. Active-high polarity is a cross-referenced
  inference (no schematic or datasheet text was found that states the
  polarity explicitly for this specific board's LED), based on: (a) the
  sibling challenger_2040_wifi board's own datasheet explicitly stating
  "Active level: High" for the identical shared reference LED circuit
  (GPIO -> resistor -> LED -> GND) reused across this iLabs product
  line, and (b) every other RP2040 board audited in this repo's family
  to date (rpipico, wiznet_5500_evb_pico, adafruit_feather_scorpio,
  challenger_2040_lora, challenger_2040_wifi, challenger_2040_nfc,
  challenger_2040_subghz) being confirmed or cross-reference-inferred
  active-high, none active-low. digital_input capability dropped to
  match this repo's established led_high precedent for dedicated
  onboard LED pins; pwm_output kept since arduino-pico's analogWrite()
  works on any RP2040 GPIO.

No onboard NeoPixel found - confirmed absent by the iLabs datasheet, the
  upstream arduino-pico pins_arduino.h (no NEOPIXEL/PIN_NEOPIXEL
  define), and the CircuitPython pins.c (no board.NEOPIXEL). No
  chipGpios tag applied.

No onboard user button found - confirmed absent by the iLabs datasheet
  (no pushbutton mentioned beyond standard reset/BOOTSEL, which is not
  a normal GPIO on RP2040, out of scope per the rpipico/board.json
  precedent) and the CircuitPython pins.c (no board.BUTTON). No
  chipGpios tag applied.

GPIO19 carries no SPI/I2C/other bus alias on this board (SPI0 lives on
  GPIO20-23, Wire0 on GPIO0-1), so the build_boards.js unconditional
  bus-capability auto-append (the "confirmed button/LED pin also
  aliased as SDA/SCL/SS/MOSI/MISO/SCK" bug class flagged for this
  audit) does not apply here - no pins_arduino.h edit was needed.
