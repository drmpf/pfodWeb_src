"ArtronShop RP2 Nano" — ArtronShop Co.,Ltd. (Thailand, www.artronshop.co.th)
Audit date: 2026-07-13

SUMMARY
-------
One change applied: added variants/rp2040/rp2040/artronshop_rp2_nano/board.json
tagging GPIO13 (PIN_LED) as the onboard LED (digital_output, pwm_output,
led_high). No other onboard button/LED/NeoPixel GPIOs found. No pins_arduino.h
edit was needed/made (the GPIO13/PIN_SPI1_SS collision is a genuine,
vendor-documented dual-purpose header pin, not a spare/unused alias — see

PER-PIN FINDINGS
-----------------
GPIO0 (PIN_SERIAL1_TX) — official pinout diagram labels this D0/"TX1"
  only (Serial/UART colour). No button/LED association anywhere. Not
  the BOOT button (see below). NO CHANGE.

GPIO13 (PIN_LED) — schematic shows LED1 (part "19-213/Y2C-CQ2R2L/3T(CY)")
  wired RP2040 GPIO13 -> R8 (330 ohm series resistor) -> LED1 -> GND:
  a standard active-high LED-to-GND circuit (GPIO driven HIGH lights the
  LED). This matches PIN_LED=13 in pins_arduino.h exactly.
  This same GPIO13 is also broken out to the Nano header as pin D13,
  labelled "CS" in the SPI colour category on ArtronShop's own official
  pinout diagram — i.e. it is simultaneously PIN_SPI1_SS (and the
  global "SS" alias). The full SPI1 bus is genuinely broken out to the
  header: D10=SCK, D11=MOSI, D12=MISO, D13=CS, all labelled/coloured as
  SPI pins on the vendor's own diagram — this is not a spare/unused
  bus, so (unlike adafruit_feather_scorpio's PIN_SPI0_SS) the
  PIN_SPI1_SS #define was left untouched in pins_arduino.h. This
  mirrors the classic Arduino Uno/Nano tradition of D13 doing double
  duty as both the onboard LED and an SPI signal (SCK there, SS/CS
  here) — a deliberate, vendor-documented design choice, not a defect.
  Applied: chipGpios["13"] = {"digital_output","pwm_output","led_high"}
  (digital_input dropped per this repo's established led_high
  precedent for dedicated onboard LED pins; pwm_output kept since
  arduino-pico's analogWrite() works on any RP2040 GPIO).

BOOT button (SW1, schematic) — wired via a 1K pull-up resistor (R10)
  across the QSPI flash chip-select net (schematic label "FLASH_SS",
  RP2040 pin 56 / QSPI_SS, shared with the external ZD25WQ16 SPI flash
  chip's CS# pin) — the same resistor value and circuit topology as the
  official Raspberry Pi Pico's BOOTSEL button. This is NOT a numbered
  GPIO; it is the same QSPI_SS-based BOOTSEL mechanism documented in
  this repo's rpipico/board.json note ("not connected to a standard
  GPIO, so it cannot be read using the usual digitalRead function").
  Out of scope for this repo's GPIO-keyed capability tagging — not a
  missed tag. Consistent with the pinout diagram showing no button
  annotation on any GPIO.

RESET button (SW2, schematic) — wired directly across the RP2040's RUN
  pin (pin 26) to GND, with a 10K pull-up resistor (R1) to +3V3 and a
  100nF debounce capacitor (C1) — the standard external reset circuit
  present on virtually every RP2040 board. RUN is not a GPIO-numbered
  pin. Out of scope.

NeoPixel / addressable RGB LED — none present. Confirmed absent from
  both the schematic (only the single plain LED1 described above) and
  the CNX Software feature summary, which lists no RGB/NeoPixel
  feature for this board.

Grove I2C connector (CN17, schematic) — a 4-pin external I2C Grove
  header wired to SDA/SCL/+3V3/GND (SDA=GPIO16, SCL=GPIO17, matching
  PIN_WIRE0_SDA/SCL already declared in pins_arduino.h). Not an onboard
  peripheral needing its own capability tag — SDA/SCL already receive
  the standard I2C bus capability via build_boards.js's normal alias
  handling.

RESULT
------
board.json created: chipGpios["13"] tags the onboard LED (led_high).
No pins_arduino.h changes (the GPIO13/SS collision is genuine/intended,
confirmed via official vendor schematic + pinout diagram, not a
spare-bus contamination bug). No other button/LED/NeoPixel pins found.
JSON validity confirmed via plain JSON.parse() after manually stripping
"//" line comments (no build_boards.js invocation, per instructions).
