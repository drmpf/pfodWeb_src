2. https://github.com/melopero/Melopero_Cookie_RP2040_Arduino_Library
   (fetched repo listing + raw source file
   src/Melopero_Cookie_RP2040.cpp) — actual pico-sdk-based C++ source:
     ledInit()   -> pinMode(21, OUTPUT)
     ledOn()     -> digitalWrite(21, HIGH)   -- CONFIRMS LED is active-high
     ledOff()    -> digitalWrite(21, LOW)
     ledToggle() -> toggles the pin 21 output state
     buttonsInit() -> gpio_init(BUTTON_A); gpio_set_dir(BUTTON_A, GPIO_IN);
                      gpio_init(BUTTON_B); gpio_set_dir(BUTTON_B, GPIO_IN);
       (no gpio_pull_up()/gpio_pull_down()/gpio_disable_pulls() call
       anywhere in this function — pad pull state is left at whatever the
       RP2040 pad reset default is, which per the RP2040 datasheet is
       pull-down enabled on GPIO pads out of reset)
     readButton(button) -> return gpio_get(button);  (raw pin level, no
       inversion/debounce applied in the library itself)
3. https://raw.githubusercontent.com/melopero/Melopero_Cookie_RP2040/master/MicroPython/examples/main_example.py
   (official MicroPython demo code shipped in Melopero's own software pack)
   — contains `if cookie.read_button(BUTTON_A): cookie.clear_screen(...)`,
   i.e. the demo treats a True/HIGH read as "button is pressed". This CLOSES
   THE LOOP left open by source #2 (which showed the buttons are read raw
   with no pull configured, but didn't by itself state which level means
   "pressed"): HIGH = pressed = active-high, consistent with the button
   switching to 3V3 when pressed and being held LOW by the RP2040's default
   pull-down the rest of the time.
4. https://github.com/melopero/Melopero_Cookie_RP2040 (fetched repo +
   MicroPython/src directory listing) — cross-checked that the C-level
   MicroPython binding (cookie_rp2040.cpp) reuses the same underlying

Per-pin reasoning:

GPIO10 (Button A):
  Onboard pushbutton, active-high (reads HIGH when pressed).
  capabilities: ["digital_input", "digital_output", "pwm_output", "button"]
  Confirmed by source #1 (hardware-overview photo caption "Button A (GPIO
  10)") and sources #2+#3 (library source shows plain GPIO_IN with no pull
  configured; official example code treats a HIGH/True read as "pressed").
  Full digital_input/digital_output/pwm_output capability retained — this is
  an ordinary GPIO wired to a switch to 3V3, not a dedicated/capacitive-only
  pin, matching this repo's vccgnd_yd_rp2040 PIN_USRKEY and
  adafruit_feather_scorpio PIN_BUTTON precedents (both keep the full
  capability set on ordinary pushbutton GPIOs).
  No bus-alias collision: GPIO10 does not appear in this board's SPI0/SPI1/
  Wire0/Wire1/Serial1 alias list, so no build_boards.js bus-capability
  auto-append applies.

GPIO11 (Button B):
  Same confirmation, reasoning, and capability set as GPIO10/Button A above
  (source #1's "Button B (GPIO 11)" caption; sources #2+#3's shared
  buttonsInit()/readButton() code path and example interpretation).
  No bus-alias collision (GPIO11 is not aliased to any SPI/Wire/Serial pin
  on this board either).

GPIO16 (NEOPIXEL / Qwiic POWER):
  NO CHANGE — left at the chip-level default full general-purpose capability
  set (no chipGpios override).
  Reasoning: source #1's official pinout table documents this pin as a
  power-enable line for the Qwiic connector and NeoPixel matrix supply rail
  ("by default power is enabled (LOW). Set pin GPIO 16 to HIGH to disable
  it"), but it is still an ordinary bidirectional GPIO from the RP2040's
  point of view — the vendor's own Arduino/MicroPython libraries expose no
  dedicated accessor function for it at all (no powerEnable()/powerDisable()
  found in source #2's library), meaning application code would simply
  pinMode(16, OUTPUT)/digitalWrite(16, ...) it like any other digital_output
  pin if it wanted to manage the power rail. This is not a fixed/dedicated
  LED, button, or NeoPixel-data pin, so no capability override or special
  tag applies, consistent with this audit's treatment of similar
  vendor-documented-but-still-general-purpose pins (e.g.
  adafruit_feather_scorpio's GPIO16-23 NEOPIXEL0-7 header, left untagged
  despite documented NeoPixel-adjacent naming).
  No bus-alias collision: GPIO16 does not appear in this board's SPI0/SPI1/
  Wire0/Wire1/Serial1 alias list either.

GPIO17 (NeoPixel Matrix data line):
  Onboard 5x5 (25-pixel) WS2812 addressable RGB matrix display, output-only
  data line, row-major pixel wiring starting at this pin.
  capabilities: ["digital_output", "led_neopixel"]
  Confirmed by source #1 (hardware-overview "Neopixel Matrix (GPIO 17)"
  caption, and section 1.1's dedicated matrix diagram/description naming
  GPIO17 as the access pin for the full 5x5 display).
  digital_input/pwm_output omitted, matching this repo's established
  NeoPixel-tagging vocabulary (vccgnd_yd_rp2040 GPIO23, adafruit_feather_
  scorpio GPIO4, waveshare_rp2040_zero GPIO16 precedents) — pwm_output is
  not meaningful for a bit-serial/PIO-driven WS2812 data line.
  No bus-alias collision: GPIO17 does not appear in this board's SPI0/SPI1/
  Wire0/Wire1/Serial1 alias list.

GPIO21 (PIN_LED / User LED):
  Onboard single green status LED, active-high.
  capabilities: ["digital_output", "pwm_output", "led_high"]
  Confirmed independently by source #1 (hardware-overview bullet "Green
  user LED on pin 21") and source #2 (library source's ledOn()/ledOff()
  functions call digitalWrite(21, HIGH) / digitalWrite(21, LOW)
  respectively — an unambiguous, code-level active-high confirmation).
  digital_input dropped to match this repo's established led_high precedent
  for dedicated onboard LED pins (rpipico, wiznet_5500_evb_pico,
  vccgnd_yd_rp2040, adafruit_feather_scorpio); pwm_output kept since
  arduino-pico's analogWrite() works on any RP2040 GPIO, enabling brightness
  dimming.
  Bus-alias collision check (per this audit's known "confirmed pin also
  aliased to a bus role" bug class, see adafruit_feather_scorpio precedent):
  this board's pins_arduino.h declares SPI0 (MISO 20u/MOSI 19u/SCK 18u/
  SS 1u), SPI1 (MISO 28u/MOSI 27u/SCK 26u/SS 29u), and Wire0/Wire1
  (SDA 12u/SCL 13u, SDA 2u/SCL 3u) — none of these values is 21, and this
  board's pins_arduino.h includes ../generic_full/common.h (not the plain
  ../generic/common.h), which was also checked and does not declare any
  additional bus role on GPIO21. CONCLUSION: no collision exists; GPIO21 is
  not aliased to any SPI/I2C bus role, so no pins_arduino.h edit was needed
  (unlike the adafruit_feather_scorpio GPIO13/PIN_SPI0_SS precedent that
  prompted this check).

Summary: Confirmed and tagged all four identity pins found in this board's
official documentation and library source (Button A GPIO10 active-high,
Button B GPIO11 active-high, NeoPixel 5x5 matrix data GPIO17 output-only,
user LED GPIO21 active-high) via Melopero's own official "Getting started"
PDF guide (hardware-overview page + pinout diagram) cross-referenced against
the Arduino library's actual pico-sdk source code (ledOn/ledOff digitalWrite
calls, buttonsInit/readButton gpio_* calls) and the official MicroPython
example's button-press interpretation. Explicitly identified but left GPIO16
(NeoPixel/Qwiic power-enable line) UNCHANGED as general-purpose GPIO, since
it has no dedicated library accessor despite being vendor-documented as a
power-control pin. No bus-alias collision found on GPIO21 or any other
tagged pin, so no pins_arduino.h edit was required for this board.
