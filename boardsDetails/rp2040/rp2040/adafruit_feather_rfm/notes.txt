Board: adafruit_feather_rfm ("Adafruit Feather RP2040 RFM", RFM95/LoRa
sibling product 5714 and RFM69/900MHz-packet sibling product 5712 — both
share the identical pinout) — chip family: rp2040
Audit date: 2026-07-13 (RP2040/RP2350 family button/LED/NeoPixel audit)

pins_arduino.h identity pins (as found, before this session's edit):
  #define PIN_LED        (13u)
  #define PIN_NEOPIXEL   (4u)

Per-pin reasoning:

GPIO4 (PIN_NEOPIXEL):
  Onboard single status WS2812 NeoPixel, output-only data line,
  active-high.
  capabilities: ["digital_output", "led_neopixel"]
  Confirmed by sources #1, #3, #4 above (all three independently name
  GPIO4 as the status NeoPixel; source #4's Zephyr devicetree confirms
  GPIO_ACTIVE_HIGH). digital_input/pwm_output omitted, matching this
  repo's established NeoPixel-tagging vocabulary (adafruit_feather_
  scorpio GPIO4, vccgnd_yd_rp2040 GPIO23 precedent) — pwm_output is not
  meaningful for a WS2812 data line (PIO/bit-banged timing, not
  analogWrite()).

GPIO7 (PIN_BUTTON / BOOT):
  Onboard bootloader-select pushbutton, also documented by Adafruit as
  usable as a general digital input when application code is running
  (same role/wording as the sibling adafruit_feather_scorpio board).
  Active-low, RP2040 internal pull-up enabled (GPIO_PULL_UP flag in the
  Zephyr devicetree; no external pull-up on this line).
  capabilities: ["digital_input", "digital_output", "pwm_output", "button"]
  Full GPIO capability retained (not marked input-only) — ordinary GPIO
  wired to a switch to GND, not a dedicated/capacitive-only pin. Matches
  this repo's adafruit_feather_scorpio/vccgnd_yd_rp2040 PIN_BUTTON/
  PIN_USRKEY precedent.

GPIO13 (PIN_LED, also PIN_SPI0_SS):
  Onboard status LED, active-high (confirmed independently by source #4,
  the Zephyr devicetree's GPIO_ACTIVE_HIGH flag — Adafruit's own guide
  describes control method (board.LED / PIN_LED) but does not state
  polarity in text, so the Zephyr source supplied the deciding
  confirmation, same pattern as the adafruit_feather_scorpio audit).
  capabilities: ["digital_output", "pwm_output", "led_high"]
  digital_input dropped to match this repo's established led_high
  precedent for dedicated onboard LED pins (rpipico, adafruit_feather_
  scorpio, challenger_2040_lora); pwm_output kept since arduino-pico's
  analogWrite() works on any RP2040 GPIO, enabling brightness dimming.

  BUG FOUND AND FIXED: this GPIO was ALSO the vendor's default
  PIN_SPI0_SS (13u) in the as-found pins_arduino.h — an exact instance
  of the "confirmed button/LED pin also aliased as a bus-role pin"
  contamination class documented for this audit (build_boards.js's
  buildEsp32Board() unconditionally does `if (g === ss) caps.push
  ('spi_ss')` regardless of any chipGpios override). No onboard SPI
  device actually uses GPIO13 as a chip-select — the RFM radio's own
  chip-select is the separate, dedicated GPIO16 (PIN_RFM_CS), confirmed
  by sources #1/#2/#3/#4 above. Fixed 2026-07-13 in
  variants/rp2040/rp2040/adafruit_feather_rfm/pins_arduino.h by removing
  the `#define PIN_SPI0_SS (13u)` line. Also removed the dependent
  `static const uint8_t SS = PIN_SPI0_SS;` alias line in the same file
  (this board's pins_arduino.h is self-contained and does NOT include
  ../generic_full/common.h the way adafruit_feather_scorpio's does, so
  leaving that alias in place after removing the #define would have left
  a dangling reference to an undefined macro — removing both lines keeps
  the file internally consistent while matching the scorpio precedent's
  intent). MISO/MOSI/SCK (GPIO8/15/14) were left unchanged — these are
  the board's genuine shared SPI bus, used by both the onboard RFM radio
  and the board's standard header SPI pins, not a spurious/unused
  default like SS was.

GPIO16-23 (PIN_RFM_CS/RST/DIO0-DIO5, RFM radio module):
  NO chipGpios entries added — CONFIRMED already fully excluded by a
  prior session's pins_arduino.h edit (no D-numbered alias exists for
  any of GPIO16-23; only the PIN_RFM_* macros reference these numbers).
  This audit's research (sources #1-#4) independently confirms all
  eight GPIOs are genuinely dedicated to the onboard RFM radio module
  (CS, RESET, and six DIO interrupt lines) with no general-purpose or
  header-exposed role. Per this repo's challenger_2040_lora precedent
  (identical reasoning, same class of onboard SPI radio module): since
  build_boards.js's buildEsp32Board() only lists a GPIO in the Designer's
  pin picker if it has a pins_arduino.h alias OR a chipGpios key, and
  these GPIOs already have neither, they are already 100% absent from
  the Designer's pin list. Adding chipGpios entries for them here would
  be COUNTERPRODUCTIVE — it would re-add each one to the pin list as a
  bare "GPIO<n>" row carrying an auto-appended "Check if available on
  board" note, undoing the existing concealment and misleadingly
  suggesting the pin's availability is merely unverified rather than
  physically dedicated to the RFM radio.

Result: board.json created at
  variants/rp2040/rp2040/adafruit_feather_rfm/board.json
with chipGpios overrides for GPIO4 (status NeoPixel, output-only,
active-high), GPIO7 (BOOT button, active-low + internal pull-up, full
GPIO + button tag), and GPIO13 (status LED, active-high, PIN_SPI0_SS
collision fixed in pins_arduino.h). GPIO16-23 (RFM radio module CS/
RST/DIO0-5) received NO chipGpios entries — confirmed already fully
excluded via the pre-existing pins_arduino.h alias omission, matching
the challenger_2040_lora precedent. pins_arduino.h was edited to remove
the colliding `#define PIN_SPI0_SS (13u)` and its dependent
`static const uint8_t SS = PIN_SPI0_SS;` alias (GPIO13 is the confirmed
LED, not a real SPI SS pin; the RFM radio's actual CS is the separate
dedicated GPIO16). No other pins on this board carry dedicated onboard
hardware requiring exclusion; MISO/MOSI/SCK (GPIO8/14/15) are the
genuine shared RFM+header SPI bus and were left unchanged.

Verification: board.json's JSON validity confirmed by manually stripping
`//` comments (protecting `https://` substrings first) and running
JSON.parse() in node -e (no build_boards.js require, no build run), per
task instructions. Result: VALID JSON, chipGpios keys ["4","7","13"] as
intended.

Summary: Confirmed and tagged all three identity pins (status NeoPixel
GPIO4, BOOT button GPIO7 active-low, status LED GPIO13 active-high) via
Adafruit's own official learn.adafruit.com guides cross-referenced with
CircuitPython's pins.c and the upstream Zephyr RTOS board port's
devicetree (which supplied the deciding GPIO_ACTIVE_HIGH/GPIO_ACTIVE_LOW/

Confirmed and left GPIO16-23 with NO chipGpios entries (already excluded
via pins_arduino.h from a prior session, independently re-verified
correct here). Found and fixed one genuine instance of this audit's
flagged "button/LED pin also aliased as a bus pin" bug class: GPIO13
(LED) doubled as the vendor's default (unused) PIN_SPI0_SS — fixed by
removing that alias (and its now-dangling SS static-const dependent)
from pins_arduino.h, matching the adafruit_feather_scorpio precedent.
