Directory: variants\rp2040\rp2040\cytron_maker_pi_rp2040\
Audit date: 2026-07-13 (RP2040/RP2350 family button/LED/NeoPixel + dedicated-hardware
pin-exclusion audit, continuing the wave that already covered ESP32/ESP8266 and the
Cytron Maker Nano/Uno RP2040 siblings on 2026-07-12).

PINS DECLARED IN THIS BOARD'S pins_arduino.h
  PIN_LED             = 3   (bespoke file, no shared common.h include)
  PIN_NEOPIXEL        = 18  (NUM_NEOPIXEL = 2, PIN_RGB alias of PIN_NEOPIXEL)
  PIN_BUZZER          = 22
  PIN_M1A = 8, PIN_M1B = 9, PIN_M2A = 10, PIN_M2B = 11   (2-channel DC motor H-bridge)
  PIN_VBATT = PIN_VOLTAGE_MONITOR = 29 (= A3)
  Serial1 GPIO0/1, Serial2 GPIO4/5
  SPI0: all "not pinned out" (31u sentinel)
  SPI1: MISO=11, MOSI=12, SCK=10, SS=15  (see SPI1 COLLISION section below)
  Wire0: SDA=16, SCL=17.  Wire1: SDA=2, SCL=3.
  D0-D29 declared directly (no GPIO23/24/25 excluded — full 0-29 range), A0-A3 =
  GPIO26-29. No PIN_BUTTON alias declared anywhere, despite the real board having
  two GPIO-connected user pushbuttons (GPIO20/GPIO21) — confirmed independently
  below; this board's own header simply never gives them a named #define.

WHY AN OVERRIDE IS NEEDED
../board.json (chip-level rp2040 default) has chipGpios: {} deliberately empty —
per that file's own comment, every aliased GPIO in a board's pins_arduino.h gets
the full digital_input/digital_output/pwm_output capability set by default.
Without a per-board override, GPIO18 (NeoPixel) would be wrongly offered as a
plain bidirectional GPIO, and GPIO20/GPIO21 (buttons) would carry no "button"
capability tag at all in the Designer.

PER-PIN REASONING / DISPOSITION

  GPIO3 (PIN_LED / LED_BUILTIN):
    capabilities: ["digital_input", "digital_output", "pwm_output", "led_high"]
    Reasoning: confirmed one of this board's 13 GPIO-linked status LEDs
    (GP0-GP7, GP16, GP17, GP26-GP28), active-high (source 2's `.value = True`
    = on pattern; source 3's "13x Status indicator LEDs for GPIO pins" spec
    independently matches the same 13-pin set). Unlike the Maker Nano/Uno
    RP2040 siblings (each with exactly ONE single dedicated onboard LED,
    electrically isolated from any other GPIO use), this board wires an
    identical small indicator LED in parallel with 13 different header GPIOs
    as a general demo/activity feature. GPIO3 is simply arduino-pico's own
    #define PIN_LED choice among that set (for LED_BUILTIN purposes) — not a
    functionally distinct/dedicated pin; all 13 remain plain D-pins
    (D0-D7/D16/D17/A0-A2) in this board's own header, and the demo code
    drives all 13 identically as ordinary digital outputs. Tagged "led_high"
    (informational — the LED and its active-high polarity are real,
    confirmed facts worth surfacing) but digital_input is DELIBERATELY KEPT,
    deviating from the Nano/Uno GPIO2/GPIO3 "drop digital_input" precedent,
    because this is demonstrably not a dedicated-only pin. Matches this
    repo's existing esp8266/oak GPIO5 precedent (single plain LED pin tagged
    led_high while keeping full digital_input/digital_output/pwm_output,
    since the LED there similarly does not preclude ordinary GPIO use of the
    same pin).

  GPIO18 (PIN_NEOPIXEL / PIN_RGB):
    capabilities: ["digital_output", "led_neopixel"]
    Reasoning: onboard 2-pixel WS2812 NeoPixel data line, output-only.
    Confirmed by three independent sources: Zephyr's dts (ws2812 node,
    chain-length 2, PIO-driven), the official demo code
    (neopixel.NeoPixel(board.GP18, 2)), and the datasheet ("2x RGB LED
    (Neopixel)"). digital_input dropped (output-only data line); pwm_output
    omitted per this repo's led_neopixel convention (NeoPixel data is a
    PIO/bit-banged protocol pin, not a PWM-dimmable single LED) — matches the
    cytron_maker_nano_rp2040 GPIO11 and cytron_maker_uno_rp2040 GPIO25
    precedents exactly (no dual-role header LED_OUT complication exists here,
    unlike the sparkfun_thingplusrp2350 GPIO14 exception).

  GPIO20 / GPIO21 (onboard user pushbuttons 1 and 2, unaliased by name in
  this board's own pins_arduino.h):
    capabilities: ["digital_input", "digital_output", "pwm_output", "button"]
    Reasoning: confirmed active-low with internal pull-up by both the Zephyr
    devicetree (button_gp20/button_gp21, GPIO_ACTIVE_LOW | GPIO_PULL_UP) and
    the official demo code (btn1.pull = Pull.UP / btn2.pull = Pull.UP,
    `if not btn1.value:` / `if not btn2.value:`). Full digital_input +
    digital_output + pwm_output + button capability set kept (not reduced to
    input-only) since these are ordinary GPIOs merely wired to switches, not
    dedicated/capacitive-only pins — matches this repo's
    cytron_maker_nano_rp2040 GPIO20 and vccgnd_yd_rp2040 GPIO24
    (PIN_USRKEY) precedents. Note these GPIOs get no named #define anywhere
    in this board's pins_arduino.h (only plain D20/D21) — the chipGpios
    override still applies correctly by GPIO number regardless of alias name,
    same mechanism as the Nano/Uno button overrides.

  PIN_BUZZER (GPIO22): OUT OF SCOPE per task instructions — no buzzer
    capability vocabulary exists in this codebase yet. No chipGpios entry
    added; matches the cytron_maker_uno_rp2040 GPIO8 (PIN_BUZZER) precedent.

  Motor driver pins GPIO8/9/10/11 (PIN_M1A/PIN_M1B/PIN_M2A/PIN_M2B):
    Investigated per task instructions ("motor driver pins are typically
    legitimately general-purpose ... but verify"). The datasheet confirms
    these drive a "dual-channel H-bridge" motor driver IC (1.0A continuous
    rating) — the H-bridge chip is downstream of the RP2040, and from the
    chip's own perspective these are ordinary PWM-capable GPIOs; this is
    exactly how a sketch is meant to control the motors
    (digitalWrite/analogWrite on these same pins). No dedicated-hardware
    restriction applies. Left at chip-level default full
    digital_input/digital_output/pwm_output capabilities; no chipGpios entry
    added.

  Servo header pins GPIO12/13/14/15: datasheet-confirmed "4x Servo motors
    (GPIO12, GPIO13, GPIO14, GPIO15)". Same reasoning as the motor pins —
    ordinary PWM-capable GPIOs routed to 3-pin servo headers, not dedicated
    non-GPIO silicon functions. Left at chip-level defaults; no chipGpios
    entry added.

  SPI1 pin collision (PIN_SPI1_SCK=10, PIN_SPI1_MISO=11, PIN_SPI1_MOSI=12,
    PIN_SPI1_SS=15) — investigated for the "confirmed button/LED pin also
    aliased as a bus signal" bug class flagged in the task background (see
    the adafruit_feather_scorpio precedent). Found: all four of these GPIOs
    are exactly the motor (GPIO10/11) and servo (GPIO12/15) pins evaluated
    above, and all four were deliberately left general-purpose (not
    "confirmed dedicated" in the button/LED sense) — so an auto-appended
    spi1_sck/spi1_miso/spi1_mosi/spi1_ss capability alongside them is not the
    same kind of spurious/misleading result the scorpio fix addressed (that
    fix targeted a bus alias colliding with a pin CONFIRMED to be
    single-purpose, e.g. an LED). Additionally confirmed this SPI1 default
    pin assignment is byte-identical to the vendor's own shipped upstream
    arduino-pico pins_arduino.h for this exact board (source 5 above) — i.e.
    a pre-existing vendor artifact, not something this repo introduced.
    Decision: left as-is, NOT fixed. If a future audit determines SPI1 is
    never genuinely usable on this board (no spare header route), revisit;
    for now this is documented rather than guessed at.

  All other declared aliases (Serial1 GPIO0/1, Serial2 GPIO4/5, Wire0
  GPIO16/17, Wire1 GPIO2/3, SPI0 "not pinned out" 31u sentinel, VBATT/A3
  GPIO29): no dedicated-hardware conflicts found for this board via the
  sources above; left at chip-level defaults, no chipGpios entries added.
  (Note GPIO2/GPIO3 double as Wire1 SDA/SCL as well as two of the 13
  status-LED pins — not a conflict, since a status LED wired in parallel
  does not preclude using the same pin for I2C, unlike the motor pins where
  the H-bridge permanently consumes the pin for a different function.)

SUMMARY
Created variants\rp2040\rp2040\cytron_maker_pi_rp2040\board.json (full
per-board override file) tagging GPIO18 as led_neopixel (2-pixel WS2812,
output-only) and GPIO20/GPIO21 as button (active-low/internal-pull-up,
full capability set retained). GPIO3 (PIN_LED) tagged led_high but --
deliberately deviating from the Nano/Uno sibling precedent -- keeps
digital_input, because vendor sources independently confirm it is one of
13 identically-wired/driven GPIO status LEDs on this board, not a single
dedicated LED. PIN_BUZZER (GPIO22) left untouched as out of scope. Motor
driver pins (GPIO8-11) and servo header pins (GPIO12-15) investigated and
confirmed legitimately general-purpose (H-bridge/servo hardware is
downstream of ordinary PWM GPIOs) -- left at chip-level defaults, no
exclusion applied. The SPI1 bus alias collision with the motor/servo pins
was investigated against the task's flagged bug class, found to be a
pre-existing vendor artifact affecting only already-general-purpose pins
(not a confirmed-dedicated pin), and left unfixed with reasoning
documented above. No build commands were run; board.json validated with a
manual comment-stripping JSON.parse check only.
