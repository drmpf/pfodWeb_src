- SD: CLK=18, CMD/MOSI=19, DAT0/MISO=20, DAT1=21, DAT2=22, DAT3/CS=23,

PER-PIN REASONING
- GPIO13 (PIN_LED / D13): onboard plain red status LED, active-high
  (sources #1, #3). Tagged capabilities: digital_output, pwm_output,
  led_high. digital_input dropped per this audit's established
  led_high/led_low convention for dedicated onboard LED pins (rpipico,
  adafruit_feather_scorpio precedents already in this codebase).
  pwm_output kept since arduino-pico's analogWrite() works on any RP2040
  GPIO (enables brightness dimming). Checked for bus-alias contamination:
  GPIO13 carries no SPI/Wire/Serial alias anywhere in this board's
  pins_arduino.h (SPI0_SS here is GPIO23, not 13, unlike the
  adafruit_feather_scorpio case) — so build_boards.js's auto-append logic
  cannot add a spurious bus capability to this pin. No pins_arduino.h edit
  needed.
- GPIO14 (PIN_NEOPIXEL): onboard single WS2812 status NeoPixel, output-only
  data line (sources #1, #2, #3, #4 all agree). Tagged capabilities:
  digital_output, led_neopixel — matches this repo's adafruit_feather_scorpio
  led_neopixel precedent exactly (no pwm_output; a NeoPixel data line is not
  driven via analogWrite()). Checked for bus-alias contamination: GPIO14
  carries no SPI/Wire/Serial alias in this board's pins_arduino.h. No
  pins_arduino.h edit needed.
- GPIO15, 18, 19, 20, 21, 22, 23 (SD card slot: DETECT, CLK, MOSI, MISO,
  DAT1, DAT2, CS): left untouched / NO CHANGE. These are genuinely
  dedicated to the onboard microSD slot, exactly as this board's own
  pins_arduino.h header comment already states, and source #1 independently
  confirms the same GPIO-to-SD-function mapping. Their SPI0 bus aliases
  (MISO/MOSI/SCK/SS) are correct and intentional (the SD card IS the SPI0
  device), so build_boards.js's automatic SPI-capability append on these
  pins is the DESIRED behavior here, not a contamination bug — no board.json
  chipGpios override and no pins_arduino.h edit applied. (Contrast: on
  adafruit_feather_scorpio, GPIO13 was BOTH the confirmed LED pin AND the
  vendor-default PIN_SPI0_SS alias with no onboard SPI device actually using
  that SS pin, which WAS a genuine contamination bug fixed by removing the
  alias — that situation does not apply here since this board's SD card
  genuinely owns SPI0.)
- No button was found or tagged. Adafruit's own documentation lists only
  RESET and BOOT hardware buttons, neither exposed as an application-
  readable GPIO (same category as the classic Raspberry Pi Pico's BOOTSEL,
  per this repo's existing rpipico/board.json precedent) — confirmed absent
  from the official Zephyr devicetree's button/gpio_keys nodes (source #3).
- No pins_arduino.h changes were made for this board (no bus-alias
  contamination found).
