pin exclusion audit.

--- Per-pin reasoning ---

GPIO23 (PIN_BUTTON_A): confirmed onboard pushbutton via upstream
pins_arduino.h + press corroboration above. Ordinary GPIO (not
capacitive-only). Tagged: digital_input, digital_output, pwm_output,
button — matches this repo's established ordinary-pushbutton precedent
(vccgnd_yd_rp2040 GPIO24 PIN_USRKEY).

GPIO10 (PIN_BUTTON_B): same reasoning as GPIO23. NOTE: this board's own
pins_arduino.h ALSO declares `PIN_SPI1_SCK (10u)` — the same GPIO number.
This is a vendor-side dual-aliasing quirk in the upstream file itself
(SPI1 is presumably unused/not broken out on this board, and GPIO10 was
repurposed for Button B). build_boards.js's unconditional SPI-alias
auto-append (documented precedent in wiznet_5500_evb_pico/board.json,
fires regardless of any chipGpios override) will still attach a
"spi_sck" bus-role tag to GPIO10 on top of the button capability set
declared here. This is expected/inherent to the vendor's own pinout, not
a bug introduced by this board.json — left as-is, flagged here for
visibility. Not "fixed" (out of scope: task only covers button/LED/
NeoPixel tagging + dedicated-hardware exclusion, not resolving vendor
pin-reuse quirks).

GPIO25 (PIN_BUTTON_C): same reasoning as GPIO23.

GPIO19 (PIN_BUTTON_D): same reasoning as GPIO23.

GPIO24 (PIN_NEOPIXEL, NUM_NEOPIXEL=64): confirmed onboard 64-pixel
addressable NeoPixel array via upstream pins_arduino.h. Output-only data
line. Tagged: digital_output, led_neopixel. pwm_output deliberately
OMITTED — a NeoPixel data line carries a bit-banged/PIO timing-critical
protocol, not a real PWM duty-cycle signal, so analogWrite() on this pin
would not do anything meaningful; matches the vccgnd_yd_rp2040 GPIO23
precedent (which also omits pwm_output for its NeoPixel pin), rather
than the alternate sparkfun_promicrorp2040/sparkfun_thingplusrp2350
precedent which keeps pwm_output on the reasoning that analogWrite()
"works on any GPIO" — judged the vccgnd precedent more appropriate here
given the much larger 64-pixel array (clearly PIO/library-driven, not a
simple dimmable LED).

GPIO22 (PIN_BUZZER): OUT OF SCOPE. No "buzzer" PinType exists in this
repo's tagging vocabulary (per task instructions). Left untouched at
chip-level defaults (digital_input/digital_output/pwm_output apply
unchanged via the empty chip-level chipGpios fallback) — this is
harmless and actually usable, since a buzzer can be driven via
digitalWrite() or analogWrite()-based tone-style code without any special
capability tag.

--- Gaps / unconfirmed items ---

- Button electrical polarity (active-high vs active-low) and pull-up/
  pull-down configuration: NOT confirmed. archikids.com.ar/documentacion
  (the vendor's own cited source) is a JS SPA that could not be scraped.
  No schematic found. This does not block the "button" capability tag
  itself (this repo's vocabulary has no separate button_high/button_low
  tag — only led_high/led_low distinguishes LED polarity), so tagging
  proceeded despite this gap. Flagged for any future firmware/example
  work targeting this board.
- No independent (non-upstream-pins_arduino.h) confirmation of the exact
  physical layout/labeling of the four buttons, or of the NeoPixel
  array's physical shape (e.g. whether it is genuinely an 8x8 grid vs.
  some other 64-pixel arrangement) — inferred only from NUM_NEOPIXEL=64
  and the "video games" press description, not directly confirmed.
