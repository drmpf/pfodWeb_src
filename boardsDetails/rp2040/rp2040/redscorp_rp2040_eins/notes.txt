PER-PIN REASONING
------------------
GPIO6 (D13, PIN_LED / LED_BUILTIN, also PIN_SPI0_SCK):
  Schematic's "Signalling and power LEDs" block shows D1 (a RED LED)
  wired: +3V3 -> D1 -> R1 (5k1 series resistor) -> drain of Q2 (AO3400A,
  N-channel MOSFET) -> Q2 source -> GND, with Q2's gate driven directly
  by the "D13_SCK" net (GPIO6/D13). This is the exact same part number
  (AO3400A) and net-naming convention ("D13_SCK") already confirmed
  active-high on the redscorp_rp2040_promini sibling's identical
  circuit. GPIO HIGH -> Q2 turns on -> current flows from +3V3 through
  D1/R1 into Q2's drain, out the source to GND -> LED lights.
  CONFIRMED ACTIVE-HIGH.
  Tagged: ["digital_output", "pwm_output", "led_high"]. digital_input
  dropped (matches redscorp_rp2040_promini/rpipico/arduino_nano_connect
  precedent for a dedicated onboard-LED-driver pin). pwm_output kept
  (arduino-pico's analogWrite() works on any RP2040 GPIO; PWMing the
  MOSFET gate dims the LED normally).

  Bus-collision bug-class check (explicitly required by this audit):
  This board's pins_arduino.h ALSO declares
  `#define PIN_SPI0_SCK (D13)` - i.e. GPIO6 doubles as the SPI0 clock
  line. The schematic's UNO-footprint header connector (J9) breaks this
  same net ("D13_SCK") out alongside MISO=D12/GPIO4, MOSI=D11/GPIO7,
  SS=D10/GPIO5 - the classic Arduino ICSP/pin-13 SPI grouping. This is
  the "confirmed LED pin also aliased as an SPI bus role" pattern this
  audit specifically watches for, but it is judged NOT a bug to fix by
  deleting the #define, for the same reasons already established on the
  redscorp_rp2040_promini sibling and the arduino_nano_connect
  precedent - and arguably even more clearly applicable here, since this
  board is an explicit, literal Arduino UNO R3 footprint replacement
  (per its own GitHub description), and "pin 13 = onboard LED + SCK" is
  the single most iconic classic-Arduino-Uno convention (visible LED
  flicker during SPI transfers is expected, universally-documented
  behaviour on Uno-shaped boards). No pins_arduino.h edit made.
  build_boards.js will auto-append the spi_sck capability on top of
  digital_output/pwm_output/led_high, matching the real dual-role
  hardware - intended, not a defect.

GPIO9 (D22, PIN_LED_R), GPIO10 (D23, PIN_LED_G), GPIO11 (D24,
PIN_LED_B) - discrete RGB LED (schematic ref D4, part "XL-3227RGB-RF"):
  This board (unlike the ProMini sibling) has an onboard 4-pin RGB LED.
  The schematic's "Signalling and power LEDs" block shows three
  independent gate resistors (R13, R14, R15 - 5k1 each) driving three
  independent N-channel MOSFETs (Q3, Q4, Q5 - all AO3400A, the same part
  used for the confirmed-active-high GPIO6/D13 user-LED driver Q2).
  Q3/Q4/Q5's gates are tied to the LED_R/LED_G/LED_B nets respectively
  (GPIO9/GPIO10/GPIO11), switching each color leg of D4 to GND through
  its own MOSFET - the same low-side N-channel switch topology as the
  confirmed-active-high user LED. The vendor's own README independently
  states the RGB LED "uses MOSFETs for RGB LED to make it work similarly
  to user LED" - i.e. the vendor itself documents the same active-high
  behaviour for all three channels, corroborating the schematic.
  CONFIRMED ACTIVE-HIGH for all three channels.
  This is a discrete 4-pin RGB LED driven by three independent
  GPIOs/MOSFETs, NOT a single-wire addressable WS2812/SK6812-style part
  - tagged led_high per channel, NOT led_neopixel.
  Bus-collision bug-class check: none of D22/D23/D24 (GPIO9/10/11) are
  aliased to any other SPI/I2C/Serial role anywhere else in this
  board's pins_arduino.h - genuinely dedicated RGB-LED-only pins, no
  collision to fix.
  Tagged (all three): ["digital_output", "pwm_output", "led_high"].
  digital_input dropped (matches the GPIO6/D13 LED precedent above).
  pwm_output kept (each channel can be PWM-dimmed/color-mixed normally
  via analogWrite()).

D2 (second RED LED in the "Signalling and power LEDs" schematic block,
near +3V3/R6): not aliased to any Dn pin anywhere in this board's
pins_arduino.h - a plain power-on/status indicator LED, not GPIO-driven
(matching the ProMini sibling's identically-placed D2). Out of scope
for GPIO-keyed capability tagging.

BOOTSEL button (schematic block "Boot source selection button", SW1):
  Wired directly to the "QSPI_SS" net - the RP2040's internal dedicated
  QSPI flash chip-select pin (package pins 51-56 region), NOT any of the
  GPIO0-29 pins this board's pins_arduino.h declares Dn aliases for.
  Mechanically identical to the plain Raspberry Pi Pico's own BOOTSEL
  button (rpipico/board.json precedent) and the redscorp_rp2040_promini
  sibling's identical BOOTSEL wiring - not readable via
  digitalRead()/any numbered GPIO, so there is no pin to attach a
  "button" capability to. Out of scope, not a missed tag.

Reset button (schematic block "Reset button", SW2):
  Wired to the RESET/RUN net - a dedicated hard-reset pin, not a
  readable GPIO. Out of scope, same as every other RP2040 board audited
  in this family.

QSPI flash (U1 W25Q128JVS SOIC / U4 W25Q128JVEIQ WSON, alternate
footprints for the same onboard flash - populate one, not both):
  Wired entirely to the RP2040's dedicated internal QSPI pins
  (QSPI_SD0-3, QSPI_SCLK, QSPI_SS), which are physically separate from
  GPIO0-29 and have no corresponding Dn alias in this board's
  pins_arduino.h. No overlap; nothing to exclude.

NeoPixel/single-wire addressable LED: none present on this board - the
only RGB element (D4, XL-3227RGB-RF) is a discrete 4-pin RGB LED driven
by 3 separate GPIO/MOSFET channels, already covered above as three
led_high pins (not led_neopixel).

Other GPIOs (D0-D1, D3-D12, D14-D21, D25-D29 / analog A0-A3): all plain
general-purpose UNO-footprint header breakouts (per the schematic's
"UNO pin connectors" block), no dedicated onboard peripheral wired to
any of them beyond the LEDs/QSPI-flash/buttons already covered above.
Left at full chip-level default capabilities (no chipGpios entry
needed) - matches the empty chip-level chipGpios philosophy for RP2040
(each board's own aliases are the full picture).

SUMMARY
-------
Four corrections applied: GPIO6 (D13, PIN_LED/LED_BUILTIN) tagged
["digital_output", "pwm_output", "led_high"] (digital_input dropped),
confirmed active-high directly from the schematic's Q2 (AO3400A
N-channel MOSFET) switch topology, identical to the redscorp_rp2040_promini
sibling's already-confirmed circuit. GPIO9/10/11 (D22/D23/D24,
PIN_LED_R/PIN_LED_G/PIN_LED_B - an onboard discrete RGB LED not present
on the ProMini sibling) each tagged
["digital_output", "pwm_output", "led_high"], confirmed active-high via
the schematic's Q3/Q4/Q5 (AO3400A N-channel MOSFETs, same topology as
the user LED) and corroborated by the vendor README's explicit
"MOSFETs...to make it work similarly to user LED" statement; tagged
led_high per discrete channel, not led_neopixel (this is a 4-pin RGB
LED, not a single-wire addressable part). The GPIO6/PIN_SPI0_SCK dual
alias was investigated as a possible "bus auto-append" bug per this
audit's standing checklist, but confirmed to be the deliberate,
expected classic-Arduino pin-13 LED+SCK sharing (this board is an
explicit Arduino UNO R3 footprint replacement) - no pins_arduino.h
changes made. BOOTSEL/RESET buttons and QSPI flash chip-select are
wired to non-GPIO RP2040 pins and are out of scope for GPIO-keyed
capability tagging. The second red LED (D2, power/status indicator) is
not wired to any GPIO and is out of scope. All other GPIOs left at
chip-level defaults.
