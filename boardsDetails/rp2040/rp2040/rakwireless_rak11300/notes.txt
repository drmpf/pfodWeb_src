Board: RAKwireless "RAK11300" (chip bucket: rp2040)
Directory: variants/rp2040/rp2040/rakwireless_rak11300/
Audit date: 2026-07-13

SUMMARY
-------
NO CHANGE. The RAK11300 is a bare WisDuo-family LoRaWAN MODULE (an
RP2040 + SX1262 SiP-style module meant to be soldered/reflowed onto a
carrier PCB, e.g. RAKwireless's own WisBlock base boards) - not a
standalone development board. Confirmed via the official RAK datasheet,
the RAKwireless store product page, and the RAKwireless forum pinout
thread (the same three sources this board's own pins_arduino.h header
comment cites) that the module itself has:
  - NO onboard status LED
  - NO onboard user button (only the RP2040's internal, non-GPIO
    BOOTSEL, which - per this audit's established convention - would
    live on a carrier/programmer board anyway, not this module)
  - NO onboard NeoPixel/WS2812
The only onboard peripheral is the SX1262 LoRa radio, wired to GPIO10,
11, 12, 13 (SPI1), 14 (NRESET), 15 (BUSY), 25 (ANT_PWR), and 29 (DIO1).
This board's own pins_arduino.h ALREADY fully excludes all eight of
those GPIOs from its `static const uint8_t D<n>` alias set (confirmed:
the alias block declares D0-D9, D16-D24, D26-D28 only - GPIO10, 11, 12,
13, 14, 15, 25, and 29 are conspicuously and completely absent) and
already carries an explicit "pfodWeb NOTE" comment (line 46) recording
this as deliberate: "GPIO10,11,12,13,14,15,25,29 are dedicated to an
onboard peripheral on this board ... not general-purpose." That prior-
session exclusion was independently re-verified against the official
datasheet's own GPIO pin-function table this session and found to be
100% correct - all eight radio pins match, and no additional dedicated
pins were found beyond what's already excluded.

Because (a) there is no LED, button, or NeoPixel to tag, and (b) the
radio's dedicated pins are already fully hidden from the Designer's pin
picker by the existing pins_arduino.h alias exclusion (same mechanism
used by the challenger_2040_lora and waveshare_rp2040_lora sibling
audits - see "WHY NO board.json IS CREATED" below), there is nothing
for a per-board board.json to override. Creating one would just be a
byte-for-byte duplicate of the chip-level variants/rp2040/rp2040/
board.json with an empty chipGpios:{} - i.e. a no-op. Per this audit's
own stated principle ("Report NO CHANGE rather than guess"), no
board.json was created for this board.

No pins_arduino.h edit was made either - no bus-alias collision exists
(see BUG-CLASS CHECK below), and the existing exclusion is already
correct.

WHY NO board.json IS CREATED
------------------------------
build_boards.js's buildEsp32Board() parser (the "rp2040" family routes
through it - see ../board.json's own family-selection comment) only
lists a GPIO in the Designer's pin picker if it appears either (a) as a
`static const uint8_t` alias in pins_arduino.h, or (b) as a key in a
per-board board.json's chipGpios object. This board's pins_arduino.h
already declares NO alias resolving to GPIO10, 11, 12, 13, 14, 15, 25,
or 29 (verified above), so all eight SX1262-dedicated GPIOs are already
100% absent from the Designer's pin list - no board.json involvement
needed to hide them. Since no LED, button, or NeoPixel exists on this
module to additionally tag, there is no chipGpios entry this audit
could correctly add. A board.json containing only a byte-for-byte copy
of the chip-level defaults with an empty chipGpios:{} would be a
functional no-op (the chip-level variants/rp2040/rp2040/board.json
already supplies those exact same defaults via fallback), so none was
created - consistent with this audit's "Report NO CHANGE rather than
guess" principle.

BUG-CLASS CHECK (button/LED aliased onto a bus pin)
-------------------------------------------------------
Not applicable in the usual sense (no button/LED exists to collide with
a bus alias), but checked anyway for the SX1262-dedicated GPIOs against
this board's OTHER (non-radio) SPI0/Wire0 bus aliases: SS=GPIO17,
MOSI=GPIO19, MISO=GPIO16, SCK=GPIO18 (PIN_SPI0_*), SDA=GPIO2, SCL=GPIO3
(PIN_WIRE0_*). None of these six numbers (16, 17, 18, 19, 2, 3) overlap
with the eight excluded radio pins (10, 11, 12, 13, 14, 15, 25, 29), so
no spurious spi_ss/spi_mosi/spi_miso/spi_sck/i2c_sda/i2c_scl capability
would be auto-appended to a radio-dedicated pin even if it were
re-exposed. No pins_arduino.h edit needed.

PER-PIN REASONING
------------------
GPIO10 (PIN_SPI1_SCK, LoRa SPI1 clock): no pins_arduino.h alias exists;
  already fully excluded from the Designer pin list. Confirmed dedicated
  via datasheet (SPI_SCK=GPIO10). No board.json entry needed.

GPIO11 (PIN_SPI1_MOSI, LoRa SPI1 data out): same - no alias, already
  excluded. Confirmed via datasheet (SPI_MOSI=GPIO11).

GPIO12 (PIN_SPI1_MISO, LoRa SPI1 data in): same - no alias, already
  excluded. Confirmed via datasheet (SPI_MISO=GPIO12).

GPIO13 (PIN_SPI1_SS, LoRa SPI1 chip-select): same - no alias, already
  excluded. Confirmed via datasheet (SPI_NSS=GPIO13).

GPIO14 (PIN_SX1262_NRESET, radio reset line): same - no alias, already
  excluded. Confirmed via datasheet (NRESET=GPIO14).

GPIO15 (PIN_SX1262_BUSY, radio busy/ready status line): same - no
  alias, already excluded. Confirmed via datasheet (BUSY=GPIO15).

GPIO25 (PIN_SX1262_ANT_PWR, antenna-switch power control - forum thread
  confirms it "needs to be set as OUTPUT and pulled HIGH for any
  transmission/receive operation"): same - no alias, already excluded.
  Confirmed via datasheet (ANT_SW=GPIO25) and independently via the
  RAKwireless forum thread.

GPIO29 (PIN_SX1262_DIO1, radio interrupt/IRQ line): same - no alias,
  already excluded. Confirmed via datasheet (DIO1=GPIO29).

No onboard LED found - confirmed absent across all sources consulted
  (official datasheet, official store product page, official forum
  thread, independent third-party writeups). This is expected: the
  RAK11300 is sold as a bare surface-mount MODULE for integration onto
  a carrier PCB (e.g. RAKwireless's own WisBlock base boards, which
  carry their own LEDs/buttons separately - out of scope for this
  module's own board.json). No chipGpios tag applied.

No onboard NeoPixel found - same reasoning/sources as above. No
  chipGpios tag applied.

No onboard GPIO-controllable user button found - same reasoning/sources
  as above; only the RP2040's internal BOOTSEL exists (not a normal
  GPIO, and would in any case live on a carrier/programmer board, not
  this module). No chipGpios tag applied.
