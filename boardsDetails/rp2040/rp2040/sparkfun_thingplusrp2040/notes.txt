=== Identity check ===
This board's own pins_arduino.h has a source comment referencing
"ProMicroRP2040_Graphical_Datasheet.pdf", which looks like it names a
different SparkFun product ("Pro Micro RP2040"). Verified via
variants/rp2040/boards.txt that this directory id genuinely maps to the
real "SparkFun Thing Plus RP2040" product:
  sparkfun_thingplusrp2040.name=SparkFun Thing Plus RP2040
  sparkfun_thingplusrp2040.build.usb_product="Thing Plus RP2040"
  sparkfun_thingplusrp2040.build.board=SPARKFUN_THINGPLUS_RP2040
Also found the sibling board variants/rp2040/rp2040/sparkfun_promicrorp2040/
board.json carries the IDENTICAL "ProMicroRP2040_Graphical_Datasheet.pdf"
citation in its own pins_arduino.h - confirming this citation is a
copy/paste quirk shared across multiple distinct SparkFun boards' upstream
arduino-pico source, not evidence of misidentification. pins_arduino.h
itself was left untouched (out of scope; only board.json/notes.txt authored
here).

Despite the shared source-citation, this board's actual pin functions
(confirmed independently below) do NOT match the Pro Micro RP2040's -
Pro Micro RP2040 has PIN_LED and PIN_NEOPIXEL on the SAME GPIO25 (single
WS2812 doubling as status LED). This board (Thing Plus RP2040) has
PIN_LED=25 (a separate, plain non-addressable LED) and PIN_NEOPIXEL=8 (a
separate WS2812) - two different GPIOs, confirmed both in pins_arduino.h
and independently via SparkFun's own hookup guide (see below).

=== Per-pin reasoning ===

GPIO8 (PIN_NEOPIXEL, NUM_NEOPIXEL=1): CONFIRMED onboard WS2812
addressable RGB LED data line. Tagged
["digital_output","led_neopixel","pwm_output"]. digital_input dropped -
matches this repo's led_neopixel precedent.

GPIO9 (PIN_SPI1_SS): CONFIRMED microSD card CS/DATA3 line, vendor-
documented "dedicated GPIO", not among the 18 header-broken-out pins.
capabilities: [] (note-only). build_boards.js's automatic SS-alias match
still attaches spi_ss on top (expected/correct, cannot be suppressed via
chipGpios and shouldn't be).

GPIO10 (D10 only, no bus alias): CONFIRMED microSD DATA2 line, vendor-
documented dedicated GPIO. capabilities: [] (note-only). No SPI-role
alias exists in pins_arduino.h for this pin, so no bus-role tag applies
either.

GPIO11 (D11 only, no bus alias): CONFIRMED microSD DATA1 line, same
treatment as GPIO10. capabilities: [] (note-only).

GPIO12 (PIN_SPI1_MISO): CONFIRMED microSD DATA0/CIPO line, vendor-
documented dedicated GPIO. capabilities: [] (note-only). Automatic
MISO-alias match still attaches spi_miso.

GPIO14 (PIN_SPI1_SCK): CONFIRMED microSD CLK/SCK line, vendor-documented
dedicated GPIO. capabilities: [] (note-only). Automatic SCK-alias match
still attaches spi_sck.

GPIO15 (PIN_SPI1_MOSI): CONFIRMED microSD CMD/COPI line, vendor-
documented dedicated GPIO. capabilities: [] (note-only). Automatic
MOSI-alias match still attaches spi_mosi.

GPIO25 (PIN_LED): CONFIRMED onboard blue status/debug LED, active-high
(vendor hookup guide MicroPython example: led.value(1) turns it on).
Tagged ["digital_output","pwm_output","led_high"]. digital_input dropped
to match this repo's established led_high precedent for dedicated
onboard LED pins.

GPIO6/7 (PIN_WIRE1_SDA/SCL): CONFIRMED Qwiic I2C1 connector pins (also
shared internally with the onboard MAX17048 fuel gauge on the same bus).
NO override - already correctly tagged via build_boards.js's automatic
SDA/SCL alias matching, matching the identical precedent already applied
to the RP2350 sibling's own Qwiic pins (left general-purpose/default).

Not investigated further / no override needed (out of scope, and no
capability leak possible regardless): GPIO23 (the tied-together SCL half
of the I2C1 pair) and GPIO24 (MAX17048 fuel-gauge ALERT pin) - neither
has ANY D<n> or bus alias declared in this board's own pins_arduino.h,
so build_boards.js's alias-driven capability grant mechanism never fires
for them no matter what the chip-level or per-board chipGpios defaults
are. GPIO0-5, 13, 16-22, 26-28 (plain D<n>/A<n> pins, Wire0 SDA/SCL,
SPI0 MISO/MOSI/SCK) are the board's genuinely general-purpose header-
broken-out pins per the vendor's own "18 broken out" count - left at
chip-derived defaults (full digital_input/digital_output/pwm_output),
no override.

=== Bug-class check (button/LED pin also aliased as bus pin) ===
Checked: none of GPIO8 (NeoPixel) or GPIO25 (status LED) collide with
any SDA/SCL/SS/MOSI/MISO/SCK alias in this board's pins_arduino.h - no
adafruit_feather_scorpio-style collision found, no #define removal
needed.

=== No onboard general-purpose button ===
Only the standard RP2040 BOOT and RESET buttons exist (vendor-confirmed:
"BOOT Button: Forces BOOTSEL mode..." / "RESET Button: Connected to
reset pin..."). Both are hardware-only, not GPIO-readable via a normal
digitalRead() - no "button" capability tag applies, matching this repo's
universal convention for RP2040-family BOOTSEL/RESET buttons.
