PER-PIN REASONING
------------------
GPIO25 (PIN_LED) — NOT tagged led_high/led_low/pwm_output.
  GPIO25 is the conventional onboard-LED GPIO on the official Raspberry Pi Pico
  reference design, confirmed active-high there (see rpipico/board.json, already
  audited 2026-07-12). However, THIS board's own SPI0 pin mapping (MISO=GPIO12,
  MOSI=GPIO3, SCK=GPIO2, SS=GPIO13) already diverges substantially from the official
  Pico's reference SPI0 pinout, proving MyRP_bot is a custom pinout, not a verbatim
  clone of the reference design — so the LED circuit (and its polarity) cannot be
  safely assumed to match the stock Pico's just because the same GPIO number was
  reused for the LED comment. Per this audit's explicit rule ("confirm via real
  vendor documentation — never guess polarity from the alias name alone... report NO
  CHANGE rather than guess"), and given zero vendor documentation exists for this
  board, GPIO25 is left untagged (falls through to the ordinary digital_input/
  digital_output/pwm_output default via the empty chipGpios, same as any other
  unremarkable GPIO on this family).

GPIO30 / GPIO31 non-existent-pin observation — investigated, NO FIX NEEDED.
  This board's pins_arduino.h sets: PIN_SERIAL1_TX=30, PIN_SERIAL2_TX=30,
  PIN_SERIAL2_RX=30, PIN_SPI1_MOSI=30, PIN_SPI1_SCK=31 (all out-of-range — real
  RP2040 silicon only has GPIO0-29), and PIN_SPI1_MISO=12 duplicates
  PIN_SPI0_MISO=12. This strongly suggests SPI1/UART1/UART2 are simply
  unused/not-wired on this particular board and the contributor left them pointing at
  arduino-pico's conventional "unimplemented peripheral" sentinel pin numbers rather
  than genuinely repurposing GPIO30/31 (which is physically impossible on RP2040).
  Traced precisely through pfodWeb_src/build_boards.js's buildEsp32Board() /
  parseEsp32Consts() (~lines 439-548, 630-724):
    - parseEsp32Consts() ONLY captures `static const uint8_t NAME = <value>;` /
      `static constexpr uint8_t NAME = <value>;` declarations (plus one level of
      #define-fallback resolution for a static-const alias chain) as pin aliases —
      raw #define macros are never harvested wholesale (this is explicitly documented
      in the parser's own comment, to avoid false hits like NEOPIXEL_NUM).
    - The bus-role capability tags (spi_ss/spi_mosi/spi_miso/spi_sck/i2c_sda/i2c_scl)
      are driven by `consts.SS/MOSI/MISO/SCK/SDA/SCL`, which this rp2040 family's
      shared generic/common.h (lines 155-161) assigns ONLY from
      PIN_SPI0_SS/MOSI/MISO/SCK and PIN_WIRE0_SDA/SCL — i.e. bus 0 only.
    - PIN_SPI1_*, PIN_WIRE1_*, PIN_SERIAL1_*, PIN_SERIAL2_* raw #defines are never
      the target of any static-const alias anywhere in common.h, so they never enter
      `consts`, never enter `aliasesByGpio`, and never enter `allGpios`.
  Consequence: no phantom GPIO30/GPIO31 pin is ever generated in the Designer's board
  data (they simply never appear), and GPIO4/GPIO5 (which only carry WIRE1/SPI1
  aliases in the raw .h source) fall back to being ordinary general-purpose D4/D5
  digital pins with no spurious spi_ss/i2c_sda/i2c_scl capability attached. This is a
  cosmetic-only quirk in the vendored pins_arduino.h with zero effect on the actual
  generated board.json/pins output — confirmed via source-reading, not guessed, and
  intentionally NOT run through build_boards.js per the task's build-command
  restriction. No chipGpios entry is needed to correct it.

GPIO12 shared between PIN_SPI0_MISO and PIN_SPI1_MISO — no conflict.
  Since PIN_SPI1_MISO is never referenced by any static-const alias (see above), only
  the SPI0 MISO role (GPIO12) is ever surfaced; no double-tagging or conflict occurs.

All other pins (D0-D22 via common.h, A0-A2 = GPIO26-28) — no board-specific evidence
found; left at the chip-level default (ordinary digital_input/digital_output/
pwm_output, plus analog_input for A0-A2), matching every other undocumented rp2040
pin in this family.

SUMMARY
-------
MyRP_bot ("MyMakers RP2040") is a non-commercial, community/education-distributed
RP2040 board (upstream arduino-pico PR by contributor nui4328, merged as commit
06e3ef9) with no findable datasheet, schematic, or vendor documentation anywhere;
this repo's pins_arduino.h is confirmed byte-identical to the real upstream file.
GPIO25 (PIN_LED) is very likely a real onboard LED but its active-high/active-low
polarity cannot be confirmed from any source, so per this audit's guidance it is
left untagged (NO CHANGE) rather than guessed. The apparent GPIO30/31
non-existent-pin usage (PIN_SPI1_MOSI/SCK, PIN_SERIAL1/2_TX/RX) was investigated in
detail and traced, via build_boards.js's parser, to have zero effect on the
generated board — SPI1/UART1/UART2 are effectively inert placeholders on this
board and require no fix. board.json was created as a full verbatim copy of the
rp2040 chip-level defaults with chipGpios: {} (no confirmed overrides).
