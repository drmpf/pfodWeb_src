CRITICAL CROSS-CHECK: pins_arduino.h vs vendor-documented pinout
------------------------------------------------------------------
The vendor wiki's own SPI/I2C pin table does NOT match this repo's
degz_suibo/pins_arduino.h:
  Vendor wiki SPI:  MISO=GP6,  MOSI=GP7,  SCK=GP16, CS=GP17
  This repo's file: MISO=16u, MOSI=19u, SCK=18u,  SS=17u   (SPI0)
  Vendor wiki I2C:  SCL=GP2, SDA=GP3
  This repo's file: SDA=4u,  SCL=5u                          (Wire0)
Only SS/CS (17) happens to coincide; MISO/MOSI/SCK are all different
GPIO numbers between the vendor's documented hardware and this repo's
declared pins_arduino.h. Combined with the byte-identical diff against
rpipico/pins_arduino.h and the header comment still citing the "Pico
datasheet", this confirms this variant's pins_arduino.h was scaffolded
from the generic Pico template and never corrected against the real
Suibo schematic — it is NOT a hand-verified hardware pinout. This is out
of scope to fix under this button/LED/NeoPixel capability-tagging audit
(rewriting PIN_SPI0_*/PIN_WIRE0_* would be a pins_arduino.h content
change, not a chipGpios capability override), but it is the deciding
factor in the PIN_LED conclusion below: given the file's other pin claims
are already demonstrably wrong relative to the vendor's own
documentation, PIN_LED=25u cannot be trusted as confirming a real
onboard LED at GPIO25 either, especially since the vendor's own GPIO
table never mentions GPIO25 in any capacity.

CONCLUSION / PER-PIN REASONING
-------------------------------
GPIO25 (PIN_LED): NOT tagged led_high/led_low. No authoritative vendor
source ties GPIO25 to an onboard LED — the vendor's own documented GPIO
table (item 2a above) omits GPIO25 entirely, and the alias's only source
is a pins_arduino.h file already shown (via the SPI/I2C mismatch above)
to be an unmodified generic-Pico-template copy rather than a hardware-
verified pinout for this board. Per this audit's rule ("if you cannot
find authoritative vendor documentation, report NO CHANGE rather than
guess at polarity from the alias name alone"), GPIO25 is left at its full
chip-default derived capabilities (digital_input, digital_output,
pwm_output) — unchanged from today's build output.

GPIO0 / GPIO1 (PIN_SERIAL1_TX / PIN_SERIAL1_RX): NOT tagged. Vendor
documentation describes these as "Tx LED"/"Rx LED" but this is (a)
internally inconsistent with a separate statement that the status LED
"does not light up on v1 Suibo boards", and (b) most consistent with a
passive UART-activity indicator wired in series with the physical UART0
TX/RX lines (which these pins are already dedicated to per
PIN_SERIAL1_TX/RX), not a general-purpose digitalWrite()-controllable
GPIO output. Matches this family's established precedent of excluding
passive/activity-only LEDs from led_high/led_low tagging (e.g.
sea_picro's passive power LED). No capability change applied.

No button alias (no PIN_BUTTON/PIN_USRKEY/BOOTSEL-as-GPIO or similar) is
declared in this board's pins_arduino.h. Vendor docs mention only a
RESET button and a BOOT button — standard dedicated hardware
reset/bootloader circuits, not digitalRead()-able GPIOs, matching every
other RP2040 board's BOOTSEL/reset button in this repo.

No NeoPixel/WS2812 alias (no PIN_NEOPIXEL or similar) is declared
anywhere in this board's pins_arduino.h, and none is mentioned in the
vendor documentation beyond the generic "programmable LEDs" phrase (too
vague to act on, and not tied to any GPIO number).

Bus-collision bug class check: this board declares SPI0 (MISO=16,
MOSI=19, SCK=18, SS=17), SPI1 (MISO=12, MOSI=15, SCK=14, SS=13), Wire0
(SDA=4, SCL=5), and Wire1 (SDA=26, SCL=27) per its own pins_arduino.h.
PIN_LED=25 does not coincide with any of these bus pins, so the
"confirmed button/LED pin also aliased as a bus pin" bug class does not
apply here regardless of the PIN_LED conclusion above — no
pins_arduino.h edit was made or needed.
