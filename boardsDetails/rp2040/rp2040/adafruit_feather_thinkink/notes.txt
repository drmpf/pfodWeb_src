Board: Adafruit Feather RP2040 ThinkInk (product 5727)
Directory: variants/rp2040/rp2040/adafruit_feather_thinkink/
Audit date: 2026-07-13
Result: board.json CREATED (chipGpios overrides for EPD connector control
lines, NeoPixel + power gate, button, LED). pins_arduino.h EDITED (removed
colliding default PIN_SPI0_SS(13u) alias — see "Bug found" below).

SUMMARY
-------
This is a Feather RP2040 with dedicated support circuitry (six GPIOs
wired to a 24-pin FPC connector) for driving an externally-attached
e-Ink/e-Paper display over its own dedicated SPI bus — Adafruit's own
Overview page is explicit: "No display is included onboard. The board
features support circuitry for common 24-pin e-Paper/e-Ink displays."
It also has a plain status LED (GPIO13, active-high), a single status
NeoPixel (GPIO21, gated by a power-enable pin on GPIO20 that must be
driven HIGH), and a BOOT pushbutton (GPIO7, active-low with internal
pull-up) — the same identity-pin pattern as the already-audited
adafruit_feather_scorpio and adafruit_feather_can sibling Feather RP2040
boards. Chip-level rp2040/rp2040/board.json has chipGpios: {} (deliberately
empty), so every GPIO with any alias in this board's pins_arduino.h gets
full digital_input/digital_output/pwm_output capability by default unless
corrected here.

PER-PIN FINDINGS
-----------------
GPIO7  (PIN_BUTTON / BOOT) — tagged button. Ordinary GPIO wired to a
  switch to GND, active-low, RP2040 internal pull-up enabled (no
  external pull-up), matching the identical module design already
  confirmed via Zephyr devicetree on the scorpio/can siblings. Full
  digital_input/digital_output/pwm_output capability retained (source 1,
  source 5).

GPIO13 (PIN_LED) — tagged led_high. Onboard status LED, active-high
  (source 1, source 3, source 4). digital_input dropped per this repo's
  established led_high precedent for dedicated onboard LED pins;
  pwm_output kept (analogWrite() works on any RP2040 GPIO).

GPIO16 (PIN_EPD_BUSY) — capabilities emptied. Dedicated Busy-Detect
  control line wired to the board's e-Ink display FPC connector (source
  1, source 3).

GPIO17 (PIN_EPD_RESET) — capabilities emptied. Dedicated active-reset
  control line for the e-Ink display connector (source 1, source 3).

GPIO18 (PIN_EPD_DC) — capabilities emptied. Dedicated Data/Command
  select control line for the e-Ink display connector (source 1,
  source 3).

GPIO19 (PIN_EPD_CS / PIN_SPI1_SS) — capabilities emptied. Dedicated SPI
  chip-select line for the e-Ink display connector's own SPI bus (source
  1, source 3). No spi_ss auto-append risk (source 6).

GPIO20 (NEOPIXEL_POWER) — capabilities emptied. NeoPixel power-enable
  gate; must be driven HIGH for the status NeoPixel to light (source 1,
  verbatim: "It needs to be set High for the NeoPixel to be powered").
  Matches the adafruit_feather_can NEOPIXEL_POWER exclusion precedent
  (same Feather RP2040 module design).

GPIO21 (PIN_NEOPIXEL) — tagged led_neopixel. Onboard single status
  WS2812, output-only data line (source 1, source 3). Depends on GPIO20
  being driven HIGH to actually receive power.

GPIO22 (PIN_EPD_SCK / PIN_SPI1_SCK) — capabilities emptied. Dedicated
  SPI clock line for the e-Ink display connector's own SPI bus (source
  1, source 3). No spi_sck auto-append risk (source 6).

GPIO23 (PIN_EPD_MOSI / PIN_SPI1_MOSI) — capabilities emptied. Dedicated
  SPI MOSI line for the e-Ink display connector's own SPI bus (source 1,
  source 3). No spi_mosi auto-append risk (source 6). PIN_SPI1_MISO is
  left "not pinned out" (31u) in this board's pins_arduino.h, consistent
  with an e-Ink display being write-only over SPI (no MISO line needed).

GPIO8, GPIO14, GPIO15 (SPI0 MISO/SCK/MOSI, Arduino-facing "SPI0" object)
  — NO CHANGE. Confirmed via source 1 to be the board's general-purpose
  "main exposed SPI" header pins, not consumed by the EPD or any onboard
  peripheral — left at full default capability, matching the scorpio/can
  precedent's treatment of their own shared SPI0 MISO/MOSI/SCK.

GPIO0-6, 9-12, 24-29 (D0-D6/D9-D12/D24-D29, A0-A3, Serial1 TX/RX, Wire0
  SDA/SCL) — NO CHANGE. Ordinary broken-out Feather header pins with no
  onboard-dedicated-hardware conflict found.

BUG FOUND AND FIXED
--------------------
GPIO13 (confirmed onboard status LED) was ALSO declared as this board's
vendor-default PIN_SPI0_SS (13u) in pins_arduino.h. build_boards.js
unconditionally auto-appends the matching bus-role capability (spi_ss
here) for whatever GPIO the resolved SS/MOSI/MISO/SCK bare aliases equal,
regardless of any chipGpios override — so without a fix, the confirmed
LED pin would have been contaminated with a spurious spi_ss capability in
the Designer's pin picker.

Investigation confirmed no onboard device uses this default SS pin — the
EPD connector has its own separate dedicated SPI1 bus (SS=GPIO19,
source 1/3) — so GPIO13's PIN_SPI0_SS alias was vendor boilerplate left
over from the generic RP2040 pin-map template, not a real hardware role.

Fix (matching the identical bug/fix already applied to
adafruit_feather_scorpio/pins_arduino.h on 2026-07-12 and
adafruit_feather_can/pins_arduino.h on 2026-07-13): removed the
`#define PIN_SPI0_SS (13u)` line from
variants/rp2040/rp2040/adafruit_feather_thinkink/pins_arduino.h, with an
explanatory pfodWeb NOTE comment left in its place. MISO/MOSI/SCK
aliases (GPIO8/15/14) were left untouched, since source 1 independently
confirms those three ARE genuine general-purpose header pins.

Note: this file's bottom section still contains a bespoke (non-
common.h) `static const uint8_t SS = PIN_SPI0_SS;` line, matching the
same file's own pre-existing D0-D29/A0-A3/SDA/SCL block. With the
PIN_SPI0_SS macro removed, this line's build_boards.js parser resolution
simply fails to resolve (SS ends up unresolved/undefined in the parser's
alias table), which safely prevents any GPIO from being mismatched
against it — same reasoning independently verified for the identical fix
on adafruit_feather_can (see that board's notes.txt). This line was
deliberately left as-is (not further edited) to match the scorpio/can
precedent's minimal-footprint fix and this project's "don't refactor
beyond the specific requested change" guideline; it has no effect on the
generated board.json.
