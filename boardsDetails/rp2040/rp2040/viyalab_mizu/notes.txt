Board audit notes: viyalab_mizu ("Viyalab Mizu RP2040", chip: rp2040)
Date: 2026-07-13

SUMMARY (one line): NO CHANGE — this board's sole identity pin (GPIO25 /
PIN_LED) is confirmed by official Viyalab docs to be a real onboard
"Programmable LED", but no authoritative source could be found for its
polarity (active-high/low) or its exact type (simple LED vs NeoPixel)
on THIS specific PCB, so per the audit's "report NO CHANGE rather than
guess" rule, GPIO25 was left at chip-level defaults (no led_high/
led_low/led_neopixel tag applied); the board's unusual SPI0 pin split
was investigated and found to be genuine, confirmed board-specific
microSD-card wiring (not boilerplate/typo), and required no chipGpios
action since it doesn't collide with GPIO25 or any other identity pin.

SPI0 PIN-SPLIT INVESTIGATION (per task brief's flagged concern)
-----------------------------------------------------------------
Confirmed genuine, board-specific customization, NOT a boilerplate
copy-paste artifact:
  - rpipico and degz_suibo (both templated from the same generic
    Pico-clone pins_arduino.h header/comment) use the STANDARD RP2040
    Pico SPI0 pinout: MISO=16, MOSI=19, SCK=18, SS=17 (GPIO16-19 block).
  - viyalab_mizu instead declares MISO=16, MOSI=7, SCK=6, SS=17 —
    MOSI/SCK moved to GPIO7/GPIO6, a DIFFERENT (but individually valid)
    RP2040 SPI0 alternate-function pin group (per the RP2040 datasheet,
    SPI0 SCK is available on GPIO2/6/18, TX/MOSI on GPIO3/7/19,
    RX/MISO on GPIO0/4/16, CSn on GPIO1/5/17 — GPIO6/7 is a legitimate,
    documented SPI0 alt-function location, just an unusual one to mix
    with GPIO16/17 for the other two signals).
  - This is consistent with Viyalab's own documented "Micro SD card
    slot" peripheral — a real onboard SD card needs its own dedicated
    SPI wiring, which plausibly explains why this board deviates from
    the generic template on exactly these two SPI0 pins while leaving
    everything else (Serial1/2, SPI1, Wire0/1) at the standard Pico
    values.
  - Checked for GPIO25 (PIN_LED) collision against all six bus alias
    values in this board's own pins_arduino.h: SS=17, MOSI=7, MISO=16,
    SCK=6, SDA=4, SCL=5 — none equal 25. No
    adafruit_feather_scorpio-style bus-capability contamination bug
    exists here; no pins_arduino.h edit was needed.
  - No chipGpios action was taken for the SPI0 pins themselves (GPIO6/
    7/16/17) — they are ordinary bus pins serving their declared SPI0
    role (auto-handled by build_boards.js's own spi_* boilerplate-alias
    logic), not a case of a button/LED pin doubling as a bus pin.

PER-PIN REASONING
------------------
GPIO25 (PIN_LED):
  - Confirmed via official Viyalab documentation to correspond to a
    real onboard "Programmable LED" feature — not leftover boilerplate,
    the vendor's own docs explicitly list it as a hardware peripheral.
  - However: polarity (active-high vs active-low) could NOT be
    confirmed for this specific board's own PCB design. Unlike the
    rpipico precedent (official Raspberry Pi documentation + numerous
    independent secondary sources explicitly stating "GP25 LED is
    active-high"), no equivalent source exists for viyalab_mizu — the
    wiki.degzrobotics.com pages that might contain this detail are
    blocked from WebFetch (HTTP 403), and no cached/indexed search
    snippet surfaced polarity information.
  - Type (simple digital LED vs WS2812/addressable NeoPixel) also could
    not be positively confirmed. The absence of any PIN_NEOPIXEL alias
    in this board's own pins_arduino.h (contrast with
    waveshare_rp2040_zero/matrix and vccgnd_yd_rp2040, which all give
    their onboard WS2812 a distinct PIN_NEOPIXEL define) is suggestive
    that it's a simple LED, but this is inference from an absence, not
    a positive vendor statement, so it was not treated as sufficient to
    apply a led_neopixel (or led_high/led_low) tag.
  - Given this board is independently confirmed to deviate from the
    generic Pico-clone boilerplate on its SPI0 pins (see above), the
    usual "it's just the same LED circuit as the reference Pico" leap
    of faith is specifically less safe to make here than it would be
    for a board that matches the template everywhere.
  - DECISION: left at chip-level auto-derived default (full
    digital_input/digital_output/pwm_output, no led_high/led_low/
    led_neopixel tag) — NO CHANGE, per the audit's explicit instruction
    to report NO CHANGE rather than guess polarity from the alias name
    alone.

GPIO0-24, 26-29 (Serial1/2, SPI0/SPI1, Wire0/1, remaining GPIOs):
  - No vendor documentation found suggesting any dedicated onboard
    button, second LED, or NeoPixel exists on any of these pins beyond
    their declared bus roles (already auto-handled by build_boards.js's
    boilerplate spi_*/i2c_*/serial_* alias logic). No override applied.

No onboard button of any kind (BOOTSEL-style or ordinary GPIO
pushbutton) is documented for this board beyond the standard BOOT+GND
jumper-bridge bootloader-entry procedure mentioned in the setup guide
(which is the same non-GPIO QSPI-CS-line BOOTSEL mechanism as the
classic Pico — see rpipico/board.json's precedent note — not a normal
digitalRead()-able pin in any case).
