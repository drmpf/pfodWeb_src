BUS-COLLISION CHECK (task brief's flagged concern)
---------------------------------------------------
The task brief specifically flagged this board as "a likely candidate"
for the confirmed-bug class where a button/LED/NeoPixel GPIO is ALSO
aliased as SDA/SCL/SS/MOSI/MISO/SCK, because this board's
pins_arduino.h happens to declare PIN_WIRE0_SDA (24u) as a separate
#define from PIN_LED (4u) (superficially resembling the
adafruit_feather_scorpio precedent bug).

Checked ALL SIX bus alias values against GPIO4 explicitly:
  SS   = PIN_SPI0_SS   = 21  -- not 4
  MOSI = PIN_SPI0_MOSI = 19  -- not 4
  MISO = PIN_SPI0_MISO = 20  -- not 4
  SCK  = PIN_SPI0_SCK  = 18  -- not 4
  SDA  = PIN_WIRE0_SDA = 24  -- not 4
  SCL  = PIN_WIRE0_SCL = 25  -- not 4
(Wire1's SDA=6/SCL=7 are not aliased to the bare SDA/SCL globals in
common.h — only Wire0's are — but neither equals 4 either way.)

CONCLUSION: No collision exists for this board. GPIO4 is not aliased
to any SPI/Wire signal, so build_boards.js's auto-append-bus-capability
behavior will NOT contaminate the confirmed "led_high" tag on GPIO4.
No pins_arduino.h edit was required (unlike adafruit_feather_scorpio,
where the collision was real and the #define was removed). The task
brief's suspicion was reasonable to check but did not pan out for this
particular board — documented here rather than silently assumed.

VENDOR / ONLINE RESEARCH
------------------------
Vendor: Vicharak (vicharak.in / store.vicharak.in), an Indian
electronics company. Product: "Shrike-Lite" — a low-cost RP2040 +
small FPGA (Renesas/Silego SLG47910, 1120 LUTs) combo board, marketed
around $4 (Hackster.io coverage: "The SHRIKE-lite Combines an FPGA and
RP2040 for Just $4").

Sources consulted for the LED pin/polarity and button question:
1. Zephyr RTOS's own official upstream board port for this exact
   board (zephyrproject-rtos/zephyr repo,
   boards/vicharak/shrike_lite/shrike_lite.dts, fetched directly via
   raw.githubusercontent.com — fetched twice independently, both times
   returning matching content):
     leds {
       compatible = "gpio-leds";
       blue_led: blue_led {
         gpios = <&gpio0 4 GPIO_ACTIVE_HIGH>;
         label = "Blue LED";
       };
     };
     aliases {
       fpga-i2c1 = &i2c1;
       watchdog0 = &wdt0;
       led0 = &blue_led;
     };
   This is the single strongest source: an official, actively
   maintained upstream board port (not a community guess) explicitly
   naming GPIO0 pin 4 as a "Blue LED" driven GPIO_ACTIVE_HIGH. No
   gpio-keys (button) node exists anywhere in this devicetree file.
2. TinyGo's board definition for vicharak_shrike-lite
   (tinygo.org/docs/reference/microcontrollers/machine/vicharak_shrike-lite/):
   `LED = IO4` — an independent toolchain's board file agreeing
   exactly on GPIO4 as the LED pin. No button constant is defined for
   this board in TinyGo either.
3. DeepWiki's auto-generated "Complete Pin Reference" for the
   vicharak-in/shrike-lite GitHub repo
   (deepwiki.com/vicharak-in/shrike-lite/10.1-complete-pin-reference):
   lists GPIO4 as "RP2040 user LED indicator", default state "Off"; no
   onboard button or NeoPixel pin listed among RP2040 user I/O.
4. CIRCUITSTATE Electronics "Getting Started with Vicharak Shrike-Lite
   RP2040 + SLG47910 FPGA Development Board" tutorial: states the board
   has "User LEDs: 2" in its features list, plus separate "Debug LEDs"
   (one for RP2040, one for FPGA) and a "Power LED". Cross-referencing
   against DeepWiki's mention of a distinct "FPGA User LED" on "FPGA
   Pin 16", the two "User LEDs" are: (a) the RP2040's GPIO4 blue LED
   confirmed above, and (b) an FPGA-side user LED wired to an FPGA pin,
   not an RP2040 GPIO at all — out of scope for this repo's GPIO-keyed
   tagging (no #define in pins_arduino.h references it either). The
   same tutorial documents onboard Reset and Boot pushbuttons for the
   RP2040 — these are dedicated reset/bootloader-strapping buttons
   (the same category as the classic Pico's BOOTSEL button — see
   rpipico/board.json's note on BOOTSEL not being a normal
   digitalRead()-able GPIO), not wired to any ordinary GPIO, so no
   "button" capability applies to any pin on this board.
5. github.com/vicharak-in/shrike-lite (the repo pins_arduino.h's own
   top-of-file comment cites as its pin source) returned HTTP 404 via
   direct WebFetch — likely a private/renamed/moved repo, or the
   WebFetch tool's GitHub-blob-page limitation. Not load-bearing since
   sources 1-4 above independently corroborate the same GPIO4/active-high
   answer via unrelated projects (Zephyr, TinyGo, DeepWiki, CIRCUITSTATE).

PER-PIN REASONING
------------------
GPIO4 (PIN_LED / LED_BUILTIN):
  - Onboard "Blue LED", confirmed ACTIVE-HIGH by Zephyr's official
    upstream devicetree (GPIO_ACTIVE_HIGH flag), independently
    corroborated by DeepWiki's separate pin-reference page and by
    TinyGo's LED=IO4 definition (three independent projects, same pin).
  - No onboard button is wired to a normal, digitalRead()-able GPIO on
    this board (Reset/Boot are dedicated strapping buttons, not
    exposed as ordinary GPIOs) — no "button" capability applies
    anywhere.
  - No NeoPixel/addressable RGB LED exists on this board per any
    source consulted.
  - Capability set applied: ["digital_output", "pwm_output",
    "led_high"] — digital_input dropped, matching this repo's
    established precedent for dedicated onboard LED pins on plain
    (non-multiplexed) GPIOs (rpipico GPIO25, vccgnd_yd_rp2040 GPIO25).
    pwm_output kept since arduino-pico's analogWrite() works on any
    RP2040 GPIO (enables brightness dimming).
  - No SDA/SCL/SS/MOSI/MISO/SCK collision (see Bus-Collision Check
    section above) — no pins_arduino.h edit needed.

All other GPIOs on this board (UART/SPI0/SPI1/Wire0/Wire1 pins, plus
the D0-D22/A0-A2 fallbacks from generic/common.h) were left at their
chip-level auto-derived defaults — no vendor documentation was found
suggesting any of them carry a button/LED/NeoPixel role, and none
collides with GPIO4.
