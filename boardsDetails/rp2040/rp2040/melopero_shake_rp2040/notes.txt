This file's SPI0/SPI1/Wire0/Wire1/Serial1/Serial2 values are byte-for-byte
identical to the plain Raspberry Pi Pico's generic pins_arduino.h EXCEPT for
Serial2 (8/9 vs Pico's not-pinned-out 31/31) and PIN_LED being unchanged at
25u (also identical to plain Pico). This board's own pins_arduino.h declares
no PIN_BUTTON, PIN_NEOPIXEL, or PIN_BATTERY alias — the real green user LED
(GPIO13), the NeoPixel (GPIO16), and the battery monitor (GPIO17) were all
identified from vendor documentation and official third-party board ports
below, not from this board's own pins_arduino.h PIN_LED macro (which turned
out to be a stale/un-updated boilerplate value — see GPIO13/GPIO25 reasoning
below).

Per-pin reasoning:

GPIO13 (vendor-documented "Green user LED", pico-sdk PICO_DEFAULT_LED_PIN):
  Onboard single green status LED.
  capabilities: ["digital_output", "pwm_output", "led_high"]
  Confirmed as THE LED pin by three independent, cleanly-extracted official
  sources: Melopero's own spec sheet/getting-started guide ("Green user LED
  on pin 13" — sources #1 and #5), Adafruit's compiled CircuitPython board
  port (MP_QSTR_LED -> pin_GPIO13, source #2), and the upstream pico-sdk
  board header (PICO_DEFAULT_LED_PIN 13, source #3). This triple agreement
  is treated as conclusive on WHICH pin is the LED.
  Polarity (active-high) confidence note: no dedicated Arduino/MicroPython
  library or Zephyr devicetree port exists for this specific board (source
  #4/#6) to quote a literal "digitalWrite(13, HIGH) turns the LED on"
  statement from, unlike the Cookie and Scorpio sibling-board audits in this
  same family. Active-high is inferred from two converging, non-guessed
  signals instead: (a) pico-sdk's board header (source #3) defines NO
  PICO_DEFAULT_LED_PIN_INVERTED macro — a macro pico-sdk's own build system
  specifically checks and requires boards to define (as 1) when their LED is
  wired active-low, and does define on boards that need it, so its absence
  here is a real (if indirect) signal from the canonical hardware-description
  source, not silence-as-guess; (b) this repo's own RP2040-family audit
  history is unanimous so far — every board audited (rpipico,
  wiznet_5500_evb_pico, vccgnd_yd_rp2040, adafruit_feather_scorpio,
  melopero_cookie_rp2040) has an onboard status LED independently confirmed
  active-high via library source or devicetree, with zero active-low
  exceptions found in this chip family to date. Flagging this transparently
  per the task's "confirm via real vendor documentation, report NO CHANGE
  rather than guess" standard: this is the one point on this board where the
  evidence is corroborating-but-indirect rather than a literal vendor
  statement, should a future audit uncover a Shake-specific library that
  contradicts it.
  digital_input dropped to match this repo's established led_high precedent
  for dedicated onboard LED pins (rpipico, wiznet_5500_evb_pico,
  vccgnd_yd_rp2040, adafruit_feather_scorpio, melopero_cookie_rp2040);
  pwm_output kept since arduino-pico's analogWrite() works on any RP2040
  GPIO, enabling brightness dimming.
  Bus-alias collision (this audit's known "confirmed pin also aliased to a
  bus role" bug class — see adafruit_feather_scorpio precedent): this
  board's pins_arduino.h originally ALSO declared GPIO13 as PIN_SPI1_SS.
  Sources #2 and #3 both independently document only ONE SPI bus for this
  exact board (SPI0: SCK18/MOSI19/MISO20/CSN1) with no second SPI bus
  referenced anywhere in either the official CircuitPython port or the
  pico-sdk board header — conclusive evidence that this board's
  pins_arduino.h PIN_SPI1_* block (byte-for-byte identical to the plain
  Raspberry Pi Pico's own generic PIN_SPI1_* values) is an unused/spare
  template default carried over when this board's arduino-pico core support
  was scaffolded, not a real, physically-wired second SPI bus. FIXED by
  removing the `#define PIN_SPI1_SS (13u)` line from pins_arduino.h (with an
  inline explanatory comment), keeping PIN_SPI1_MISO/MOSI/SCK as-is, exactly
  matching the adafruit_feather_scorpio PIN_SPI0_SS removal precedent.

GPIO16 (vendor-documented "RGB WS2812 LED (aka NeoPixel)", pico-sdk
PICO_DEFAULT_WS2812_PIN):
  Onboard single WS2812 addressable RGB LED, output-only data line (this
  board has ONE NeoPixel, not a matrix — contrast with the sibling
  melopero_cookie_rp2040's 5x5 matrix).
  capabilities: ["digital_output", "led_neopixel"]
  Confirmed by the same three-source agreement as GPIO13: Melopero's spec
  sheet (source #1/#5), CircuitPython's pins.c (MP_QSTR_NEOPIXEL ->
  pin_GPIO16, source #2), and pico-sdk's board header (PICO_DEFAULT_WS2812_
  PIN 16, source #3).
  digital_input/pwm_output omitted, matching this repo's established
  NeoPixel-tagging vocabulary (vccgnd_yd_rp2040 GPIO23, adafruit_feather_
  scorpio GPIO4, melopero_cookie_rp2040 GPIO17 precedents) — pwm_output is
  not meaningful for a bit-serial/PIO-driven WS2812 data line.
  No bus-alias collision: GPIO16 does not appear anywhere in this board's
  SPI0/SPI1/Wire0/Wire1/Serial1/Serial2 alias list.

NO CHANGE items (left at chip-level default, no chipGpios override — see
board.json's own inline comments for the equivalent reasoning):
  - GPIO17 ("Battery monitor" — vendor-documented low-battery alert output,
    MP_QSTR_BATTERY -> pin_GPIO17 in CircuitPython). No capability tag in
    this repo's established vocabulary (button/led_high/led_low/
    led_neopixel) fits a battery/charge-status monitor signal, and no
    dedicated library accessor exists for it beyond the plain named pin
    alias — identical treatment and rationale to melopero_cookie_rp2040's
    analogous GPIO16 "NEOPIXEL/Qwiic POWER" pin, which received the same NO
    CHANGE disposition in that board's audit.
  - GPIO25 (this board's own arduino-pico pins_arduino.h PIN_LED value,
    left completely unedited/unchanged in pins_arduino.h). This value is
    byte-for-byte identical to the plain Raspberry Pi Pico's own generic
    PIN_LED (25u) and is almost certainly an un-updated leftover from the
    generic Pico variant template used to scaffold this board's arduino-pico
    core support — this board's pins_arduino.h is otherwise identical to
    the plain Pico template apart from its Wire0/Wire1/SPI1/Serial2 pin
    numbers, which WERE customized for the real hardware, while PIN_LED
    apparently was not. None of the three independent official sources
    (#1/#2/#3, all specifically enumerating this board's own real pin
    functions) names any function for GPIO25 on this board; the real,
    triple-source-confirmed green user LED is GPIO13 (tagged above). No
    pins_arduino.h edit was made for GPIO25 since it carries no
    bus-collision risk (GPIO25 does not appear in any SPI/Wire/Serial alias
    on this board) and leaving PIN_LED technically "wrong" but harmless in
    the Arduino core is out of scope for this board.json-focused audit
    (board.json capability tagging operates on real GPIO numbers directly,
    independent of what any #define macro name claims).
  - No accelerometer/gyroscope/IMU/motion-sensor chip exists on this board
    despite the "Shake" product name (confirmed absent via sources #1, #2,
    #3, #4, and #5 above, all independently silent on any such component;
    this board's real onboard peripherals are limited to the LED, single
    NeoPixel, Qwiic/Stemma QT I2C connector, and LiPo battery
    charger/monitor circuitry). No GPIOs are dedicated to a nonexistent
    sensor, so nothing to tag.

JSON validity: verified via a manual `//`-comment-stripped JSON.parse() in
node (no build_boards.js require(), per task instructions) — parses cleanly,

Summary: Confirmed and tagged the two real onboard identity pins on this
board (green user LED GPIO13, active-high inferred with an explicit
transparency note on the indirect nature of the polarity evidence; single
WS2812 NeoPixel GPIO16, output-only) via triple-source agreement across
Melopero's own official documentation, Adafruit's compiled CircuitPython
board port, and the upstream Raspberry Pi pico-sdk board header. Fixed a
confirmed button/LED-pin-also-aliased-as-bus-role collision on GPIO13
(PIN_SPI1_SS) by removing the colliding #define from pins_arduino.h, since
both independent official third-party board ports for this exact board
document only one SPI bus. Explicitly investigated and RULED OUT an onboard
accelerometer/gyroscope/IMU despite the "Shake" product name — none exists;
the name is marketing-only. Left GPIO17 (battery monitor) and GPIO25
(pins_arduino.h's own, apparently stale, PIN_LED value) UNCHANGED at the
chip-level default, both with full reasoning recorded above and in
board.json's inline comments.
