PER-PIN REASONING
- GPIO18/19/20: Confirmed by FOUR independent sources (official Pimoroni datasheet PDF, current
  shop.pimoroni.com product page, forums.pimoroni.com tutorial code, Zephyr board docs) to be a
  SINGLE onboard RGB LED (common-anode / active-low), NOT three separate single-color LEDs and
  NOT the plain single-color LED the PIN_LED alias name might suggest. GPIO19 is the specific
  channel this board's pins_arduino.h aliases as PIN_LED/LED_BUILTIN (its own header comment:
  "Use the Green LED element on pin 19 as LED_BUILTIN") — confirming the task's hint that
  Pimoroni "Tiny" boards have RGB, not single-color, onboard LEDs. Tagged using this repo's
  per-channel RGB vocabulary (precedent: variants/esp32/esp32s3/nora_w10/board.json):
    GPIO18: ["digital_output", "pwm_output", "led_r_low"]
    GPIO19: ["digital_output", "pwm_output", "led_g_low"]  (PIN_LED / LED_BUILTIN)
    GPIO20: ["digital_output", "pwm_output", "led_b_low"]
  pwm_output kept on all three — vendor docs explicitly describe PWM-dimming these pins.
  digital_input dropped, matching this repo's led_high/led_low/led_r_*/led_g_*/led_b_*
  precedent for dedicated onboard LED pins throughout the codebase.

- GPIO23: NOT declared anywhere in this board's pins_arduino.h (no PIN_BUTTON alias), but
  confirmed via the official datasheet's own pinout diagram ("BOOTSEL GP23 — BOOT/DFU mode
  protected by diode") and product-page prose ("Switch for basic input (doubles up as DFU
  select on boot)"; "clever circuitry that lets you use the boot button as a user controllable
  switch... GPIO 23") to be a real, diode-isolated, user-readable GPIO wired to the board's
  physical BOOT switch — distinct from the separate RESET button, which drives the RUN
  (hardware reset) pin directly and is not a GPIO at all (same out-of-scope RESET rationale as
  rpipico/board.json and waveshare_rp2040_zero/board.json). Added purely via a chipGpios entry
  (the general "GPIO absent from pins_arduino.h but present in chipGpios" mechanism already
  supported by build_boards.js's buildEsp32Board(), which unions pins_arduino.h aliases with
  chipGpios keys). Tagged ["digital_input", "button"] — digital_output/pwm_output deliberately
  OMITTED: no vendor source confirms it is electrically safe to drive this diode-coupled
  BOOT/DFU-select line as an output, so the conservative choice matches this repo's existing
  precedent for u-blox EVK-NORA-W10's GPIO0 (SW2/BOOTn, "multifunctional - usable for other
  user functions in software after power-up") in variants/esp32/esp32s3/nora_w10/board.json,
  which likewise received digital_input+button only, no output capabilities, for the same
  "boot-select-multiplexed pin" reason.

BUS-COLLISION CHECK (per task's specific hint re: PIN_SPI0_SS)
This board's own pins_arduino.h declares PIN_SPI0_SS as a dummy value of 17u (its own comment:
"not available on any header pin but needs to be defined for ../generic/common.h so use a
dummy"). The confirmed RGB LED/button pins are 18, 19, 20, and 23 — none of which equal 17 (SS),
4 (MISO/SDA0), 7 (MOSI/SCL1), 6 (SCK/SDA1), or 5 (SCL0). So build_boards.js's unconditional
SS/SDA/SCL/MOSI/MISO/SCK alias auto-append never fires on any tagged pin here — UNLIKE the
adafruit_feather_scorpio precedent (where the vendor default PIN_SPI0_SS DID collide with that
board's confirmed onboard LED pin and had to be removed from pins_arduino.h). No pins_arduino.h
edit needed on this board; the apparent "17 vs 19" proximity flagged in the task brief turned
out not to be an actual collision once the real values were checked.
