Board: iLabs "Challenger RP2040 SD/RTC" (chip bucket: rp2040)
Directory: variants/rp2040/rp2040/challenger_2040_sdrtc/
Audit date: 2026-07-13

SUMMARY
-------
Confirmed the onboard microSD card reader occupies GPIO9-13 (SPI1 CS/SCK/
MOSI/MISO + card-detect) and the onboard Microchip MCP79410 I2C real-time
clock's interrupt/alarm line (MFP, datasheet-named "PIN_RTC_INTERRUPT" but
not an actual macro in arduino-pico) occupies GPIO25. The RTC's I2C bus
itself (Wire0, GPIO0/1) is the board's ordinary shared general-purpose I2C
bus, not RTC-exclusive, so it was left untouched. Created board.json (this
board previously had none) with chipGpios entries for all seven confirmed
dedicated/hardware-identity GPIOs: 9, 10, 11, 12 (SD SPI1 bus, capabilities
emptied), 13 (SD card detect, restricted to digital_input), 24 (onboard
LED, tagged led_high), and 25 (RTC interrupt, restricted to digital_input).
No onboard NeoPixel and no onboard user pushbutton found. pins_arduino.h
was NOT modified - no #define collision/bug-class issue exists on this
board (see "COLLISION BUG CLASS CHECK" below).

COLLISION BUG CLASS CHECK (button/LED pin also aliased as SDA/SCL/SS/
MOSI/MISO/SCK, causing an unwanted auto-appended bus capability)
------------------------------------------------------------------
Not applicable to this board. None of the seven tagged GPIOs (9, 10, 11,
12, 13, 24, 25) carry a bare-named SS/SDA/SCL/MOSI/MISO/SCK alias in this
board's pins_arduino.h - in fact NO GPIO on this board does, since the
file declares no such bare-named `static const uint8_t` globals at all
(only numeric PIN_SPI0_*/PIN_SPI1_*/PIN_WIRE0_* #defines and a `#define SS
SD_SS` macro chain, none of which build_boards.js's parser harvests - see
source #9). This means build_boards.js's unconditional spi_ss/spi_mosi/
spi_miso/spi_sck/i2c_sda/i2c_scl auto-append cannot fire for ANY pin on
this board, dedicated or general-purpose - a pre-existing pins_arduino.h
gap unrelated to this audit (also already flagged, out of scope, on the
challenger_2040_lora/subghz siblings' own notes.txt). No pins_arduino.h
edit was made or needed.

PER-PIN REASONING
------------------
GPIO9 (PIN_SPI1_SS, SD Card #CS): no D-alias in pins_arduino.h; confirmed
  dedicated to the onboard microSD connector's SPI1 chip-select via the
  iLabs datasheet. capabilities: []. Adding this chipGpios entry makes the
  GPIO visible in the Designer pin list (it would otherwise be fully
  concealed, having zero pins_arduino.h alias) alongside an auto-appended
  "Check if available on board" note - accepted per this task's
  instruction to tag every confirmed dedicated-hardware GPIO, matching
  the adafruit_feather_adalogger precedent's choice for its own SD-card
  GPIOs.

GPIO10 (PIN_SPI1_SCK, SD Card SCK): same as GPIO9 - confirmed via iLabs
  datasheet ("GPIO10 is the serial clock (SCK)"). capabilities: [].

GPIO11 (PIN_SPI1_MOSI, SD Card SDO/data-out): same as GPIO9 - confirmed
  via iLabs datasheet ("GPIO11 is the serial data output (SDO)").
  capabilities: [].

GPIO12 (PIN_SPI1_MISO, SD Card SDI/data-in): same as GPIO9 - confirmed
  via iLabs datasheet ("GPIO12 is the serial data input (SDI)").
  capabilities: [].

GPIO13 (SD_CARD_DETECT, also aliased D14): confirmed via iLabs datasheet
  ("D14/GPIO13 card detect (Has a weak external pull (220K) up for low
  power consumption)"). Since this GPIO DOES carry a D14 alias, it is
  already visible in the Designer pin list and would otherwise default to
  full digital_input/digital_output/pwm_output capability via the
  chip-level chipGpios:{} fallback. Restricted to capabilities:
  ["digital_input"] - digital_output/pwm_output dropped since driving
  this pin as an output could contend with the card socket's own switch
  state and the vendor's own external 220K pull-up; digital_input
  retained since reading card presence is a genuine, safe, useful
  operation. Matches this repo's adafruit_feather_adalogger
  PIN_CARD_DETECT and solderparty_rp2350_stamp PIN_CARD_DETECT
  precedent exactly.

GPIO24 (PIN_LED / LED_BUILTIN, D18 alias): tagged ["digital_output",
  "pwm_output", "led_high"]. Presence confirmed by the official iLabs
  datasheet ("This LED is connected to pin D18"). Active-high polarity is
  a cross-referenced inference (this board's own datasheet page does not
  state the polarity - confirmed by a full-page re-search finding no
  "Active"/"active level" text): sibling challenger_2040_wifi's own
  datasheet states "Active level: High" for the identical shared
  reference LED circuit reused across this iLabs product line, and
  sibling challenger_2040_nfc uses the identical GPIO24 pin for its own
  led_high-tagged LED. digital_input capability dropped to match this
  repo's established led_high precedent for dedicated onboard LED pins;
  pwm_output kept since arduino-pico's analogWrite() works on any RP2040
  GPIO, enabling brightness dimming.

GPIO25 (MCP79410 RTC's MFP / datasheet-named "PIN_RTC_INTERRUPT", no
  actual pins_arduino.h macro exists for it - confirmed absent from both
  the local and upstream copies): the onboard MCP79410 real-time clock's
  open-drain interrupt/alarm output signal, driven by the RTC chip and
  merely read by the RP2040. No pins_arduino.h alias exists for this GPIO
  (zero occurrences anywhere in the file), so it would otherwise be fully
  concealed from the Designer pin list; this entry surfaces it (with an
  auto-appended "Check if available on board" note alongside this one,
  same as GPIO9-12) per this task's instruction to tag every confirmed
  dedicated-hardware GPIO. Restricted to capabilities: ["digital_input"] -
  digital_output/pwm_output dropped since driving this pin from the
  RP2040 side would fight the RTC's own drive of the line; digital_input
  retained since reading the RTC's interrupt/alarm flag is a genuine,
  safe, useful operation. Matches this repo's wiznet_5100s_evb_pico INTn
  precedent (dedicated onboard interrupt line, input-only since
  chip-driven).

GPIO0/GPIO1 (Wire0 SDA/SCL, also aliased D7/D8): the RTC's I2C bus per the
  vendor datasheet ("Uses I2C0 (Wire) for communication"), but this is
  the board's ordinary shared general-purpose I2C0 bus (not a second,
  RTC-exclusive channel like challenger_2040_nfc's Wire1-dedicated-to-
  PN7150 arrangement) - a user can wire up additional I2C peripherals on
  the same bus (e.g. via a STEMMA QT-style connector). Left as ordinary
  general-purpose pins, matching the adafruit_feather_adalogger
  precedent's treatment of its own shared Wire bus. No chipGpios override
  applied.

No onboard NeoPixel found - confirmed absent by a full-page re-search of
  the official iLabs datasheet (no NeoPixel/WS2812/addressable-RGB-LED
  text found anywhere on the page) and by the upstream/local
  pins_arduino.h (no NEOPIXEL/PIN_NEOPIXEL define present). No chipGpios
  tag applied.

No onboard user pushbutton found (beyond the standard RP2040 BOOTSEL,
  which is not a normal GPIO on RP2040, out of scope per the
  rpipico/board.json precedent) - confirmed absent by the same full-page
  re-search of the official iLabs datasheet. No chipGpios tag applied.
