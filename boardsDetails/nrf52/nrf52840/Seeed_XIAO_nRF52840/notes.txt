SOURCES CONSULTED
=================
1. This repo's own Seeed_nRF52/variants/Seeed_XIAO_nRF52840/variant.h and
   variant.cpp (the vendor's own BSP, dropped into the repo by the user
   for this import). PRIMARY source for every pin index/meaning — the
   vendor's own g_ADigitalPinMap array comments name each pin's exact
   peripheral role ("// LSM6DS3TR", "// MIC", "// BQ25100", "// On-board
   QSPI Flash", etc). Confirmed the array's inline comments ("D20 is
   P0.26 (LED RED)" etc, continuing "D21".."D32") are STALE/WRONG vendor
   documentation — real Arduino pin index is determined by ARRAY
   POSITION, not the comment text (position 11 = LED_RED per variant.h's
   own #define LED_RED (11), not "D20" as the comment claims). This is a
   comment-only vendor typo with zero functional effect (comments don't
   compile) but would have misled a less careful reading — verified by
   cross-checking every #define in variant.h against its array position
   in variant.cpp, all consistent by position.
2. https://wiki.seeedstudio.com/XIAO_BLE/ (fetched via WebFetch) —
   CONFIRMED: onboard RGB LED is common-anode / active-LOW
   (digitalWrite LOW = on), directly contradicting variant.h's own
   LED_STATE_ON=(1) macro (which would imply active-high if trusted at
   face value) — trusted the wiki over the macro, tagged led_r_low/
   led_g_low/led_b_low, not led_*_high. Also confirmed: no user-
   accessible button pin (PIN_BUTTON1 = PINS_COUNT sentinel, matches);
   NFC1/NFC2 are "free GPIO" per this page's general description (later
   research below narrowed this — see item 3); VBAT_ENABLE(14)/
   PIN_CHARGING_CURRENT(22) purposes; LSM6DS3TR IMU + PDM mic are
   Sense/Sense-Plus-only populated components (base board has the pin
   definitions but unpopulated pads for these).
3. https://forum.seeedstudio.com/t/nrf52840-plus-using-pins-d14-and-d15-as-gpio/295248
   (fetched via WebFetch) — CRITICAL finding, not obvious from the wiki
   alone: P0.09/P0.10 (this board's NFC1/NFC2, Arduino index 30/31) are,
   by nRF52840 SILICON default, latched to the NFC antenna function via
   the UICR NFCPINS register. Using them as plain GPIO requires clearing
   that register bit — a ONE-WAY change (reverting needs a J-Link and
   full chip erase) that none of this core's generated pfodWeb sketches
   ever perform. A plain pinMode()/digitalWrite() on these pins would
   silently do nothing while NFCPINS is still set. This directly
   contradicts a naive reading of item 2's "free GPIO" wiki phrasing —
   trusted the more specific, technically-detailed forum finding.
4. https://docs.cirkitdesigner.com/component/... (Cirkit Designer pinout
   pages, via WebFetch's search-result synthesis) — used only to confirm
   the physical header pinout: base/Sense expose D0-D10 (11 pins) plus
   power/ground on the edge castellated pads; NOTHING at Arduino index
   11 and above is brought out to any header pad on this board (LED,
   IMU, mic, QSPI flash, NFC, VBAT are all internal-only, wired directly
   to onboard components). This is the basis for excluding indices
   11-32 wholesale (they are either genuinely dedicated to onboard
   hardware, or simply have no physical pad a user could wire to).
5. https://learn.adafruit.com/introducing-the-adafruit-nrf52840-feather/nrf52-adc
   (Adafruit's own nRF52 ADC guide, via WebSearch) — confirmed the
   Adafruit-derived core's default analogReference() is AR_INTERNAL
   (0.6V * gain 6 = 0-3.6V), used for this board.json's
   adc.defaultRefVolts. variant.h's own ADC_RESOLUTION(12) macro used
   for adc.bits/max (12-bit, 0-4095).

DECISIONS
=========
KEPT available (plain digital_input/digital_output/pwm_output, plus
analog_input on A0-A5, i2c_sda/scl on D4/D5, spi_ss/sck/miso/mosi on
D7/D8/D9/D10): D0-D10 — the 11 real header-exposed GPIOs, no dedicated
onboard consumer, matches this repo's general "keep general-purpose bus
pins available" policy.

TAGGED (button/led vocabulary): GPIO11/12/13 (LED_RED/BLUE/GREEN) tagged
led_r_low/led_b_low/led_g_low + digital_output + pwm_output. Internal-
only (no header pad) but this is exactly what the led_* capability
vocabulary exists for — letting the Designer offer "control the onboard
LED" without requiring a physical wire. No button tag anywhere (no
physical button pin exists on this board per source #2).

EXCLUDED (capabilities: [], each with a note explaining why):
- GPIO14 (VBAT_ENABLE): control line for the battery-voltage divider;
  needs a specific LOW-then-read-then-HIGH sequence the Designer's plain
  pin types can't express safely, and misuse risks damaging the VBAT pin
  per source #2's own wiki text.
- GPIO15-18 (LSM6DS3TR-C IMU power/SCL/SDA/INT1): dedicated I2C bus +
  control lines to the onboard accelerometer/gyro (unpopulated pad on
  this base board, but same pin definitions and same exclusion
  reasoning as the Sense variant where it IS populated).
- GPIO19-21 (PDM mic power/clock/data): dedicated bus to the onboard
  microphone (unpopulated pad on this base board).
- GPIO22 (PIN_CHARGING_CURRENT): dedicated onboard BQ25100 charge-IC
  configuration pin, not general GPIO.
- GPIO23 (unnamed ~CHG charge-status signal): real per variant.cpp's
  array comment but never aliased by any macro in variant.h, so it is
  not reachable from a sketch on this core at all — documented here for
  completeness, no chipGpios entry actually needed (it simply never
  appears in the generated output since nothing aliases it).
- GPIO24-29 (QSPI flash SCK/CS/IO0-3): dedicated bus to the onboard 2MB
  flash chip.
- GPIO30/31 (NFC1/NFC2): NFC/UICR caveat, source #3.
- GPIO32 (PIN_VBAT): requires the VBAT_ENABLE sequencing from GPIO14,
  which the Designer can't express — see source #2/#4's read-enable
  procedure.

NOT GUESSED: nothing in this board's chipGpios reflects a guess — every
capability/exclusion above traces to a specific source in the list.

SUMMARY: 33 total Arduino pin indices (0-32); 11 kept as plain
general-purpose GPIO (D0-D10), 3 tagged as onboard LED channels
(GPIO11-13), 19 excluded as dedicated-to-onboard-hardware or
UICR/sequencing-constrained (GPIO14-32).
