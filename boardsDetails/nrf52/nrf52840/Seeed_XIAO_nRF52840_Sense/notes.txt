SOURCES CONSULTED
=================
Same sources as boardsDetails/nrf52/nrf52840/Seeed_XIAO_nRF52840/notes.txt
(1-5) — see that file for the full list and per-source findings. This
notes.txt only records what's DIFFERENT about the Sense variant.

Confirmed via `diff` against the vendor's own source
(Seeed_nRF52/variants/Seeed_XIAO_nRF52840/variant.h vs .../
Seeed_XIAO_nRF52840_Sense/variant.h): the two files are byte-for-byte
identical except for the header include-guard name and one extra
`#define TARGET_SEEED_XIAO_NRF52840_SENSE` line. Every pin index,
every macro value, is identical between base and Sense.

Source #2 (https://wiki.seeedstudio.com/XIAO_BLE/) explicitly states the
LSM6DS3TR-C IMU and PDM microphone are populated components ONLY on the
Sense/Sense Plus variants — the base board (and the plain Plus board)
ship the identical pin definitions for GPIO15-21 but leave those pads
unpopulated.

DECISION
========
Because the pin map is identical, this board's board.json chipGpios map
is IDENTICAL to the base board's (same 11 kept, same 3 LED tags, same
19 exclusions) — the populated-vs-unpopulated IMU/mic distinction does
NOT change any keep/exclude decision, since both are "internal, no
header pad, dedicated to an onboard peripheral" either way (populated
or not, a user has no way to wire anything else to those pins). The
notes text for GPIO15-21 in this board's own board.json says "populated
on this Sense variant" instead of the base board's generic "dedicated to
the onboard IMU/mic", purely for documentation accuracy — no capability
difference.

NOT GUESSED: no new research was needed for this board — it inherits the
base board's fully-sourced findings verbatim, since the underlying
hardware pin map is provably identical (byte-diff confirmed).

SUMMARY: identical to Seeed_XIAO_nRF52840 — 11 kept general-purpose
GPIO (D0-D10), 3 onboard LED channels tagged, 19 excluded.

FOLLOW-UP CHECK (2026-09-13, same day, user-requested — "check the Sense
variant's IMU/mic wiki table too"): re-parsed this board's own wiki
table row-by-row (29 rows total, carefully re-extracted from the raw
HTML using a tag-boundary-aware parser after the first parse attempt
silently returned empty cells due to this page's HTML omitting
`</td>` closing tags — a second parsing gotcha worth remembering for any
future re-check of this same page).

Found the wiki table is INCOMPLETE for this board's IMU/mic pins: it
lists only "6 DOF IMU_PWR" (P1.08) and "6 DOF IMU__INT1" (P0.11) for the
IMU, and "PDM Microphone_DATA" (P0.16) and "PDM Microphone_CLK" (P1.00)
for the mic — it does NOT have a row for the IMU's I2C bus (Wire1 SCL
P0.27 / SDA P0.07, GPIO16/17 in this board's chipGpios) or for
"PDM Microphone_PWR" (P1.10, GPIO19). Both are real, named signals in
Seeed's own vendor source (`PIN_WIRE1_SCL`/`PIN_WIRE1_SDA` and
`PIN_PDM_PWR` in `variant.h`, needed for the LSM6DS3TR-C to actually be
addressable over I2C and for the mic to actually power up) — the wiki
table's marketing-level pinout summary simply isn't exhaustive here.
Confirmed the same 3-row gap exists on the Sense Plus board's own table
too (spot-checked, see that board's notes.txt).

This does NOT change any exclusion decision — GPIO16/17/19 were already
correctly excluded (dedicated IMU I2C bus / mic power line) based on the
primary vendor source (`variant.h`/`variant.cpp`), which remains
authoritative and complete regardless of the wiki table's gaps. Recorded
here so a future reviewer doesn't mistake the wiki table's silence on
these 3 pins for evidence they don't exist or aren't dedicated — they
do, and are, per the vendor's own source code.

Also independently re-confirmed the LED polarity/pin-assignment finding
via a THIRD method this pass, per the user's own direct schematic read:
the schematic shows all three RGB LED channels wired active-LOW at
P0.06 (blue), P0.30 (green), P0.26 (red) — an exact match, pin-for-pin,
with this repo's own chipGpios entries (GPIO12=LED_BLUE=P0.06,
GPIO13=LED_GREEN=P0.30, GPIO11=LED_RED=P0.26, all tagged led_*_low).
Three independent sources (wiki body text, initVariant() boot behavior,
and now the schematic directly) all agree — no ambiguity remains on
this point.
