What "esp32s2usb" actually is:
- This is NOT a distinct physical product with its own PCB/silkscreen. It
  is a generic Arduino-ESP32 core BUILD VARIANT ("ESP32S2 Dev Module (USB
  CDC/MSC on boot)"-style target) used to build firmware for the ESP32-S2's
  native USB-OTG peripheral (CDC serial + firmware-update-over-MSC), for
  flashing onto ANY ESP32-S2 board that has USB D+/D- wired out (e.g.
  DevKitC-1, Saola-1, or any other native-USB ESP32-S2 board). Its
  USB_MANUFACTURER/USB_PRODUCT strings ("Espressif Systems" /
  "ESP32-S2-USB") are just the default USB descriptor text the compiled
  firmware presents to a host PC, not a marketing name for a specific
  purchasable board. This explains why the file defines no LED/button/
  NeoPixel: the variant is hardware-agnostic by design, only fixing the
  generic pin defaults (UART/I2C/SPI/ADC/touch/DAC) that are common to the
  chip, plus the USB descriptor strings that differentiate this variant's
  firmware from the plain "esp32s2" (UART-only) variant.
- espboards.dev's ESP32S2 Native USB pinout page (source 2) independently
  corroborates this: it flags the board as a "generic match" against
  esp32-s2-saola-1's PlatformIO board id, i.e. treats it as a reference/
  generic board rather than a uniquely branded product.

Onboard LED/button/NeoPixel check:
- pins_arduino.h itself: no LED_BUILTIN, no RGB_BUILTIN, no BUTTON/BOOT
  alias anywhere in the file.
- espboards.dev (source 2) pin-legend check: the page's generic symbol key
  includes a "Built-in LED" glyph (used site-wide across many of their
  board pages), but when asked to enumerate every labeled pin in this
  specific board's detailed pin-mapping table, NO GPIO is actually tagged
  LED or LED_BUILTIN - the legend entry is unused boilerplate for this
  board, not a real assignment. This matches pins_arduino.h having no LED
  macro at all.
- No product page, teardown, or schematic was found describing an onboard
  LED, RGB/NeoPixel, or general-purpose pushbutton for this variant, since
  it isn't a physical product to begin with (see above) - only the
  standard chip-level GPIO0 BOOT strapping pin exists, already covered by
  the chip-level board.json's pinNotes ("Must be HIGH for normal boot"),
  and per this codebase's established precedent (pico32, XIAO_ESP32S3,
  um_tinys3, amyboard) a bare BOOT/RST bootloader-entry pair is not tagged
  as a general-purpose "button" capability without explicit vendor
  confirmation of sketch-readable use - which doesn't exist here either.

Alias-collision check (per this session's methodology - a GPIO tagged

- Not applicable - no button/LED/NeoPixel candidate GPIO was found at all

  (Noted in passing: GPIO8 already carries three aliases here - SDA, A7,
  and T8 - but this is normal multi-alias overlap for a single physical
  ESP32-S2 pin, not a button/LED candidate, so it needs no action.)

Chip-level board.json coverage check:
- variants/esp32/esp32s2/board.json (chip default, no per-board override
  exists or is needed) already lists chipGpios entries for every GPIO this
  variant's aliases reference: TX(43)/RX(44) -> digital_input/output/pwm;
  SDA(8)/SCL(9) -> analog_input+digital+pwm; SS(34)/MOSI(35)/MISO(37)/
  SCK(36) -> digital_input/output/pwm; A0-A19 and T1-T14 map to GPIO1-20,
  all present with analog_input where the chip supports it; DAC1(17)/
  DAC2(18) -> dac_output, matching the chip.json comment "ESP32-S2 has two
  8-bit DAC channels on GPIO 17 and GPIO 18." GPIOs 19-20 (USB D-/D+,
  correctly excluded from chipGpios) are not referenced by any alias in
  this file, confirming the variant doesn't clash with the chip-level USB
  exclusion. Nothing in this variant requires an addition, exclusion, or
  correction to the chip-level default.

build variant for the ESP32-S2's native USB-OTG (CDC+MSC firmware-update)

was created; this notes.txt is the sole record of the review so the board
is not re-flagged in a future sweep.
