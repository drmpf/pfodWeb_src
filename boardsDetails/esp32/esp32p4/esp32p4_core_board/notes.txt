Virtual-pin resolution (LED_BUILTIN):
  pins_arduino.h defines:
    #define PIN_RGB_LED 44
    static const uint8_t LED_BUILTIN = SOC_GPIO_PIN_COUNT + PIN_RGB_LED;
  This is the same offset-encoding gotcha seen on Unexpected Maker boards this session
  (RGB_BUILTIN = PIN_NEOPIXEL + SOC_GPIO_PIN_COUNT): LED_BUILTIN is NOT a real GPIO number - it is a
  sentinel value that the Arduino-ESP32 core's digitalWrite()/rgbLedWrite() layer detects and
  redirects to the RMT-driven addressable-LED driver on the REAL underlying pin, PIN_RGB_LED = GPIO44.
  So the addressable RGB LED genuinely lives on GPIO44, not on some GPIO "80-something" virtual
  number. build_boards.js does not resolve this encoding, so it was resolved manually here from the
  vendor header alone (self-consistent, no external source needed to establish the real GPIO number -
  only used external sources to look for corroborating product documentation and to check for a
  physical button).

Bus-alias collision check (per this session's repeated build_boards.js gotcha):
  GPIO44 was checked against every other alias/const in the file: SDA(7), SCL(8), SS(30), MOSI(33),
  MISO(32), SCK(31), TX(37), RX(38), A0-A7(16-23), T0-T13(2-15). No collision - GPIO44 is not
  aliased as any bus pin anywhere in this file, so no boilerplate bus-alias line needed deleting.
  (GPIO35/36, the strapping/BOOT_MODE pins under consideration for a button tag, were checked too -
  also no bus-alias collisions - but the check is moot since neither was tagged.)

Tagged:
- GPIO44 -> "led_neopixel". Confirmed directly from vendor pins_arduino.h (#define PIN_RGB_LED 44,
  used as the real pin behind the LED_BUILTIN/RGB_BUILTIN virtual-pin encoding for the new
  rgbLedWrite() API). Capabilities changed from
  ["digital_input","digital_output","pwm_output"] to
  ["digital_output","led_neopixel","pwm_output"] (digital_input dropped), matching this repo's
  established led_neopixel tagging convention.

Considered but NOT tagged:
- GPIO35 ("BOOT_MODE 35" comment) and GPIO36 ("BOOT_MODE2 36 pullup" comment) - considered as
  candidates for a "button" capability tag because ESP32-P4 dev boards commonly wire a physical BOOT
  pushbutton to GPIO35 (confirmed generically true by esptool/Espressif documentation, and confirmed
  board-specifically true for the sibling dfrobot_firebeetle2_esp32p4 variant via DFRobot's own wiki).
  However, for THIS specific "ESP32P4 Core Board" variant:
    - pins_arduino.h has only a bare comment, no #define, and the identical comment text is copied
      verbatim across all four ESP32-P4 variants in this repo regardless of whether they have a
      confirmed physical button (dfrobot=yes, m5stack_tab5=no tag applied) - so the comment alone is
      not board-specific evidence.
    - No single vendor product could be confidently identified as THE exact hardware this official
      Espressif Arduino-core variant models (multiple similarly-named "P4 + C6 core board" products
      exist from different vendors with differing GPIO/SDIO wiring, none matching this variant's
      GPIO47-54 SDIO pin assignment exactly).
    - The one closely-matching candidate product page found (Spotpear ESP32-P4-C6 Module Core Board)
      explicitly describes GPIO36 as a bare pull-up/pull-down pad, not a soldered pushbutton, and does
      not mention any onboard RGB LED - consistent with (not contradicting) leaving both unconfirmed
      hardware features untagged here, though this is a different vendor product so it is not treated
      as authoritative for this variant either way.
  This is a deliberate no-guess decision, consistent with the same policy already applied to
  m5stack_tab5 in this repo for the identical boilerplate comment. Left completely untagged; a human
  reviewer with the exact vendor's schematic for the specific physical board Espressif modeled this
  Arduino-core variant on could confirm/deny a physical BOOT button and its real GPIO if desired.

Summary of changes made: Tagged GPIO44 capabilities to
["digital_output","led_neopixel","pwm_output"] in board.json (onboard addressable RGB LED, resolved
from the LED_BUILTIN/RGB_BUILTIN virtual-pin offset encoding in pins_arduino.h to its real GPIO 44).
Added a pfodWeb NOTE comment block at the top of board.json documenting this and the button
non-decision. No button was tagged - no board-specific vendor confirmation of a physical BOOT/user
pushbutton was found for this exact "ESP32P4 Core Board" variant (only generic ESP32-P4 strapping-pin
behavior and boilerplate comment text shared across unrelated sibling variants, some tagged, some not).
No bus-alias collisions were found for GPIO44 (or for GPIO35/36, moot since untagged), so no
boilerplate alias lines needed deleting from pins_arduino.h.
