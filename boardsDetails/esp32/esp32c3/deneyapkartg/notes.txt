Trigger
-------
Discovery sweep flagged this board's pins_arduino.h for declaring:
  static const uint8_t GPKEY = 9;
  #define KEY_BUILTIN GPKEY / BUILTIN_KEY GPKEY / BT GPKEY
  #define TX1 TX / RX1 RX
  static const uint8_t PWM0 = 0; PWM1 = 1; PWM2 = 3;
and asked to check PWM0/1/2 (GPIO0/1/3) against this board's TX/RX for a
collision, given the classic ESP8266/ESP32 default TX=1/RX=3 numbering
made GPIO1/GPIO3 look suspicious at a glance.

Full pins_arduino.h contents reviewed (57 lines). Key declarations:
  LED_BUILTIN = SOC_GPIO_PIN_COUNT + 10  (virtual RGB LED sentinel, D3)
  GPKEY = 9         (KEY_BUILTIN/BUILTIN_KEY/BT)
  TX = 21, RX = 20  (TX1/RX1 aliases)
  SDA = 8, SCL = 2
  SS = 7, MOSI = 6, MISO = 5, SCK = 4
  A0..A5 = 0,1,3,4,5,6
  D0..D6 = 20,21,9,10,8,7,2
  PWM0 = 0, PWM1 = 1, PWM2 = 3

TX/RX collision check (per playbook precedent)
-----------------------------------------------
The sibling board `deneyapkart` (no "g" suffix; a different, older
ESP32 - not ESP32-C3 - product from the same vendor) was audited in an
earlier session and is the canonical example of a TX/RX hard-reservation
bug: its onboard RGB LED pins (LEDG=1, LEDR=3) coincided with that
board's TX=1/RX=3, so build_boards.js's serial hard-reservation would
silently discard any chipGpios tag placed on them, and they were
deliberately left untagged as a documented consequence.

For deneyapkartg, this board's own TX/RX pins are TX=21, RX=20 (the
ESP32-C3's default USB-Serial/JTAG UART0 pins), NOT GPIO0/1/3. PWM0/
PWM1/PWM2 sit on GPIO0/1/3 and GPKEY sits on GPIO9 - none of these
overlap GPIO20/21. This was confirmed two ways: (a) directly from this
board's own pins_arduino.h values, and (b) independently from the
espboards.dev pin-mapping table, which lists the same RX=GPIO20/
TX=GPIO21 and PWM0=GPIO0/PWM1=GPIO1/PWM2=GPIO3 assignments.

CONCLUSION: No TX/RX collision exists on this board for GPKEY or for
PWM0/1/2. The "GPIO1/GPIO3 looks suspicious" flag from the discovery
sweep was a false alarm specific to the classic Arduino Uno/ESP8266
TX=1/RX=3 convention; this ESP32-C3 board uses different UART pins
(20/21) entirely, so no pin here had to be left untagged for this
reason - unlike the deneyapkart sibling board.

Alias-conflict check (SDA/SCL/SS/MOSI/MISO/SCK contamination)
----------------------------------------------------------------
Checked whether GPIO9 (GPKEY/button) is aliased anywhere else in this
file as SDA(8)/SCL(2)/SS(7)/MOSI(6)/MISO(5)/SCK(4). It is not - none of
those pin numbers equal 9. GPIO9 is separately aliased as D2=9, which is
just a plain digital-pin label (not an SPI/I2C role) and does not
contaminate the button's capability list. No pins_arduino.h edit was
needed (contrast with the earlier waveshare_esp32_c3_zero case this
session, where GPIO9 was also aliased SCL and that line had to be
deleted).

Action taken
------------
Created board.json as a full copy of the chip-level esp32c3/board.json
default, with one change: GPIO9's capabilities changed from the default
["digital_input","digital_output","pwm_output"] to ["digital_input",
"button"], matching this repo's established button-tagging precedent
(adafruit_qtpy_esp32c3, waveshare_esp32_c3_zero). The chip-level
pinNotes entry "9": "Must be HIGH for normal boot" (standard ESP32-C3
strapping-pin warning) was retained as-is.

GPIO0/1/3 (PWM0/PWM1/PWM2) were left unchanged from the chip-level
default (they already carry the full analog_input/digital_input/
digital_output/pwm_output capability set appropriate for general-purpose
PWM/analog pins) - no serial-only forcing applies to them since they do
not coincide with this board's TX(21)/RX(20).

No pins_arduino.h edit was made (no alias contamination found).
