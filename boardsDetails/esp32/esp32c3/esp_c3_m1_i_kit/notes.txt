Audit date: 2026-07-12
Task type: dedicated-hardware pin-exclusion audit (two flagged self-collisions/USB-share

DECLARATIONS AUDITED (from this board's own pins_arduino.h):
  LED_WARM = 18, LED_COLD = 19   (file's own comment: "also connected to USB D- and D+")
  LED_RED = 3, LED_GREEN = 4, LED_BLUE = 5   ("RGB LED")
  TX=21, RX=20, SDA=8, SCL=9, SS=7, MOSI=6, MISO=5, SCK=4 (SCK/MISO collided with

CONCLUSIONS / WHAT WAS APPLIED:

1. GPIO18/19 (LED_WARM/LED_COLD): CONFIRMED shared with native USB D-/D+ by the vendor's
   own pin table (source #2, corroborated by #3). The chip-level board.json already
   excludes GPIO18/19 for exactly this reason. No board.json change was needed or
   possible for these two pins - documented in this board's new board.json header comment
   as a rare confirmed case of a real onboard LED whose pin cannot be offered because it
   is already committed to native USB. NOT tagged, NOT re-added to chipGpios.

2. GPIO3/4/5 (LED_RED/LED_GREEN/LED_BLUE): CONFIRMED genuine onboard discrete RGB LED by
   the vendor spec (source #2, directly applicable per its own "shares the same schematic
   diagram" statement). Kept available in the new board.json (chipGpios entries unchanged
   from the chip-level default's capability lists - analog_input/digital_input/
   digital_output/pwm_output on GPIO3/4, analog_input_serial/digital_input/
   digital_output/pwm_output on GPIO5). NOT tagged led_r_high/led_g_high/led_b_high (or
   the _low variants): despite the RGB LED's existence and exact pin mapping being
   confirmed with high confidence from a primary vendor document, no source found (PDF
   text, secondary pinout sites, vendor site) states the drive polarity, and the one
   available schematic image could not be rendered/inspected in this environment. Per
   this project's established "never guess LED polarity" policy (see e.g.
   variants/esp32/esp32c3/sparkfun_pro_micro_esp32c3/board.json for the identical
   could-not-confirm situation on a sibling ESP32-C3 board), each of GPIO3/4/5 was given
   an informational "note" field on its chipGpios entry instead of a polarity tag.

3. GPIO4/GPIO5 self-collision with this file's own SCK/MISO aliases: this is a genuine
   in-file collision (not a shared common.h issue), so fixed by deleting the SCK and MISO
   declaration lines directly from pins_arduino.h (SS and MOSI kept unchanged; GPIO3 has
   no equivalent collision - its only other alias is A3, which is expected/harmless).
   Deletion documented with a plain-English NOTE comment in the file (no literal old
   declaration text reproduced, per the comment-blind-parser rule).

SUMMARY: GPIO18/19 confirmed already-excluded-at-chip-level for USB D-/D+ sharing (no
action needed/possible); GPIO3/4/5 confirmed genuine discrete RGB LED and kept available
but left untagged for polarity (unconfirmed, schematic image unreadable in this
environment); SCK/MISO self-collision with LED_GREEN/LED_BLUE fixed by deleting those two
alias lines from pins_arduino.h. New board.json created (full copy of the chip-level
default plus the above documentation and per-pin notes).
