===============================================================================
BOARD IDENTITY
===============================================================================
Real, commercially shipping hardware: Valetron Systems VALTRACK-V4-VTS-ESP32-C3,
a 4G-LTE/2G vehicle GPS tracking device ("VTS" = Vehicle Tracking System). Sold
on Crowd Supply, Tindie, and the vendor's own store (valetron.com), targeted at
the Indian market (INR pricing seen in secondary sources). IP67-sealed
enclosure, 52x65x30mm, 12-42V DC vehicle power input with reverse-polarity
protection, 3.7-4.2V Li-Po/Li-Ion backup battery.

Core silicon confirmed via multiple independent sources:
  - Espressif ESP32-C3FH4 (RISC-V, 2.4GHz WiFi+BLE, 4MB inbuilt flash) - main MCU.
  - SIMCom A7672S (regional variants of the A7672 series) - 4G-LTE-CAT1/2G
    cellular modem with inbuilt GNSS, U.FL antenna connector.
  - LIS3DH - 12-bit 3-axis accelerometer (I2C).
  - MP2617 / MP2617A - Li-ion battery charger IC with power-path management.
  - TPS54240 - buck (step-down) power converter.
  - MIC94060YC6 - load/power switch, used per teardown for modem power gating.
  - 3x addressable RGB LEDs (WS2812/NeoPixel-style, parts U51/U52/U53),
    driven via the Adafruit_NeoPixel library per the vendor's own firmware repo.
  - A level-translator IC bridging the modem's 1.8V I/O domain to the
    ESP32-C3's 3.3V logic (explains the need for a dedicated second UART
    rather than sharing the main UART0).

A sibling board, VALTRACK_V4_MFW_ESP32_C3 ("MFW" = mobile field worker
variant, a different physical product per Valetron's own product pages),
shares byte-identical GPIO_* pin declarations in its own pins_arduino.h -
confirmed independently in this session by directly grepping that file
(variants/esp32/esp32c3/VALTRACK_V4_MFW_ESP32_C3/pins_arduino.h). It is being
audited separately (potentially by a parallel session/agent) since it is a
distinct commercial product even though the two share firmware/GPIO
conventions - see the vendor's own GitHub repo name:
"Source code for VALTRACK-V4-VTS-ESP32-C3 & VALTRACK-V4-MFW-ESP32C3 designs".

===============================================================================
PER-PIN REASONING (confirmed vs. judgment-call distinction)
===============================================================================

GPIO0 / GPIO1 (TX1 / RX1) - EXCLUDED.
  Status: vendor-corroborated (not a pure name guess), but no single source
  explicitly states "TX1/RX1 connects to the cellular modem" in so many
  words. Reasoning chain: vendor firmware repo confirms a genuine second
  UART ("UART1") distinct from the main UART0 (TX/RX = GPIO21/20); the
  independent teardown confirms a level-translator IC bridging the SIMCom
  A7672S modem's 1.8V UART to the ESP32's 3.3V logic, and no other
  UART-capable onboard peripheral is documented anywhere. Putting these two
  facts together is a strong, well-supported inference, not a leap from the
  macro name alone (the macro name here is generic - "TX1/RX1" - it doesn't
  even self-declare its purpose the way GPIO_PWRKEY or GPIO_GSM_ENABLE do).

GPIO2 (GPIO_ANALOG_IN) - KEPT, default capabilities unchanged, no tag added.
  Status: name-based judgment call, NOT vendor-confirmed. No source found
  states what this pin actually measures. Left available per playbook policy
  (KEEP category covers analog sensor readings: voltage/battery monitors,
  etc.), consistent with this being a vehicle tracker with backup-battery and
  wide-range DC input - both plausible candidates for what this pin senses -
  but this is explicitly NOT confirmed and is documented as such in the
  board.json "note" field on GPIO2's chipGpios entry.

GPIO3 (GPIO_INT1) - EXCLUDED.
  Status: vendor-corroborated. LIS3DH accelerometer confirmed onboard via
  two independent sources (vendor spec page + third-party teardown); "INT1"
  is literally the LIS3DH datasheet's own signal name for its first
  interrupt output pin. High confidence.

GPIO4 (GPIO_TPS_ENABLE and GPIO_CHG_IN - both alias GPIO4) - EXCLUDED
  (regardless of which declaration the compiled firmware actually uses).
  Status: vendor-corroborated for BOTH candidate identities, ambiguity
  intentionally left unresolved because it doesn't change the outcome.
  The teardown independently confirms both a TPS54240 buck converter
  (matching "TPS_ENABLE" - an enable line for this regulator) and an
  MP2617A battery charger with power-path management (matching "CHG_IN" - a
  charge-input/status line) are real onboard chips. No firmware source file
  was examined line-by-line to determine which of the two `static const`
  declarations is actually referenced by application code (both compile
  fine as C++ - re-declaring the same integer value under two different
  names is not a compiler error, so this is not necessarily a bug, possibly
  just two menu/config variants or legacy naming). Whichever is "real", GPIO4
  is dedicated to one of two onboard power-management ICs either way, so
  EXCLUDE is correct under both readings - this was a deliberate decision
  to not need to resolve the ambiguity rather than an oversight.

GPIO5 / GPIO6 (GPIO_IIC_DATA / GPIO_IIC_CLOCK, also the standard SDA/SCL
aliases) - EXCLUDED.
  Status: vendor-corroborated. This is the I2C bus wired to the onboard
  LIS3DH accelerometer. Per playbook policy, I2C buses are normally KEPT
  available by default (multi-drop, often has headroom for a user's own
  device) unless there's a documented exclusive onboard consumer AND no
  accessible header - both apply here: LIS3DH is a confirmed exclusive
  consumer, and the product is a sealed IP67 enclosure with no external I2C
  breakout documented anywhere in any source consulted.

GPIO7 (GPIO_PWRKEY) - EXCLUDED.
  Status: vendor-corroborated by strong name-pattern + confirmed-chip match.
  "PWRKEY" is the standard, universal name SIMCom uses for its cellular
  module power-on control line across its entire module family reference
  designs; the A7672S modem is independently confirmed onboard via two
  sources. High confidence despite no single source showing this exact pin
  wired in a schematic.

GPIO8 (GPIO_LED_SIGNAL) - KEPT, tagged capabilities:
  ["digital_output", "led_neopixel", "pwm_output"].
  Status: vendor-confirmed. Vendor firmware repo/docs explicitly describe 3
  cascaded WS2812/NeoPixel-style RGB LEDs (U51/U52/U53) driven via the
  Adafruit_NeoPixel library (NEO_GRB+NEO_KHZ800) on this pin - a specific,
  unambiguous technical description, not just a name match. Confirmed not
  the board's TX/RX/TX1/RX1 (21/20/0/1) before tagging, per playbook 7a's
  required pre-check. pwm_output included per this repo's existing
  led_neopixel precedent (e.g. waveshare_esp32_s3_zero's GPIO21 entry),
  since the pin supports the chip's LEDC peripheral at the silicon level.

GPIO9 (GPIO_SOS) - KEPT, tagged capabilities: ["digital_input", "button"].
  Status: well-corroborated judgment call, explicitly NOT fully
  vendor-schematic-confirmed - flagged here per the task's own guidance to
  distinguish this tier clearly. The vendor firmware docs page (source 3)
  independently glosses this pin as "SOS/Switch button" (going beyond just
  restating the pins_arduino.h macro name), and AIS-140's regulatory
  requirement for a hard-wired panic button on Indian commercial-vehicle
  trackers (source 7) is strong circumstantial support for a real physical
  button existing on this exact product category. However, no source
  supplies a schematic or product photo explicitly pointing at a physical
  SOS button component/switch on this specific PCB. Tag applied because the
  combined evidence (name + independent vendor gloss + regulatory context +
  real commercial VTS product) clears a reasonable bar, but a future
  reviewer should treat this as corroborated-not-proven if stricter
  evidence is later required. Confirmed not the board's TX/RX/TX1/RX1
  (21/20/0/1) before tagging.

GPIO10 (GPIO_GSM_ENABLE) - EXCLUDED.
  Status: vendor-corroborated. Teardown independently confirms a
  MIC94060YC6 load/power switch used for modem power control; "GSM_ENABLE"
  directly matches this function (gating power to the A7672S modem/its
  supply rail). High confidence.

GPIO11 - no chipGpios change (not aliased anywhere in this board's
  pins_arduino.h, either before or after this audit's edits). Left at the
  esp32c3 chip-level default, unlabeled.

GPIO20 / GPIO21 (RX / TX) - unchanged, this is the board's primary/main
  UART used for the pfod Serial connection (confirmed by this being the
  standard Arduino-core UART0 default for ESP32-C3, distinct from the
  modem's dedicated UART1 on GPIO0/1 discussed above). Not part of this
  exclusion audit's scope - kept as the board's designated Serial pins.

ONE-LINE SUMMARY
===============================================================================
VALTRACK_V4_VTS_ESP32_C3 is a real Valetron Systems 4G-LTE vehicle GPS
tracker (ESP32-C3 + SIMCom A7672S modem + LIS3DH accelerometer + MP2617A
charger + TPS54240 regulator + 3x NeoPixel status LEDs); excluded GPIO0/1
(modem UART), GPIO3 (accelerometer INT1), GPIO4 (TPS enable / charger input,
vendor-corroborated dual-purpose ambiguity), GPIO5/6 (accelerometer I2C),
GPIO7 (modem PWRKEY), and GPIO10 (modem GSM enable, MIC94060YC6 load
switch) - all vendor-corroborated via the official firmware repo, vendor
spec/firmware doc pages, and an independent third-party teardown; kept and
tagged GPIO8 as led_neopixel (vendor-confirmed 3x WS2812 status LEDs) and
GPIO9 as button (well-corroborated via vendor doc gloss + AIS-140 regulatory
context, but explicitly flagged as not fully vendor-schematic-proven); kept
GPIO2 (GPIO_ANALOG_IN) at default capabilities as an undocumented,
name-based-judgment-call analog sensing input.
