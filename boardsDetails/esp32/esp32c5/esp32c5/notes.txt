     LP_GPIO2..LP_GPIO5 are the chip's fixed low-power I2C/UART

     on every ESP32-C5 module, not evidence of an onboard device on this
     specific reference board.

     fixed subset of GPIOs, separate from the HP (main) core's
     general-purpose I2C/UART controllers which can be routed to any
     GPIO via the standard GPIO matrix.

Reasoning:
  GPIO27 (PIN_RGB_LED): CONFIRMED real onboard WS2812 NeoPixel, stated by
  Espressif's own official user guide for the exact physical reference
  board this generic entry models. High confidence - primary vendor
  source, plus independent third-party corroboration (esp32.co.uk).
  Tagged capabilities ["digital_output","led_neopixel","pwm_output"],
  matching this repo's existing led_neopixel precedent (esp32c6/esp32c6
  GPIO8, waveshare_esp32_s3_zero GPIO21, adafruit_qtpy_esp32c3 GPIO2).

  Alias-collision check (this session's new playbook step): compared
  GPIO27 against this variant's own TX/RX/SDA/SCL/SS/MOSI/MISO/SCK alias
  list (11/12/0/1/6/8/9/10) and the A0-A5 analog alias list
  (1/2/3/4/5/6) - GPIO27 appears in neither. No conflicting boilerplate
  bus alias exists for this pin (build_boards.js's unconditional
  SDA/SCL/SS/MOSI/MISO/SCK/TX/RX-append behavior does not fire here). No
  pins_arduino.h edit was needed.

  Also noted: GPIO27 is itself listed as a strapping pin in Espressif's
  official user guide, but the chip-level board.json's pinNotes (sourced
  from the ESP32-C5 Technical Reference Manual's strapping-pin section)
  only lists GPIOs 4, 5, 6, and 23 as boot-mode-sensitive. Left
  pinNotes unchanged - adding a GPIO27 strapping note was not directly
  TRM-sourced during this audit and is out of scope for the LP-pin/RGB
  question this task targeted; flagging here for a possible future
  chip-level pinNotes review.

  LP_SDA=2/LP_SCL=3 (LP-domain I2C, WIRE1/SDA1/SCL1) and LP_RX=4/LP_TX=5
  (LP-domain UART): KEEP as general-purpose GPIOs. Espressif's own
  pin-function table shows these are simply the chip's fixed LP_I2C/
  LP_UART controller pins - a hardware pin-mux constraint of the ESP32-C5
  LP (low-power) core, which has its own small dedicated set of I2C/UART
  peripheral instances separate from the HP (main) core's I2C/UART (which
  can be routed to any GPIO via the GPIO matrix). This is architecturally
  different from "a second bus wired to an onboard chip" - it just means
  GPIO2/3/4/5 are the ONLY pins capable of driving the LP-domain I2C/UART
  hardware blocks, should a sketch choose to use them. No onboard
  peripheral consumer of the LP bus is documented on the DevKitC-1
  reference board - the LP_SDA/SCL/RX/TX names describe a capability, not
  a dedicated wiring. A user sketch remains free to use GPIO2/3/4/5 as
  plain digital or analog GPIOs. Left unchanged from chip-level defaults
  (GPIO2/3/4/5 all already carry analog_input+digital_input+
  digital_output+pwm_output, matching their A1/A2/A3/A4 analog aliases).
