um_tinyc6 (chip: esp32c6) - Unexpected Maker TinyC6
Button/LED capability-tagging audit (playbook section 7a) - 2026-07-12

CONTEXT
-------
This board already had a board.json from an earlier dedicated-hardware
pin-exclusion pass (sections 1-6): it excludes GPIO22 (RGB_PWR, the
NeoPixel's internal power-gate line) from chipGpios. That earlier pass
never applied the section 7a button/LED capability tags. This session's
task was to apply those tags only, using the virtual-pin resolution hint
from sibling boards um_edges3_d/um_nanos3 (RGB_BUILTIN = PIN_NEOPIXEL +
SOC_GPIO_PIN_COUNT convention).

PER-PIN REASONING
------------------
GPIO23 (RGB_DATA / RGB_BUILTIN virtual pin) - TAGGED
  Virtual-pin resolution: pins_arduino.h defines
  "RGB_BUILTIN = RGB_DATA + SOC_GPIO_PIN_COUNT", which is a virtual pin
  number (SOC_GPIO_PIN_COUNT is a compile-time chip-pin-count constant,
  not itself a GPIO) - build_boards.js's regex-only parser has no way to
  evaluate that arithmetic expression, so it cannot resolve RGB_BUILTIN
  to a real pin on its own. The real underlying GPIO is simply the value
  stored in RGB_DATA, i.e. 23 - confirmed both by pins_arduino.h's own
  "static const uint8_t RGB_DATA = 23;" line and independently by the
  vendor schematic's DI-to-IO23 wiring (source 3 above).
  Alias-collision check: this board's SDA/SCL/SS/MOSI/MISO/SCK/SDO/SDI
  aliases resolve to 6/7/18/21/20/19/21/20 respectively - none equal 23,
  so tagging GPIO23 will not cause build_boards.js to append a spurious
  i2c_*/spi_* capability alongside led_neopixel. No pins_arduino.h edit
  was required.
  TX/RX check: TX=16, RX=17 - GPIO23 is neither, so the tag will not be
  silently discarded by the hard TX/RX capability override.
  Applied: chipGpios["23"].capabilities =
    ["digital_output", "led_neopixel", "pwm_output"]
  (pwm_output kept since GPIO23 supports it at the chip level per the
  pre-existing chip-level default and the sibling precedent boards above
  both keep pwm_output alongside led_neopixel.)

GPIO9 (BOOT button, silicon strapping pin) - TAGGED
  No pins_arduino.h alias names this pin as a button (as expected - the
  project's established policy is that pins_arduino.h alias names are
  never trusted alone for button/LED identity; this pin was found and
  confirmed purely via the vendor schematic's SW1/R14/IO9 wiring,
  corroborated by UM's own help-site documentation of BOOT-button
  behavior). This board.json's existing pinNotes already carried
  "9": "Must be HIGH for normal boot" from the earlier strapping-pin
  audit pass, consistent with (but not by itself sufficient evidence
  for) a BOOT button being wired there - the schematic confirms it.
  Alias-collision check: GPIO9 is not SDA/SCL/SS/MOSI/MISO/SCK/SDO/SDI
  (6/7/18/21/20/19/21/20) on this board, and not TX/RX (16/17) either -
  no spurious bus/serial capability risk, no pins_arduino.h edit
  required.
  Applied: chipGpios["9"].capabilities = ["digital_input", "button"]
  (restricted set only - the pre-existing digital_output/pwm_output
  entries were removed per policy: a button pin with a fixed pull
  resistor + switch has no externally-useful output/PWM role).

GPIO22 (RGB_PWR) - NO CHANGE (re-confirmed, not re-tagged)
  Already excluded from chipGpios by the earlier dedicated-hardware
  pass, with a pre-existing header comment. The schematic (source 3)
  independently re-confirms this is correct: GPIO22 feeds the WS2812's
  VDD pin as a power-gate/enable line, not a general-purpose or
  button/LED-identity pin in its own right. No capability tag applies
  here and none was added.

RESET button contact (schematic SW1, second contact pair) - NOT TAGGED
  Wired directly to the ESP32-C6's RESET/EN silicon pin (CHIP_PU), which
  is not a GPIO and has no entry in chipGpios at all. Nothing to tag.

SUMMARY
-------
Tagged GPIO23 as the real NeoPixel data pin (resolved from the virtual
RGB_BUILTIN = RGB_DATA + SOC_GPIO_PIN_COUNT encoding) with
["digital_output","led_neopixel","pwm_output"], and GPIO9 as the
confirmed onboard BOOT button with ["digital_input","button"]. Both
findings confirmed directly from the vendor's own KiCad schematic
(TinyC6_Schematic_P1.pdf), no guessing from pins_arduino.h alias names
alone. No SDA/SCL/SS/MOSI/MISO/SCK/TX/RX alias collisions found on
either tagged GPIO, so no pins_arduino.h edit was needed. GPIO22
(RGB_PWR power-gate) remains correctly excluded from the earlier pass;
re-confirmed, not re-tagged.
