PER-PIN REASONING

GPIO9 (BUT_BUILTIN): KEPT, tagged capabilities ["digital_input","button"]
(restricted set per playbook section 7a - normal full default NOT carried
over). Confirmed onboard user button via source 4 (mentions "a user button")
and source 5 (GPIO9=Button1 in both the pin table and raw Tasmota GPIO
array). Chip-level pinNotes already flags "Must be HIGH for normal boot"
(GPIO9 is an ESP32-C6 strapping pin) - consistent with a button using an
external pull-up, pressed = pulled LOW, matching Tasmota's non-inverted
Button1 convention (default active-low with internal/external pull-up).

GPIO10/GPIO11/GPIO22/GPIO23 (REL1/REL2/REL3/REL4): KEPT at full chip-level
default capabilities (digital_input/digital_output/pwm_output - NOT
restricted). Per playbook section 3's explicit, standing relay-output KEEP
policy: "a relay is a simple digital on/off actuator, and controlling it
from pfodWeb IS the point of using such a board with pfodWeb - do not
exclude." Confirmed 4x 10A/240VAC relay outputs via source 4 (product page)
and source 5 (Tasmota Relay1-4 mapping matches these exact GPIOs). Each
pin given an informational "note" field identifying its relay-channel role
and rating - matches the existing per-pin "note" precedent already used on
other audited boards (e.g. VALTRACK_V4_MFW_ESP32_C3 GPIO2). Left at full
default capabilities rather than trimmed to output-only, consistent with
this repo's existing waveshare_esp32_s3_relay_6ch precedent, which left its
own relay-drive GPIOs (1,2,41,42,45,46) at full default capabilities too.

GPIO1/GPIO2/GPIO3/GPIO15 (DIN1/DIN2/DIN3/DIN4): KEPT, but capabilities
trimmed to ["digital_input"] only (chip-level default for these GPIOs
otherwise also includes analog_input/digital_output/pwm_output, all
dropped). Confirmed opto-isolated digital inputs, 5-30VDC, via source 4
(product page) and source 5 (Tasmota Switch1-4 mapping matches these exact
GPIOs). The GPIO pin in this circuit is wired only to an optocoupler's
phototransistor collector/emitter (external voltage drives an internal LED;
the GPIO only ever reads the resulting isolated logic level) - a genuine
board-level input-only signal path, even though the ESP32-C6 chip's own
inputOnlyGpios list is empty (this chip has no input-only-at-silicon pins;
the restriction here is board wiring, not chip silicon - explicitly checked
per this session's task, no chip-level GPIO34-style restriction applies to
any DIN pin). Matches playbook section 3's KEEP policy for sensor/status
pins ("a legitimate pfodWeb data-display use case"). Each pin given an
informational "note" field identifying its DIN-channel role and voltage
range.

GPIO5/GPIO4 (TX1/RX1): KEPT, NO board.json entry added - falls through
unmodified to the chip-level default (analog_input/digital_input/
digital_output/pwm_output on both). This board's own pins_arduino.h groups
TX1/RX1 together with SDA/SCL/SS/MOSI/MISO/SCK under a single comment block
("available at UEXT and pUEXT +" ... "-") - i.e. these are the standard
Olimex UEXT/pUEXT general-purpose expansion-header signals (UART+I2C+SPI),
not a UART wired to a specific onboard peripheral chip. Source 4 confirms
"two UEXT connectors" exist on this board, supporting the general-purpose
reading. No dedicated onboard consumer identified for TX1/RX1 in any source
consulted - treated as general-purpose per playbook section 3's default
("General-purpose I2C/SPI buses [and by the same logic, UART headers]
without a documented exclusive onboard consumer... KEEP"). GPIO4/GPIO5 are
also aliased A4/A5 in pins_arduino.h (harmless - already covered by the
chip-level default's analog_input capability on those pins, not a bus-alias
collision).

ALIAS-COLLISION CHECK (new item this session)
Explicitly checked whether GPIO9 (button), GPIO10/11/22/23 (relays),
GPIO1/2/3/15 (DIN), or GPIO5/4 (TX1/RX1) collide with this board's own
primary-UART/bus aliases - the exact identifiers build_boards.js's
buildEsp32Board() unconditionally consumes via consts.TX/RX/SDA/SCL/SS/
MOSI/MISO/SCK (matched by literal declared name, see build_boards.js
~L541-548, 662-703). Read this board's pins_arduino.h directly:
  TX  = 16
  RX  = 17
  SDA = 6
  SCL = 7
  SS  = 21
  MOSI = 18
  MISO = 20
  SCK = 19
None of these 8 values (16,17,6,7,21,18,20,19) match any of the 9 pins
being tagged/noted (9,10,11,22,23,1,2,3,15) or TX1/RX1 (5,4). CONCLUSION:
no alias contamination found; no boilerplate aliases needed deletion. (This
is distinct from the harmless A1/A2/A3/A4/A5 analog aliases on DIN1-3 and
TX1/RX1, which only add analog_input capability already present at the
chip-level default and were not touched.)

Chip-level GPIO34-style input-only check: ESP32-C6's chip-level board.json
(variants/esp32/esp32c6/board.json) declares "inputOnlyGpios": [] with an
explicit comment "every exposed GPIO is bidirectional - no input-only
pins." Confirmed no silicon-level input-only restriction applies to any
DIN pin (the DIN1-4 input-only-ness enforced in this board's board.json is
a board-wiring decision, documented above, not a chip-silicon fact).

DEFERRED / NOT CHANGED (left as chip-level default, no tag)
GPIO8 (LED_BUILTIN): NOT tagged with a led_* capability this session,
despite source 5's Tasmota table showing GPIO8=Led1 (component code 288,
"non-inverted"). This pin was outside the explicitly-flagged scope for this
audit pass (the flagged content list was BUT_BUILTIN/REL1-4/DIN1-4/TX1/
RX1 only; LED_BUILTIN is ordinary ESP32 boilerplate already filtered out of
the discovery-sweep regex). Attempted to confirm real electrical polarity
via the vendor's own schematic PDF (source 6) but the WebFetch tool could
not extract PDF schematic content from the GitHub blob page (returned only
page-shell text). Per playbook policy ("never guess a button/LED polarity
tag without confirmed vendor evidence"), left GPIO8 at its unmodified
chip-level default capabilities (digital_input/digital_output/pwm_output,
no led_* tag) rather than guess active-high vs active-low from the Tasmota
component-code naming alone. Flagged here for a future pass if the
schematic PDF can be read directly (e.g. via a PDF-capable fetch) or the
user manual PDF (sources 2/3/7) can be successfully retrieved and read.

SUMMARY
Olimex ESP32-C6-EVB confirmed as a real, vendor-documented industrial I/O
board. Created variants/esp32/esp32c6/esp32c6-evb/board.json (full copy of
the chip-level esp32c6 default) with 9 edited chipGpios entries: GPIO9
tagged button (restricted capability set); GPIO10/11/22/23 (REL1-4) left at
full default capabilities plus an informational relay-channel note each;
GPIO1/2/3/15 (DIN1-4) trimmed to digital_input-only plus an informational

pUEXT header signals, left unmodified/un-noted. No GPIOs excluded - matches
the task's expectation that this board needs capability tags/documentation
only, no exclusions. Alias-collision check performed and passed clean (no
SDA/SCL/SS/MOSI/MISO/SCK/TX/RX boilerplate contamination). GPIO8 (LED)
deferred, undecided, documented above for a future pass.
