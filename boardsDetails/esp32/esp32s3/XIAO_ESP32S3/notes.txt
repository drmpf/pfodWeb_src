Sweep flag verification:
- Read C:\ai\aicode\pfodWeb\variants\esp32\esp32s3\XIAO_ESP32S3\pins_arduino.h
  in full (56 lines). Confirmed the discovery sweep's flag was a FALSE
  POSITIVE for "dedicated hardware": the only #define lines are
  USB_VID (0x2886) and USB_PID (0x0056), which are USB descriptor macros,
  not pins. No BAT_VOLT_PIN, no PIN_NEOPIXEL, no BUTTON/BOOT alias, no

  the usual TX/RX/SDA/SCL/SS/MOSI/MISO/SCK/A<n>/D<n>/T<n> aliases) - this
  is a real onboard-LED declaration, just not a "#define" the sweep's
  #define-only grep would have caught. Investigated per the task's
  opportunistic button/LED/battery check since the board had zero prior
  review.

Alias-collision check (per this session's new methodology - GPIO used as
button/LED must not also be a boilerplate SDA/SCL/SS/MOSI/MISO/SCK/TX/RX
alias elsewhere in the same pins_arduino.h, since build_boards.js
unconditionally appends those capabilities regardless of chipGpios):
- GPIO21 (tagged led_low): pins_arduino.h aliases are SDA=5, SCL=6,
  SS=44, MOSI=9, MISO=8, SCK=7, TX=43, RX=44. GPIO21 matches NONE of
  these (nor any A<n>/D<n>/T<n> alias touching that same GPIO number).
  Clean - no alias line needed deletion.
- Existing TX/RX conflict rule, checked the same way: SS=44 collides
  with RX=44 in this vendor file (pre-existing vendor overlap, not
  something this audit introduced). build_boards.js's ESP32 pin-builder
  checks `g === rx` FIRST and does an early `continue` with capabilities
  forced to exactly ['serial_rx'] (see pfodWeb_src/build_boards.js
  ~line 662-668), before the SDA/SCL/SS/MOSI/MISO/SCK append block ever
  runs (~line 698-703). So GPIO44 correctly ends up RX-only in the
  generated output; the SS alias on the same GPIO is silently and
  safely dropped by construction. No action needed - verified by reading
  the generator code, not just assumed.
