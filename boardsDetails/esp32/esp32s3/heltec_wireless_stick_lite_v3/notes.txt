2. PINS CONSIDERED BUT NOT TAGGED

GPIO35 (LED, confirmed active-high single-color/white LED via Zephyr dts) -
  NOT TAGGED. Reason: GPIO35 does NOT currently exist as an entry in this
  board's chipGpios map, nor in the chip-level default
  variants/esp32/esp32s3/board.json. The chip-level file's own comment states
  GPIOs 33-37 are blanket-excluded chip-wide as "octal flash/PSRAM" pins for
  ALL ESP32-S3 boards, regardless of whether a given board's specific module
  (this one is ESP32-S3FN8, no PSRAM) actually uses octal PSRAM. This board's
  own vendor pins_arduino.h clearly repurposes GPIO34/35/36/37 for other
  functions (SS/LED/Vext/MISO), so the blanket exclusion may not really apply
  to this specific board - but that is a chip-level/base-file pin-exclusion
  policy question, not something in scope for this capability-tagging task.
  Per task instructions ("do NOT touch existing pin-exclusions... only modify
  the specific GPIO capability array(s) you're tagging"), adding a brand-new
  chipGpios["35"] entry would go beyond tagging an existing entry and would
  effectively reverse an inherited chip-level exclusion decision. This is a
  genuine, confirmed-by-evidence LED pin that I deliberately left UNTAGGED
  and unmodified - not a guess, not an oversight. Flagging for human review:
  should GPIO35 (and by extension GPIO34/36/37 on this board, already
  documented as excluded/reserved for SS/Vext/MISO) be reinstated into
  chipGpios as a board-specific override of the chip-level octal-PSRAM
  assumption, given this module has no PSRAM?

No other candidate button/LED pins were found for this board (only one LED,
one user button, and one separate non-GPIO hardware reset switch per the
Zephyr board documentation).

3. SUMMARY OF WHAT WAS TAGGED

TAGGED: GPIO0 -> ["digital_input", "button"] (onboard "USER SW" / PRG button,
confirmed via Zephyr board devicetree gpio-keys node). GPIO0 already existed
in chipGpios with no TX/RX conflict (TX=43, RX=44), so the capability array
was safely modified in place.
GPIO35 (LED) was investigated and confirmed via vendor/Zephyr sources but was
NOT tagged, for the chip-level pin-exclusion reason explained above.
