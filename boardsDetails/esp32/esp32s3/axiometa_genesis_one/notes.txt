=== Reasoning per pin group ===

1. VBAT_SENSE (GPIO10) + getBatteryVoltage() macro
   KEEP (matches playbook's battery-monitor KEEP precedent). The macro
   `((analogRead(VBAT_SENSE)/4095.0)*3.3*2.0)` multiplies the ADC reading
   by 2x -- strong internal evidence of a real onboard 1:1 voltage divider
   ahead of this pin, consistent with the vendor's own confirmed "battery
   socket... with short-circuit protection" (implies charge/sense
   circuitry). No change to chipGpios capabilities needed (analog_input
   already present in the chip-level default); added an informational
   "note" field on GPIO10 in board.json documenting the divider so future
   reviewers don't have to re-derive it.

2. P1_IO0 .. P8_IO2 (24 GPIOs, the 8 "AX22" expansion ports)
   KEEP ALL -- confirmed general-purpose, not dedicated hardware. The
   AX22 standard is explicitly designed so any of the 8 ports can accept
   any of "50+ sensors and peripherals" (buttons, LEDs, motor drivers,
   relays, displays, etc. per CNX Software) -- there is no fixed onboard
   consumer soldered to a specific port; the consumer is whichever
   module the end user plugs in. This matches the playbook's explicit
   "general-purpose bus without a documented exclusive onboard consumer"
   KEEP precedent. No vendor schematic/doc found showing any port
   hard-wired to a fixed onboard peripheral (as opposed to a standard,
   swappable AX22 module) -- if a future source contradicts this for one
   specific port, only that port's pin(s) should be excluded, not the
   whole set.

   Two exceptions found within these 24, both already handled correctly:

   a) GPIO43 (TX / P8_IO1) and GPIO44 (RX / P8_IO2): the board's own
      pins_arduino.h explicitly comments these as "Fixed communication
      pins (shared across all ports)" directly above the TX/RX
      declarations -- vendor-confirmed as deliberate, not boilerplate
      (also matches ESP32-S3's conventional default UART0 pin pair,
      typically routed to the onboard USB-UART bridge for flashing/
      logging). build_boards.js's own TX/RX precedence logic (forces any
      GPIO matching the parsed TX/RX consts to capabilities:
      ['serial_tx']/['serial_rx'] only, discarding any other role) already
      produces the correct outcome automatically -- no board.json change
      required for these two GPIOs specifically.

   b) GPIO1 (P1_IO0), collision with a separate "SS" alias: unlike TX/RX,
      the vendor file had NO comment/confirmation marking GPIO1 as a real
      dedicated SPI slave-select -- it was declared as plain boilerplate
      (`static const uint8_t SS = 1;`) with no supporting evidence found
      in any of the sources above. Checked the display-label mechanism
      specifically (build_boards.js's `_displayAliases`/`_primaryAlias`):
      GPIO1's boilerplate A0/T1 identity-block aliases already win the
      display label over any TX/RX/SDA/SCL/SS/MOSI/MISO/SCK alias, so the
      SS alias was never actually going to change GPIO1's displayed name.
      The real, confirmed risk was capability contamination: left in
      place, `if (g === ss) caps.push('spi_ss')` in build_boards.js would
      unconditionally add a spurious spi_ss capability to GPIO1's
      capability list regardless of chipGpios -- exactly the failure
      mode this session's new alias-collision check was added to catch.
      FIXED: deleted the `static const uint8_t SS = 1;` line from
      pins_arduino.h entirely (not commented out -- build_boards.js's
      regex parser matches `static const ...;` text regardless of a
      leading `//`, per the playbook's documented parser gotcha #2).
      MOSI=11/MISO=12/SCK=13 were checked too and do NOT collide with any
      port pin (ports only span GPIO1-9,14-18,21,38-46) -- left unchanged.

3. SDA=47 / SCL=48 (STEMMA QT / Qwiic connector)
   KEEP, no change. CNX Software confirms a dedicated STEMMA QT/Qwiic
   connector on the board. GPIO47/48 are outside all 8 ports' pin sets,
   so no P<n>_IO<m> naming collision exists. I2C is inherently multi-drop
   and Qwiic/STEMMA QT is itself a general-purpose plug-in-sensor
   standard -- matches the playbook's "general-purpose I2C/SPI bus...
   even if only one device happens to be attached in the reference
   design" KEEP precedent (here, potentially many different plug-in
   Qwiic sensors, not even a single fixed one). i2c_sda/i2c_scl
   capability tagging still applies automatically via build_boards.js's
   alias matching, unaffected by this audit.

4. MOSI=11 / MISO=12 / SCK=13
   KEEP, no change. Not part of any port's pin set, no collision, no
   vendor doc/schematic found showing a fixed onboard SPI peripheral
   (flash/PSRAM chip-select pins are the already chip-level-excluded
   26-37 range). Treated as default/general SPI convenience pins per
   playbook's general-purpose-bus KEEP precedent.

=== Summary ===

KEEP all 24 P<n>_IO<m> expansion-port GPIOs (confirmed general-purpose
AX22 ports, no fixed onboard consumer) and VBAT_SENSE/GPIO10 (confirmed
battery monitor via internal divider-math evidence) with chipGpios left
identical to the chip-level default (informational "note" added on
GPIO10 only). Found and fixed one real alias collision: deleted a
vendor-boilerplate, never-confirmed `SS = GPIO1` alias from
pins_arduino.h that collided with the confirmed P1_IO0 port pin and
would have added a spurious spi_ss capability to it (display label was
unaffected, since GPIO1's A0/T1 identity-block aliases already took
precedence). TX(GPIO43)/RX(GPIO44) collide with
P8_IO1/P8_IO2 too but are vendor-confirmed as a real shared UART and are
already handled correctly by build_boards.js's existing TX/RX precedence
logic with no board.json change needed. board.json created (full
chip-level-default copy plus documentation) since none existed before.
