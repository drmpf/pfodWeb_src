FINDINGS: VIRTUAL RGB_BUILTIN / REAL GPIO
Per the vendor header:
  static const uint8_t RGB_DATA = 41;
  #define RGB_BUILTIN (RGB_DATA + SOC_GPIO_PIN_COUNT)
  static const uint8_t LED_BUILTIN = RGB_BUILTIN;
RGB_BUILTIN/LED_BUILTIN are virtual pin numbers (RGB_DATA + an offset,
e.g. 41+N) used only by the new Arduino rgbLedWrite()/digitalWrite()
convenience API to select the "use the addressable RGB helper" code
path — they do not name a real GPIO. The REAL physical NeoPixel data
GPIO is RGB_DATA = 41, confirmed both by build_boards.js's parser
(only RGB_DATA resolves to a plain integer; RGB_BUILTIN/LED_BUILTIN do
not) and by the NanoS3 product page's "RGB LED via an IO pin" text.

FINDINGS: SS/MOSI/MISO/SDO/SDI/SCK ALIAS-LEAK (same bug class as
um_edges3_d)
The vendor pins_arduino.h declared:
  SS = 34, MOSI = 35, MISO = 37, SDO = 35, SDI = 37, SCK = 36
All four GPIOs (34-37) fall inside the GPIO33-37 range the chip-level
esp32s3/board.json already excludes as reserved octal flash/PSRAM pins,
and um_nanos3's own board.json chipGpios already omitted 34-37
(matching the chip default). Despite that, build_boards.js's
buildEsp32Board() unions chipGpios keys with EVERY GPIO referenced by a
pins_arduino.h alias (aliasesByGpio), so the still-present SS/MOSI/
MISO/SCK/SDO/SDI declarations would silently re-add GPIO34-37 as
user-selectable pins (digital_input/digital_output/pwm_output plus
spi_ss/spi_mosi/spi_miso/spi_sck-style aliasing) in the Designer, even
though the board intentionally excludes them as internal PSRAM/flash
bus lines. This is the exact bug flagged for this task and previously
found/fixed on the sibling um_edges3_d board.

FIX APPLIED (pins_arduino.h)
Deleted the `SS`/`MOSI`/`MISO`/`SDO`/`SDI`/`SCK` declaration block
(GPIO34-37) entirely and replaced it with a plain-English "pfodWeb
NOTE" comment (no literal re-statement of the deleted declarations as
commented-out code, since build_boards.js's regex parser is
comment-blind and a `//`-prefixed `static const uint8_t SS = 34;` line
would still match it). A plain `= -1;` override was NOT used, per the
known-bug flag for this task: since no other declaration of the same
alias name exists elsewhere in this board's single self-contained
header (unlike a shared common.h scenario), deletion was the correct
and sufficient fix — there is no second declaration anywhere else in
this file's flattened source that would otherwise win.
No board.json chipGpios edit was needed for this part: GPIO34-37 were
already absent from um_nanos3's chipGpios (matching the chip-level
default), so once the leaking aliases are gone, no leak path remains.

FINDINGS / TAGGING: LED (section 7a)
GPIO41 (RGB_DATA) is confirmed as the board's onboard NeoPixel data
pin — parsed directly from this board's own pins_arduino.h (a real,
non-virtual numeric GPIO assignment) and corroborated by the NanoS3
product page's RGB LED description. Tagged GPIO41's chipGpios
capabilities as ["digital_output", "led_neopixel", "pwm_output"] in
board.json (dropping "digital_input", matching the um_tinys3 precedent
for led_neopixel-tagged pins). GPIO42 (RGB_PWR, the NeoPixel's internal
power-gate) remains excluded from chipGpios entirely — that exclusion
predates this task (an earlier dedicated-hardware-exclusion pass) and
was left untouched, only its board.json header comment was extended to
document the led_neopixel tagging alongside it.

CONSIDERED BUT NOT TAGGED: BUTTON
No BUTTON/BOOT alias is declared anywhere in this board's
pins_arduino.h (only RGB_DATA/RGB_PWR are hardware-identity-named;
no button-style constant exists at all). WebSearch results for the
NanoS3 product page explicitly and affirmatively state the board does
NOT ship with a populated BOOT or RESET button — "the NanoS3 includes
everything you need other than a USB connector and buttons for IO0 and
RESET ... those need to be provided by you, if required." This is
stronger evidence than the um_tinys3 case (where the button question
was simply undocumented either way); here the vendor page affirmatively
confirms absence. GPIO0 keeps its existing "Must be HIGH for normal
boot" pinNotes strapping warning but is NOT tagged as a "button" —
there is no onboard button wired to it. No battery-sense ADC pin is
declared in this board's header either, and none was tagged.

SUMMARY (one line)
GPIO41 (RGB_DATA) tagged "led_neopixel" as the confirmed real onboard
NeoPixel data pin (RGB_BUILTIN/LED_BUILTIN are virtual RGB_DATA+offset
numbers, not real GPIOs, and are correctly invisible to
build_boards.js's parser); no button exists on this board per vendor
confirmation, so none was tagged; and the vendor header's
SS/MOSI/MISO/SDO/SDI/SCK aliases on GPIO34-37 were deleted from
pins_arduino.h (not just absent from chipGpios) to close the same
alias-leak bug in build_boards.js already fixed on the sibling
um_edges3_d board, since GPIO34-37 sit inside the chip's excluded
octal-flash/PSRAM range.
