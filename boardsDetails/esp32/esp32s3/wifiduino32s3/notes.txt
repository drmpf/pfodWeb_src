REASONING
  GPIO48 (led_neopixel):
  - This board's own pins_arduino.h wires LED_BUILTIN/RGB_BUILTIN/
    RGB_BRIGHTNESS to GPIO48 via the PIN_RGB_LED macro - this is the
    modern Arduino-ESP32 core's marker for an onboard WS2812-style
    addressable RGB LED driven through rgbLedWrite() (RMT peripheral),
    not a plain digitalWrite() LED.
  - Independently corroborated by espboards.dev, which lists an onboard
    "RGB LED" for this exact board and shows GPIO48 as LED_BUILTIN in its
    pin table.
  - Directly precedented in this repo: the generic "esp32s3" (ESP32-S3-
    DevKitC-1) board.json already tags GPIO48 "led_neopixel" for the
    exact same PIN_RGB_LED=48 pattern, and waveshare_esp32_s3_zero tags
    its RGB_BUILTIN pin (GPIO21 there) the same way.
  - Alias-collision check: SDA=4, SCL=5, SS=10, MOSI=11, MISO=13, SCK=12,
    TX=43, RX=44 - none equal 48, so build_boards.js's automatic spi_*/
    i2c_* capability append (keyed off these aliases) does not touch
    GPIO48. (D5=48 is a plain header-label alias, not one of the bus-
    alias names the parser watches, so it is not a collision source
    either.) Safe to retag.
  - No pins_arduino.h edits were needed for this change (no alias needed
    deleting), so the "don't write the deleted declaration's literal text
    in a comment" landmine does not apply here - nothing was deleted.

  GPIO0 (left untagged - NO CHANGE):
  - No vendor alias (KEY_BUILTIN, BOOT, RESET, or similar) exists in this
    board's pins_arduino.h, unlike its classic-ESP32 sibling wifiduino32
    (which has `KEY_BUILTIN = 0`).
  - No independent documentation source found that confirms a physical
    BOOT/RESET button on this specific board (espboards.dev's page,
    checked verbatim for "button"/"BOOT"/"RESET", contains none of those
    words).
  - Per audit policy, a "button" capability tag requires an explicit
    vendor alias or explicit vendor documentation of a physical button,
    not just the generic ESP32-S3 strapping-pin fact that GPIO0 is
    commonly wired to a BOOT button on many dev boards. Tagging without
    that confirmation would be exactly the kind of "discovery-sweep
    guess" this audit is meant to avoid. GPIO0 capabilities are left at
    the chip-level default: ["digital_input", "digital_output",
    "pwm_output"] (already correctly excludes analog_input, matching real
    ESP32-S3 hardware - GPIO0 has no ADC channel on this chip, despite
    this board's pins_arduino.h mislabeling it "A0"; that mislabeling
    predates this audit and needed no fix since the chip-level default
    already ignores it).

  Dedicated-hardware pin-exclusion check:
  - All header pin aliases (A0-A5 -> GPIOs 0-5, D0-D13 -> GPIOs
    44,43,45,46,47,48,18,17,21,42,41,40,38,39) resolve to GPIOs already
    inside the chip-level default's included set (0-18, 21, 38-48).
  - None fall inside the excluded flash/PSRAM range (26-37) or USB range
    (19-20), and none reference GPIOs 22-25 (which do not exist in
    silicon). No EXCLUDE changes were needed, and no blanket-identity-
    block aliases needed deleting from pins_arduino.h.

SUMMARY
  Created board.json for wifiduino32s3 (none existed before) as a full
  copy of the esp32s3 chip-level default, with GPIO48 retagged
  ["digital_output", "led_neopixel", "pwm_output"] - confirmed onboard
  WS2812-style RGB LED (PIN_RGB_LED/RGB_BUILTIN in this board's own
  pins_arduino.h, corroborated by espboards.dev, and precedented by the
  identical pattern already tagged on the generic "esp32s3" board in this
  repo). GPIO0 was investigated as a candidate BOOT button (per the
  classic-ESP32 sibling wifiduino32's confirmed KEY_BUILTIN=0) but left
  UNCHANGED - this S3 variant declares no such alias and no independent
  source confirms a physical button on this exact board, so it was not
  guessed. No dedicated-hardware EXCLUDE changes or pins_arduino.h
  deletions were needed; all header-exposed GPIOs are already within the
  chip-level default's included range.
