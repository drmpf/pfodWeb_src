Product research - what AMYboard actually is:
- AMYboard is a $29.90 DIY Eurorack-compatible (10HP) music synthesizer
  module built around an ESP32-S3-WROOM-1 module (dual-core Xtensa LX7,
  8 MB RAM/PSRAM), designed by Brian Whitman (Shorepine) to run the
  open-source "AMY" fixed-point synthesis engine (virtual analog, FM,
  wavetable, sample playback). Ships MicroPython firmware by default; also
  usable from Arduino sketches via the AMY-Arduino library (available in
  Arduino Library Manager). Confirms the "AMY synthesizer engine" hypothesis
  from the task brief.
- I/O is entirely audio/music-domain, not general-purpose GPIO: ten 3.5 mm
  jacks (stereo audio in/out, 2x CV, MIDI in/out, stereo S/PDIF digital
  audio), microSD card slot for samples, onboard DIP switches for
  1 Vpp/10 Vpp level selection, USB-C (power/MIDI/serial/file access), an
  I2C "host port for accessories - encoders, displays, and more" (external
  Grove-style connector, matches the SDA=17/SCL=18 bus and the file's own
  "PCM9211, OLED display, ADC" comment), and a 10-pin Eurorack power
  connector. PCM9211 (TI 24-bit stereo ADC / S/PDIF-AES3 receiver) is a real
  audio chip, consistent with the file's I2C comment.

Alias-collision check (per this session's methodology - a GPIO tagged
button/LED must not also be a boilerplate SDA/SCL/SS/MOSI/MISO/SCK/TX/RX
alias elsewhere in pins_arduino.h, since build_boards.js unconditionally
appends those bus capabilities regardless of chipGpios):
- Not applicable here - no button/LED/NeoPixel candidate GPIO was found at
  all (see below), so there is nothing to check for collision. For
  completeness: the only GPIO that could ever be considered a button
  candidate is GPIO0 (BOOT strapping pin), which does NOT collide with any
  of TX(43)/RX(44)/SDA(17)/SCL(18)/SS(10)/MOSI(11)/MISO(13)/SCK(12) - it
  simply was never tagged in the first place (see below).

Pins considered but NOT tagged:
- GPIO0 (BOOT/strapping pin, already carries the chip-level pinNote "Must be
  HIGH for normal boot"): considered as a possible "button" candidate since
  ESP32-S3 boards commonly wire BOOT to GPIO0. Every source found (README,
  firmware.md, faq.md) describes BOOT (with RST) purely as a download-mode /
  hardware-self-test trigger, never as a documented general-purpose,
  sketch-readable user button (contrast with um_pros3's board.json
  precedent, where a third-party board-support page explicitly enumerated
  it as "BTN0 GPIO0 labeled as BOOT button" - no equivalent explicit
  "this is also a usable button in your code" statement exists for
  AMYboard). Left untagged - consistent with this codebase's more common
  precedent for BOOT-only buttons (pico32, XIAO_ESP32S3, um_tinys3).
- No other pin (LED, NeoPixel, battery-sense, camera, etc.) was found
  anywhere in vendor documentation, the designer's own blog post, or
  third-party write-ups. The board's entire non-power I/O surface is
  audio/MIDI/CV jacks, SD, and I2C - none of which map to a GPIO capability
  this designer tracks.

Applied:
- NO CHANGE. No board.json override was created for this board - the
  existing chip-level default (variants/esp32/esp32s3/board.json) already
  correctly represents every GPIO amyboard exposes; TX(43)/RX(44) are
  handled generically by build_boards.js's serial_rx/serial_tx branch, and
  SDA(17)/SCL(18)/SS(10)/MOSI(11)/MISO(13)/SCK(12) correctly pick up their
  i2c_sda/i2c_scl/spi_ss/spi_mosi/spi_miso/spi_sck capabilities from the
  generic alias-matching in build_boards.js with no override needed. Per
  established precedent (e.g. pico32's notes.txt), a board.json is only
  created when there is an actual capability change to apply - there is
  none here.

Summary: Discovery-sweep flag description was imprecise (the file has more
than USB macros - 8 real bus-pin aliases), but its underlying "no dedicated
hardware to exclude" conclusion is correct and now independently confirmed
via the byte-for-byte-matching upstream vendor file plus 6+ independent
AMYboard documentation/press sources. AMYboard (Shorepine's AMY-synth-engine
Eurorack module) has no onboard general-purpose button, LED, or NeoPixel -
only the standard BOOT/RST bootloader-entry buttons, which per this
codebase's established precedent are not tagged as a "button" capability
without explicit vendor confirmation of general-purpose/user-code use. No
board.json was created; this notes.txt is the sole record of the review so
the board is not re-flagged in a future sweep.
