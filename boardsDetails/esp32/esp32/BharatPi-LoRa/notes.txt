BharatPi-LoRa (chip: esp32) - button/LED capability-tagging audit (section 7a)
Date: 2026-07-12

CONTEXT
This board already has a board.json override from an earlier dedicated-
hardware-exclusion pass. That pass already excludes GPIO2/4/14 from
chipGpios entirely (no "2"/"4"/"14" keys present) because pins_arduino.h's
own comments identify them as the onboard RFM95W LoRa radio's DIO0/SS/RST
control lines (and their duplicate A0/A3/A4 analog aliases were removed
too). This session's task was to apply button/LED tagging, which that
earlier pass never did. pins_arduino.h also declares
`static const uint8_t LED_BUILTIN = 2;` (plus the usual BUILTIN_LED /
LED_BUILTIN redefinition boilerplate) - GPIO2 is the LED_BUILTIN candidate
this audit had to evaluate.

FLAGGED PIN: GPIO2 (LED_BUILTIN)
No other undeclared onboard button candidate was found (see BUTTON section
below).

REASONING

GPIO2 (LED_BUILTIN): NOT TAGGED, left excluded (no chipGpios "2" entry -
unchanged from the prior exclusion pass). The vendor's own MIT-licensed
GitHub sample code for THIS EXACT LoRa board (both transmitter and
receiver sketches) wires GPIO2 solely to the onboard RFM95W radio's
interrupt line, with no LED-driving code anywhere. No vendor pinout page,
schematic, or PDF could be retrieved after a genuine multi-source research
attempt (5 separate failed fetch attempts across bharatpi.net, edgehax.com,
Scribd, a reader-proxy retry, and Hackster.io) to confirm whether a
physically separate onboard LED also exists on the same pin, or whether
the LED_BUILTIN declaration in pins_arduino.h is simply generic
Arduino-ESP32 core boilerplate (this exact "LED_BUILTIN = GPIO2" pattern
is extremely common across many unrelated ESP32-WROOM boards, including
ones with no physical LED at all). The one piece of LED evidence found
(the generic BharatPi Blink test sketch) was validated in the sibling
Node-Wifi board's audit, which has no radio module and therefore no
conflict - it does not resolve the question for this radio-equipped
board. Per this project's strict "never guess LED polarity/presence"
policy, and because the pin is already committed to the LoRa radio's
interrupt duty by this board's own prior audit pass, this pin was left
untagged/excluded rather than guessed. This is a documented-reason
non-tag, not an oversight.

COLLISION CHECK (per playbook step 5): GPIO2 is not aliased anywhere in
this file as SDA/SCL/SS/MOSI/MISO/SCK (those are GPIO21/22/5/23/19/18
respectively, all distinct pins) - no bus-capability contamination risk
applies here regardless of the no-tag decision.

BUTTON CHECK: No additional onboard user pushbutton was found in any
source. The only boot-button reference found anywhere (WebSearch) is the
standard ESP32 flash/boot button on GPIO0, which is standard silicon-level
behavior on every ESP32-WROOM module (not a BharatPi-LoRa-specific
feature) and is already covered by this file's existing GPIO0 alias
(declared as A5). Not re-tagged as a separate button alias.

GUESS VS NO-GUESS SUMMARY
No guess was made. GPIO2 was left untagged/excluded based on: (a) the
vendor's own MIT-licensed LoRa example code confirming exclusive radio-
interrupt use with zero LED code, (b) the already-established prior-pass
exclusion of this pin for the same radio hardware, and (c) the inability,
after a genuine multi-source attempt, to find any vendor evidence that an
independent physical LED safely coexists on this specific pin on this
specific board. The one piece of LED-blink sample code found is a generic
BharatPi test sketch already consumed as evidence for a different,
radio-less sibling board, so it does not settle the question here.

SUMMARY
GPIO2/LED_BUILTIN on BharatPi-LoRa: left untagged and excluded from
chipGpios (unchanged from the prior dedicated-hardware-exclusion pass) -
vendor's own LoRa sample code shows the pin dedicated to the radio's DIO0
interrupt with no LED code, and no source could confirm an independent
onboard LED safely coexists there; documented as a deliberate no-guess
non-tag rather than an oversight. No separate onboard user button found
(GPIO0's boot button is standard ESP32 silicon behavior, already aliased).
No other board.json changes made; only the top-of-file NOTE comment was
extended with this audit's findings.
