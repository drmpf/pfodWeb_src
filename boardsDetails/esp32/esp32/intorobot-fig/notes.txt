REASONING PER FLAGGED PIN
--------------------------
GPIO0 (KEY_BUILTIN): TAGGED. Same KEY_BUILTIN=0 naming pattern already
confirmed this session as a real onboard user button on the sibling
widora-air board (see boardsDetails/esp32/esp32/widora-air/notes.txt and
variants/esp32/esp32/widora-air/board.json) - the standard ESP32 GPIO0/BOOT
strapping pin doubling as a physical user "key" button, a well-established
pattern across this ESP32 board family. espboards.dev's independent pinout
table for this exact board corroborates the GPIO0/KEY_BUILTIN association.
Decision: KEEP GPIO0, capabilities set to exactly ["digital_input",
"button"] (dropped analog_input_serial/digital_output/pwm_output from the
chip-level default, matching the button-tag exclusion convention used
throughout this codebase). Existing "Must be HIGH or floating on reboot"
pinNotes entry for GPIO0 left unchanged (inherited from chip default).

GPIO21/22/27 (RGB_G_BUILTIN/RGB_B_BUILTIN/RGB_R_BUILTIN): ROLE CONFIRMED,
POLARITY NOT CONFIRMED. This is a genuine discrete 3-GPIO RGB LED (three
separate named constants driving three separate GPIOs - not a single
WS2812/NeoPixel data pin), corroborated independently by espboards.dev's
pinout table for this exact board matching pins_arduino.h. However, despite
consulting every source found (items 1-8 above, including IntoRobot's own
GitHub organisation, which DOES publish schematic repos for several of its
other boards but has none for "Fig"; the official docs.intorobot.com site,
unreachable by any available tool; and both English and Chinese-language
web searches), no vendor schematic, datasheet, or documentation stating
active-high vs active-low drive polarity for this RGB LED was found
anywhere. Per the audit's explicit "don't guess if polarity evidence is
weak" instruction, NO led_r_high/led_r_low (or _g_/_b_) capability tag is
applied to any of the three channels - applying one would risk driving the
LED backwards (inverted brightness, or a channel appearing permanently on)
in the Designer UI. Decision: chipGpios capabilities for GPIO21/22/27 are
left UNCHANGED from the chip-level default. A pinNotes entry was added for
each of the three GPIOs documenting the confirmed RGB-channel role and the
unconfirmed polarity, so a Designer user sees the context instead of a
silently generic GPIO. This mirrors the precedent set this session by the
d1_mini32 board's GPIO35/_VBAT treatment (confirmed role, unconfirmed
circuit detail -> pinNotes documentation, no guessed capability tag) and
the nina_w10 board's fuller precedent of leaving RGB LED channels untagged
entirely when no polarity evidence exists.

ALIAS-COLLISION CHECK (task step 4, critical)
-----------------------------------------------
This board's bus-role aliases (from pins_arduino.h): TX=1, RX=3, SDA=23,
SCL=19, SS=5, MOSI=16, MISO=17, SCK=18. None of these equal 0, 21, 22, or
27 - the button pin and all three RGB LED channel pins are free of any
SDA/SCL/SS/MOSI/MISO/SCK/TX/RX alias. build_boards.js's unconditional
bus-capability appends (which run independent of chipGpios settings) will
not silently attach an i2c_sda/spi_mosi/etc. capability to the button tag
or contaminate the RGB channel pins. No pins_arduino.h edit was required
for this board - no colliding boilerplate alias exists to delete.
