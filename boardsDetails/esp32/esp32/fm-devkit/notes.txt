4. https://raw.githubusercontent.com/dragon-engineer/esp32_fmdevkit/master/example_firmware/FMDevKit_BluetoothAudio/FMDevKit_BluetoothAudio.ino
   Official example firmware, read for LED/button GPIO handling (quoted
   verbatim, not paraphrased):
     pinMode(LED_BUILTIN, OUTPUT); // Blue built-in LED
     digitalWrite(LED_BUILTIN, HIGH);
     pinMode(SW1, INPUT);
     pinMode(SW2, INPUT);
     pinMode(SW3, INPUT);
     pinMode(SW4, INPUT);
     attachInterrupt((SW1), sw1_callback, FALLING); // Register all input callback
     attachInterrupt((SW2), sw2_callback, FALLING);
     attachInterrupt((SW3), sw3_callback, FALLING);
     attachInterrupt((SW4), sw4_callback, FALLING);
   ...and later, in the main loop's async LED handler:
     if (btConnectionParams.conn_stat.state == ESP_A2D_CONNECTION_STATE_CONNECTED) {
       // btLedBlinkState toggles true/false on a 300ms/150ms cycle
     } else {
       ...
       btLedBlinkState = false;
       ...
     }
     digitalWrite(LED_BUILTIN, btLedBlinkState);
   BUTTONS: pinMode(SWn, INPUT) (plain INPUT, not INPUT_PULLUP) combined
   with attachInterrupt(..., FALLING) is decisive: a FALLING edge on a pin
   with no internally-enabled pull-up only makes sense if the board
   provides its own external/onboard pull-up and the button pulls the pin
   to GND on press - i.e. genuine active-low hardware buttons. Combined
   with source #2's explicit "Button Switch N ... Input" pinout-table rows,
   this is solid, board-specific, vendor-authored confirmation (not an
   alias-name guess).
   LED: digitalWrite(LED_BUILTIN, ...) is genuinely used to drive a
   Bluetooth-connection-status indicator, confirming this is a real,
   actively-driven LED (not dead/unused code). However the polarity
   evidence is circumstantial, not explicit: HIGH is written once at boot
   (before Bluetooth is even started - a transient initial value, not
   necessarily "off"), and LOW is the steady value while disconnected
   (btLedBlinkState fixed false in the disconnected branch). While a LOW-
   when-idle / blinking-when-active UX pattern is plausible for an
   active-high LED, this is an inference about UX intent, not an explicit
   on/off-semantic statement (contrast with e.g. this repo's
   espresso_lite_v2 precedent, which had a named boolean library function
   explicitly mapping "on" to a specific level). No comment in the source
   states which level lights the LED. Per the playbook's "never guess"
   policy, this evidence was judged insufficient to tag led_high/led_low.

FINDINGS AND DECISIONS
-----------------------
GPIO4/18/19/21 (SW1/SW2/SW3/SW4): CONFIRMED onboard pushbuttons via the
  vendor's own README pinout table ("Button Switch N ... Input") and
  independently corroborated by the vendor's own example firmware
  (INPUT + FALLING-interrupt pattern implying an onboard pull-up and
  active-low press). Tagged ["digital_input", "button"] in board.json's
  chipGpios entries for all four pins (analog_input_serial dropped from
  GPIO4, digital_output/pwm_output dropped from all four), matching this
  repo's button-tag exclusion rule/precedent (widora-air, intorobot-fig,
  espresso_lite_v1: a confirmed dedicated button is not also offered as a
  general-purpose output/PWM/analog pin in the Designer).

GPIO5 (LED_BUILTIN): role CONFIRMED (genuine onboard "Blue User LED"/LED2,
  per the vendor's own README and actively used in the vendor's own
  firmware), polarity NOT CONFIRMED (no schematic exists anywhere for this
  board - the vendor repo is firmware-only with an empty hardware-files
  directory - and no source states active-high/active-low explicitly; the
  firmware's digitalWrite pattern is suggestive of active-high but not an
  explicit statement). Per the playbook's "never guess" rule and this
  repo's own intorobot-fig precedent (confirmed role, unconfirmed polarity
  -> pinNotes documentation only, no capability tag), NO led_high/led_low
  tag was applied. chipGpios["5"] capabilities left unchanged
  (["digital_input","digital_output","pwm_output"], same as the chip-level
  default - GPIO5 has no ADC channel on ESP32 silicon so analog_input was
  never present). A pinNotes["5"] entry was appended (preserving the
  existing "Must be HIGH or floating on reboot" strapping-pin text)
  documenting the confirmed LED identity and the unconfirmed-polarity
  evidence gap, so a Designer user sees the context instead of a silent
  plain GPIO.

Alias-collision check (CRITICAL step per playbook): this board's own
  pins_arduino.h declares TX=1, RX=3, SDA=16, SCL=17, and SCK/MISO/MOSI/SS
  all = -1 (explicitly unused/undefined - no SPI bus is wired on this
  board). None of these equal 4, 5, 18, 19, or 21 - none of the four
  tagged button pins or the LED pin collide with any bus-role alias, so
  build_boards.js's unconditional i2c_sda/i2c_scl/spi_*/serial capability
  appends cannot silently contaminate any of the tagged pins. No line in
  pins_arduino.h needed deletion - there is no colliding boilerplate alias
  to remove.
