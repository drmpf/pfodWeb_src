REASONING PER FLAGGED PIN

- GPIO12 (SAFFRON_LED): CONFIRMED (not a guess) simple GPIO-driven LED,
  active-high, via vendor's own MIT-licensed sample code (source 3a).
  TAGGED: capabilities ["digital_output", "led_high", "pwm_output"] in
  board.json chipGpios (pwm_output kept since it was already present on
  GPIO12 in the chip-level default; analog_input_serial/digital_input
  dropped per the LED-tag exclusion rule in the audit playbook section 7a).
  Not TX/RX (board's TX=1/RX=3) so the tag is not overridden by the
  serial-pin hard-reservation in build_boards.js.

- GPIO2 (WHITE_LED): CONFIRMED (not a guess) simple GPIO-driven LED,
  active-high, via vendor's own MIT-licensed sample code (source 3a) AND
  independently corroborated by the separate Blink_LED_Test sketch (3b)
  which explicitly comments "HIGH is the voltage level" = on. Also matches
  this board's own pins_arduino.h LED_BUILTIN=2 declaration (pre-existing,
  unflagged boilerplate). TAGGED: ["digital_output", "led_high",
  "pwm_output"]. Not TX/RX.

- GPIO13 (GREEN_LED): CONFIRMED (not a guess) simple GPIO-driven LED,
  active-high, via vendor's own MIT-licensed sample code (source 3a).
  TAGGED: ["digital_output", "led_high", "pwm_output"]. Not TX/RX.
  NOTE: three separate single-color LED tags used (led_high on each of
  GPIO2/12/13 individually), NOT led_r_high/led_g_high/led_b_high - no
  evidence found anywhere (vendor code, product description, or naming)
  that these are one physical packaged RGB LED; the Saffron/White/Green
  naming and the vendor's own sequential (not simultaneous/color-mixing)
  blink pattern both point to three discrete single-color LEDs.

- GPIO17 (TX2) / GPIO16 (RX2): CONFIRMED general-purpose (not a guess of
  "probably fine" - actively verified absence of any dedicated onboard
  consumer). These are the classic ESP32's default UART2 pins, broken out
  to the header as this board's secondary hardware serial port. No vendor
  source (product page, official GitHub sample code covering SD card, LED,
  and other Node-WiFi-specific projects) ties them to an onboard GSM/LoRa/
  GPS module - this specific "Node WiFi" SKU has no such module (those are
  BharatPi's separate A7672S-4G and LoRa product lines, each with its own
  already-audited board.json in this repo). LEFT AS-IS: no board.json
  chipGpios change, no pins_arduino.h edit - both remain normal available
  GPIOs. Mentioned in the board.json's top NOTE comment as the board's
  secondary UART for future reviewers' context, but no pin-level
  exclusion or special tag was warranted.

GUESS VS NO-GUESS SUMMARY
- No guesses were made. Every tagging/exclusion decision above is backed by
  either the vendor's own MIT-licensed GitHub sample code (LED polarity/
  independence, SD card pin usage) or a documented absence of evidence
  after actively searching for a TX2/RX2-to-peripheral connection (product
  page, pinout page attempts, GitHub project folder listing).
- Sources that were attempted but failed/were unhelpful (bharatpi.net direct
  fetch, edgehax.com PDF mirror, r.jina.ai proxy of both, Hackster.io page)
  are recorded above as dead ends so a future reviewer doesn't re-attempt
  the same failing fetches expecting a different result - the GitHub sample
  code ended up being the decisive, sufficient source for all 5 pins.

SUMMARY
- GPIO12/SAFFRON_LED, GPIO2/WHITE_LED, GPIO13/GREEN_LED: tagged "led_high"
  (+ pwm_output, kept from chip default) in board.json chipGpios - three

- GPIO17/TX2, GPIO16/RX2: confirmed general-purpose secondary UART, NOT
  excluded - left available, no board.json chipGpios change, no
